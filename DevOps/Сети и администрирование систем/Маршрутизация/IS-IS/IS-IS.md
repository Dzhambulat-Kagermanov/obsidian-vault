### Этапы установления соседства (adjacency) в IS-IS:

* **New** - состояние когда процесс установления соседства только начинается. Маршрутизатор переходит в это состояние в момент загрузки или при настройке начальной конфигурации IS-IS;
* **One-Way** - IS-IS маршрутизатор переходит в это состояние после Hello PDU. Маршрутизатор находится в этом состоянии пока не будет получен Hello PDU пакет, содержащий адрес локального маршрутизатора в качестве соседа;
* **Initializing** - состояние в которое переходит маршрутизатор при получении Hello PDU пакета, в котором указан его собственный локальный адрес в качестве соседа. Это состояние означает, что была установлена двунаправленная связь;
* **Up** - состояние полного функционирования отношений IS-IS. Это состояние означает, что были сформированы отношения соседства и произошла синхронизация баз данных маршрутизаторов;
* **Down** - состояние утерянного соседства. IS-IS маршрутизатор переходит в это состояние по одной из нескольких причин: несоответствие зоны (area), окончание таймаута удержания или ошибка аутентификации;
* **Reject** - состояние маршрутизатора после сбоя проверки подлинности. IS-IS маршрутизатор будет постоянно менять свое состояние между этим и состоянием Down.

Так же как и в OSPF для установления соседства используется сообщения типа Hello - IS-IS Hello, но есть несколько существенных отличий.

IS-IS также формирует соседства благодаря обмену сообщениями IS-IS Hello(IIH), но в отличие от OSPF, IS-IS имеет три разных типа Hello сообщений. Для рассылки Hello на широковещательных и на Point-to-Point интерфейсах в IS-IS используются разные типы сообщений. Помимо этого Hello для широковещательных интерфейсов делятся на два типа: Level 1 и Level 2. В итоге можно сказать, что мы имеем дело со следующими типами IS-IS Hello (или как их еще называют IIH):
1. Point-to-Point;
2. L1 LAN;
3. L2 LAN.

### Конфигурация IS-IS на маршрутизаторах:

#### Простая настройка (Все роутеры в L2):

```Router
! 1. Включаем процесс маршрутизации. Задаем имя процесса (локальное значение, не передается соседям)
R1(config)# router isis <CORE_NET>

! 2. Настраиваем NET
R1(config-router)# net 49.0001.0000.0000.0001.00
! 49 = частный AFI
! 0001 = Area ID
! 0000.0000.0001 = System ID (уникален!)
! 00 = N-SEL (всегда 00)

! 3. Выбираем уровень работы
R1(config-router)# is-type level-2-only
! Варианты: level-1, level-2-only, level-1-2 (по умолчанию)
! Для магистральных роутеров лучше level-2-only, чтобы не тащить лишнюю БД L1.

! 4. Включаем широкие метрики (ОБЯЗАТЕЛЬНО для современных сетей)
R1(config-router)# metric-style wide
! Старые метрики (narrow) имеют макс. значение 63 на линк и 1024 на путь.
! Wide позволяют использовать метрики до 16 миллионов, что нужно для TE и больших сетей.

! 5. Опционально: Отключаем проверку MTU (частая проблема при старте)
R1(config-router)# no lsp-mtu-check
! Если MTU на линках разный, IS-IS может не поднять соседство. 
! В продакшене лучше исправить MTU, но для лабы это полезно.

R1(config-router)# exit

! 6. Применяем на интерфейсах
R1(config)# interface GigabitEthernet0/0
R1(config-if)# ip address 10.1.12.1 255.255.255.252

! Включаем IS-IS на интерфейсе
R1(config-if)# ip router isis <CORE_NET>

! Задаем уровень соседства конкретно на интерфейсе (переопределяет глобальный is-type)
R1(config-if)# isis circuit-type level-2-only

! Задаем стоимость линка
R1(config-if)# isis metric 10 level-2
R1(config-if)# exit

! 7. Loopback интерфейс (анонсируем его в сеть)
R1(config)# interface Loopback0
R1(config-if)# ip address 1.1.1.1 255.255.255.255
R1(config-if)# ip router isis <CORE_NET>
R1(config-if)# exit
```

**metric-style** - это способ указать сколько метрик может быть для достижения цели. 
* Старый стиль: `metric-style narrow` (по умолчанию в старых IOS)
	* - **Размер поля метрики:** 6 бит.
		- **Максимальная метрика на один линк:** **63**.
		- **Максимальная метрика на весь путь:** **1024**.
		- **Проблема:**
		    1. Вы не можете задать стоимость линка больше 63. Если у вас есть линк 100 Гбит и линк 100 Мбит, вы не сможете адекватно отразить разницу в скорости (обоим придется давать числа в диапазоне 1-63).
		    2. Если сумма метрик пути превышает 1024, маршрут считается **недостижимым** (бесконечность). В больших сетях это легко превысить.
		    3. Не поддерживает расширения для Traffic Engineering (TE).
* Новый стиль: `metric-style wide` (стандарт для современных сетей)
	* - **Размер поля метрики:** 24 бита.
	- **Максимальная метрика на один линк:** **16 777 215**.
	- **Максимальная метрика на весь путь:** Огромное число (практически бесконечно для земных сетей).
	- **Преимущества:**
	    1. Можно гибко настраивать веса под любые скорости (от 1 Мбит до 400 Гбит).
	    2. Поддерживает **TLV для Traffic Engineering** (резервирование полосы пропускания, явные пути).
	    3. Обязателен для работы **Segment Routing**.
* `metric-style transition`: Отправлять и принимать оба типа. Полезно при миграции сети со старого оборудования на новое.

> **Важно!** Каждый интерфейс попадает в таблицу LSDB если ввести в интерфейсе `ip router isis <CORE_NET>`. Если маршрут должен пересылаться другим маршрутам то отключать такой интерфейс нельзя (`passive-interface <int>`).


#### Продвинутая настройка (Timers & Authentication):

```Router
R1(config)# router isis <CORE_NET>
! Ускорение таймеров (Hello каждые 100мс, Dead в 3 раза больше)
R1(config-router)# timers lsp-interval 50
R1(config-router)# timers spf 50 200 1000
! Логика: initial-wait 50ms, second-wait 200ms, max-wait 1000ms

! Настройка аутентификации (MD5)
R1(config-router)# area-password cisco123
! Или для конкретного уровня:
R1(config-router)# authenticate key-chain <MY_KEYS> level-2

R1(config-router)# exit

! Настройка ключей
R1(config)# key chain <MY_KEYS>
R1(config-keychain)# key 1
R1(config-keychain-key)# key-string SuperSecretKey
R1(config-keychain-key)# cryptographic-algorithm hmac-md5
```

### Полезная дополнительная информация:

#### Две независимые базы данных (LSDB) на одном роутере:

Когда роутер работает как `level-1-2`, он ведет **две полностью раздельные базы данных**. Маршруты из L2 **не появляются** в L1 автоматически (и наоборот). Без дополнительной настройки L1-роутеры не увидят маршруты из других областей! Эти базы НЕ синхронизируются автоматически!

#### Автоматическая генерация дефолта в L1 (ATT Bit)

Когда L1/L2 роутер имеет **хотя бы одно активное L2 соседство**, он автоматически устанавливает **ATT (Attached) бит** в своих L1 LSP.

L1/L2 роутер с рабочим L2-соседством:
1. Рассылает L1 LSP с битом ATT=1
2. L1 роутеры (R1, R2) видят ATT=1
3. L1 роутеры автоматически устанавливают **дефолтный маршрут** на этого L1/L2 роутера!

Если есть несколько L1/L2 роутеров на границе области, L1-роутеры получат **несколько дефолтных маршрутов** и будут балансировать трафик между ними. Это может быть как фичей, так и багом. Генерацию можно запретить или включить явно:

```Router
router isis <CORE_NET>
 ! Запретить генерацию дефолта в L1 (если не хотите)
 no attach-send-default
 ! Или явно включить (зависит от версии IOS)
 attach-send-default
```

#### Разные настройки метрик и таймеров на уровнях

На L1/L2 роутере можно (и иногда нужно) задавать **разные параметры для L1 и L2**:

```Router
interface GigabitEthernet0/0
 ! Для L1-соседей ставим метрику 10
 isis metric 10 level-1
 ! Для L2-соседей ставим метрику 50 (чтобы трафик предпочитал другой путь в ядре)
 isis metric 50 level-2
```

Разные таймеры:

```Router
router isis CORE
 ! L1: более агрессивные таймеры для быстрой реакции внутри области
 timers lsp-interval 50 level-1
 ! L2: более консервативные для стабильности ядра
 timers lsp-interval 200 level-2
```

Разная аутентификация:

```Router
router isis <CORE_NET>
 ! L1: простая аутентификация внутри доверенной области
 area-password cisco123
 ! L2: строгая аутентификация на магистральных линках
 authenticate key-chain BACKBONE_KEYS level-2
```

Если на интерфейсе не указан уровень (`level-1` или `level-2`), применяется глобальная настройка `is-type` или дефолтное поведение.

#### Потребление ресурсов (CPU / RAM):

L1/L2 роутер — самый "тяжелый" с точки зрения ресурсов:

|Ресурс|L1 only|L2 only|L1/L2|
|---|---|---|---|
|**Размер LSDB**|Только своя область|Только backbone|Обе базы|
|**Количество SPF-расчетов**|При изменениях в L1|При изменениях в L2|При изменениях в любом уровне|
|**Память под LSP**|~N LSP|~M LSP|~(N+M) LSP|
|**CPU при конвергенции**|Низкая|Средняя|Высокая (два отдельных расчета)|

**Рекомендация:**
- В больших сетях выносите функции L1/L2 на отдельные, более мощные роутеры;
- Обычные "листовые" роутеры делайте `level-1-only` или `level-2-only`.

#### Пассивные интерфейсы и уровни:

Команда `passive-interface` ведет себя по-разному в зависимости от уровня.

```Router
router isis CORE
 ! Этот интерфейс будет пассивным ТОЛЬКО для L1
 passive-interface Loopback0 level-1
 ! А этот — для обоих уровней
 passive-interface Loopback1
```

> Важно! Если вы забудете сделать Loopback пассивным, IS-IS будет рассылать на него Hello-пакеты, которые никуда не денутся. Это не критично, но засоряет логи и тратит ресурсы.

#### Конфликт адресации областей:

На L1/L2 роутере **все интерфейсы уровня 1 должны иметь одинаковый Area ID** в NET. L1-соседство требует совпадения Area ID. L2-соседство — не требует.

```Router
! ❌ НЕПРАВИЛЬНО:
interface Gi0/0  ! подключен к Area 49.0001
 isis circuit-type level-1

interface Gi0/1  ! подключен к Area 49.0002
 isis circuit-type level-1

router isis CORE
 net 49.0001.0000.0000.0001.00  ! Area ID = 49.0001

! Результат: Соседство на Gi0/1 НЕ ПОДНИМЕТСЯ, 
! потому что Area ID в NET роутера (49.0001) 
! не совпадает с областью соседа (49.0002).

! ✅ ПРАВИЛЬНО:
! На интерфейсах L1 — одна область.
! На интерфейсах L2 — можно соединять любые области,
! потому что L2 не проверяет Area ID.
```

#### Взаимодействие с другими протоколами (Redistribution):

Если вы делаете редистрибьюцию (например, из BGP или статических маршрутов) на L1/L2 роутере, нужно явно указать **в какой уровень** анонсировать маршруты.

```Router
router isis CORE
 ! Анонсировать статические маршруты ТОЛЬКО в L2 (в ядро)
 redistribute static ip level-2
 
 ! А анонсировать подключенные сети и в L1, и в L2
 redistribute connected ip level-1-2
 
 ! Или с фильтрацией:
 redistribute bgp 65001 level-2 route-map BGP_TO_ISIS
```

**Без указания уровня** маршруты могут попасть не туда, куда вы ожидаете (зависит от дефолтов вендора).

#### Отсутствие автоматического "Route Leaking" (протекания маршрутов):

**Route Leaking** — это механизм ручного "переливания" (анонсирования) маршрутов из одного уровня IS-IS в другой. В контексте IS-IS термин "leaking" обычно относится к направлению **L2 → L1**.

По умолчанию в IS-IS работает так:
* L1 → L2: Автоматически (префиксы из области попадают в ядро);
* L2 → L1: НЕ автоматически (кроме дефолтного маршрута через ATT-бит);

###### Почему так сделано?

1. **Масштабирование**: L1-роутеры не должны хранить всю таблицу маршрутизации интернета или большой сети провайдера. Им достаточно знать "как выйти наружу".
2. **Изоляция**: Сбои или изменения в ядре (L2) не должны вызывать пересчет маршрутов на периферии (L1).
3. **Простота**: Принцип "default route up, specific routes down" — классический подход иерархической маршрутизации.

##### Почему может понадобиться leaking?



Пользователь за **R1** хочет попасть на сервер **10.10.10.0/24** за **R4**.

![[Снимок экрана 2026-03-11 141233.png|697]]

| Роутер         | Что видит в таблице                              | Куда отправит пакет           |
| -------------- | ------------------------------------------------ | ----------------------------- |
| **R1 (L1)**    | `0.0.0.0/0 via R2` (дефолт от ATT-бита)          | На R2 (любой трафик "наружу") |
| **R2 (L1/L2)** | `10.10.10.0/24 via R3` (из L2 LSDB)              | На R3, через ядро             |
| **R3 (L1/L2)** | `10.10.10.0/24 via R4` (из L1 LSDB Area 49.0002) | На R4                         |
| **R4 (L1)**    | `10.10.10.0/24 connected`                        | На сервер ✅                   |

**В чем проблема?**

1. **Нет контроля**: Вы не можете применить политику к конкретному префиксу на границе области, потому что L1-роутеры его "не видят";
2. **Субоптимальность**: Если есть два выхода из области (R2 и R2b), R1 будет балансировать **весь** межобластной трафик между ними, даже если для конкретного префикса один путь явно лучше;
3. **Отладка**: На R1 вы не увидите в `show ip route` конкретный маршрут `10.10.10.0/24`, только дефолт. Сложнее диагностировать проблемы.

**Настройка переливания с L2 → L1 в R2 и R3:**

```Router
ip prefix-list IMPORTANT-SERVICES seq 5 permit 10.10.10.0/24

! Route-map для фильтрации:
route-map LEAK_SPECIFIC permit 10
 match ip address prefix-list IMPORTANT-SERVICES
 set metric 50 level-1      ! Задаем метрику для "протекшего" маршрута
 set tag 200                ! Помечаем тегом для идентификации

router isis CORE
 ! Разрешаем "протекание" маршрутов из L2 в L1
 redistribute isis ip level-2 into level-1 route-map LEAK_SPECIFIC
```

**Преимущества:**

- Теперь R1 **видит конкретный маршрут** к серверу;
- Можно задать **разные метрики** для разных префиксов при "протекании";
- Можно применять **политики** (QoS, PBR) на L1-роутерах для конкретных сетей;
- **Тег (tag 200)** помогает отфильтровать "протекшие" маршруты при дальнейшей редистрибьюции.

##### Критически важный механизм: Up/Down бит

Когда маршрут "протекает" из L2 в L1, IS-IS устанавливает специальный **Up/Down (U/D) бит** в соответствующем TLV. Зачем он нужен? **Предотвращение петель маршрутизации.** Маршрут с U/D=1 ("пришел сверху из L2"). НЕ МОЖЕТ быть переслан обратно в L2. 

**Пример процесса:**

```Schema

R1 (L1/L2) ----> AREA A (L1) <---- L2 Backbone ----> AREA B (L2) <---- R2 (L1/L2)

```

1. Сеть 10.0.0.0/24 существует в Area B;
2. R2 "протекает" её в L1 Area B (ставит U/D=1);
3. R1 видит этот маршрут в L1 от R2;
4. R1 НЕ имеет права анонсировать этот маршрут с U/D=1 обратно в L2!;
5. Петля невозможна.
