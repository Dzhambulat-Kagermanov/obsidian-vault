## 1. Что такое логирование

**Логирование (logging)** — регистрация событий, происходящих в программной системе, в форме записей, которые можно сохранить, передать и проанализировать. 

**Лог (log)** — отдельная запись или совокупность таких записей. 

**Журнал** — упорядоченное хранилище записей.

**Событие** — факт, который система сочла значимым: вход пользователя, начало обработки запроса, ошибка соединения, изменение конфигурации, перезапуск процесса. Запись в логе — *представление* события, а не само событие: приложение может не записать важный факт, записать его с задержкой или неточно описать причину.

Пример:

```text
2026-11-14T10:15:23.412Z INFO auth-service request_id=7a91 user_id=482 action=login result=success
2026-11-14T10:15:25.019Z WARN api-gateway request_id=8b12 status=429 route=/api/orders
2026-11-14T10:15:28.105Z ERROR payments request_id=9c23 error=upstream_timeout duration_ms=3000
```

Первая запись сообщает об успешной аутентификации, вторая — об ограничении частоты запросов, третья — о тайм-ауте при обращении к зависимому сервису. Но без контекста нельзя автоматически утверждать, что тайм-аут вызван именно сетью или что ответ `429` является неисправностью.

### 1.1. Зачем нужны логи

- **Диагностика:** выяснить, что произошло перед сбоем, и найти вероятную причину.
- **Эксплуатация:** видеть запуск, остановку, обновление и изменение состояния компонентов.
- **Безопасность и аудит:** исследовать попытки входа, изменения прав, доступ к ресурсам и действия администраторов.
- **Анализ поведения:** понимать, какие операции выполнялись и как они завершились.
- **Подтверждение событий:** иметь временную последовательность для разбора инцидента; при этом логи не становятся автоматически юридически достоверными доказательствами.

**Ключевой принцип:** логировать нужно то, что помогает ответить на конкретный операционный вопрос. Большой объем записей сам по себе не означает хорошую наблюдаемость.

## 2. Логи в модели Observability

**Observability (наблюдаемость)** — способность судить о внутреннем состоянии системы по ее внешним сигналам. Обычно рассматривают три взаимодополняющих источника: логи, метрики и трассировки.

| Сигнал | Основной вопрос | Пример | Сильная сторона | Ограничение |
|---|---|---|---|---|
| Логи | Что именно произошло? | `payment rejected: insufficient_funds` | Контекст конкретного события | Объем, неполнота, неоднородность |
| Метрики | Насколько часто и насколько сильно? | Доля ошибок 5xx за 5 минут | Эффективная агрегация и алерты | Мало подробностей отдельного случая |
| Трассировки | Где и по какому пути прошел запрос? | API → auth → database | Связь операций между сервисами | Семплирование и необходимость инструментирования |

Пример расследования: метрика показывает рост ошибок HTTP 500; трассировка указывает на задержку вызова БД; лог приложения содержит код ошибки SQL и идентификатор запроса. Каждый сигнал отвечает на свою часть вопроса.

Логи могут существовать без метрик и трассировок, но максимальная польза достигается при **корреляции**: одинаковые `trace_id`, `span_id`, `request_id` и согласованные временные метки связывают события между системами.

### 2.1. Логи не заменяют аудит

Операционный лог описывает работу приложения. **Аудиторский журнал** предназначен для отслеживания значимых действий субъектов: кто, когда, что изменил, к какому ресурсу обратился и с каким результатом. Для аудита обычно строже требования к полноте, доступу, срокам хранения и защите от изменений. Не каждую строку `INFO` следует считать аудиторским событием.

## 3. Жизненный путь записи

Упрощенная цепочка:

```text
Источник события
  → формирование записи
  → локальный вывод (stdout/stderr, файл, journald, Syslog)
  → сборщик / агент
  → обработка и маршрутизация
  → транспорт
  → приемник / хранилище
  → индексирование или организация потоков
  → запросы, визуализация, оповещения
  → архивирование / удаление по политике хранения
```

Этапы не обязательны в каждой системе: маленькое приложение может писать только в файл, а контейнерное приложение — в stdout, который считывает среда исполнения. Отдельные компоненты могут объединять несколько функций.

| Этап | Задача | Типичные риски |
|---|---|---|
| Генерация | Зафиксировать полезный контекст | Событие не записано; секрет попал в лог |
| Локальная запись | Пережить кратковременные сбои сети | Переполнение диска; потеря при завершении |
| Сбор | Прочитать новые записи | Пропуск после ротации; дублирование |
| Обработка | Разобрать, обогатить, отфильтровать | Потеря полей; некорректный парсинг |
| Доставка | Передать на следующий узел | Недоступность сети; переполнение очереди |
| Хранение | Обеспечить поиск и retention | Высокая стоимость; неудачная схема индексации |
| Использование | Поиск, корреляция, алерты | Ложные выводы; высокая задержка запроса |

Подробности архитектуры и способов надежной доставки вынесены в самостоятельные заметки.

## 4. Источники логов

### 4.1. По происхождению

1. **Ядро и ОС:** сообщения ядра, загрузка, системные службы, события доступа и аудита.
2. **Приложения:** бизнес-операции, ошибки, фоновые задания, API-запросы.
3. **Веб- и прокси-серверы:** access logs и error logs, коды ответов, маршруты, длительность обработки.
4. **Базы данных:** подключения, ошибки запросов, медленные запросы, репликация.
5. **Контейнеры и оркестраторы:** stdout/stderr контейнеров, события запуска, изменения состояния рабочих нагрузок.
6. **Сетевое оборудование:** маршрутизаторы, коммутаторы, межсетевые экраны, VPN-шлюзы.
7. **Системы безопасности:** аутентификация, IDS/IPS, контроль привилегий, события политики доступа.
8. **Облачные платформы:** действия в управляющем API, сетевые потоки, события управляемых сервисов.

### 4.2. По назначению

- **Access log:** факт обращения к ресурсу; не обязательно содержит полный результат внутренней обработки.
- **Error log:** сообщения об ошибках и исключениях.
- **Audit log:** действия субъектов и изменения, значимые для контроля.
- **Application log:** события бизнес-логики и внутренней работы.
- **Security log:** потенциально опасные действия, проверки, блокировки.
- **Debug/trace log:** диагностические подробности, которые обычно ограничивают по времени или объему.

Один источник может порождать несколько типов журналов, а одно событие — попадать в несколько журналов. Важно заранее понимать, где находится *авторитетная* запись для конкретного вопроса.

## 5. Анатомия записи

Минимально полезная запись должна отвечать на вопросы **когда, где, что произошло, с каким результатом и с каким контекстом**.

Пример структурированного события:

```json
{
  "timestamp": "2026-11-14T10:15:28.105Z",
  "severity": "ERROR",
  "service": "payments",
  "environment": "production",
  "host": "app-02",
  "event_name": "payment.provider.timeout",
  "message": "Payment provider did not respond before deadline",
  "request_id": "9c23",
  "trace_id": "4f8e0a12c6d743f0a9c1b7d5e8f210ab",
  "duration_ms": 3000,
  "outcome": "failure"
}
```

| Поле | Для чего нужно | Нюанс |
|---|---|---|
| `timestamp` | Время события | Указывать часовой пояс; предпочтительно UTC и ISO 8601/RFC 3339 |
| `severity` | Важность сообщения | Не является доказательством масштаба инцидента |
| `service`, `host` | Источник | Имена и адреса могут меняться; полезны стабильные идентификаторы |
| `environment` | Контур | Не смешивать production и test без маркировки |
| `event_name` | Машинно-стабильный тип события | Предпочтительнее парсинга произвольного текста |
| `message` | Понятное человеку описание | Формулировка может меняться между версиями |
| `request_id`, `trace_id` | Корреляция | Не всегда уникальны глобально; учитывать область генерации |
| `duration_ms` | Числовой контекст | Единицы измерения должны быть явными |
| `outcome` | Результат операции | Полезен для фильтрации успехов и отказов |

Не все поля обязательны всегда. Для системных событий вместо `request_id` могут быть важны `pid`, `unit`, `uid`, `process`, `facility` или `errno`.

### 5.1. Время события и время приема

Нужно различать:

- **Event time:** когда событие произошло по часам источника.
- **Ingestion time:** когда запись принял сборщик или хранилище.
- **Processing time:** когда запись была обработана конкретным компонентом.

При сетевых задержках, очередях и неверно настроенных часах эти значения могут расходиться. Поэтому для расследований важны синхронизация времени (NTP/chrony), указание временной зоны и контроль задержки доставки.

### 5.2. Многострочные сообщения

Stack trace, сообщения Java/Python и некоторые SQL-ошибки занимают несколько строк. Если агент считает каждую строку отдельным событием, контекст распадается. Решение — **multiline-объединение** на этапе сбора по надежным правилам. Оно требует ограничений по времени и размеру, иначе может увеличивать память и задержку обработки.

## 6. Уровни важности и смысл событий

Часто используются уровни:

| Уровень | Типичное назначение | Пример |
|---|---|---|
| `TRACE` | Максимальная детализация внутреннего выполнения | Проход по этапам алгоритма |
| `DEBUG` | Данные для диагностики разработчиком | Параметры выбранной ветки обработки |
| `INFO` | Обычное значимое событие | Сервис запущен, задача завершена |
| `WARN` / `WARNING` | Необычная ситуация без обязательного отказа | Повторная попытка соединения |
| `ERROR` | Операция завершилась ошибкой | Не удалось сохранить объект |
| `FATAL` / `CRITICAL` | Критический отказ компонента | Процесс не может продолжать работу |

Названия и порядок уровней зависят от библиотеки и системы. Например, Syslog определяет собственную шкалу severity от 0 (Emergency) до 7 (Debug), а многие прикладные библиотеки используют TRACE/DEBUG/INFO/WARN/ERROR/FATAL. **Нельзя механически приравнивать все шкалы без явного сопоставления.**

### 6.1. Практические правила

- Обычные успешные действия не должны автоматически получать `WARN` или `ERROR`.
- Одна неудачная попытка соединения с успешным повтором может быть `WARN`, а не инцидентом.
- Уровень записи не заменяет метрики доступности и влияния на пользователей.
- Не записывать каждую итерацию горячего цикла на уровне `INFO`.
- На время диагностики можно временно повысить детализацию, затем вернуть ее обратно.
- События безопасности и аудита не следует терять из-за отключения отладочных логов.

## 7. Формы представления логов

### 7.1. Неструктурированный текст

```text
Payment failed for order 9132 after 3000 ms
```

Прост для человека, но сложен для надежного автоматического поиска по полям.

### 7.2. Полуструктурированный текст

```text
level=error service=payments order_id=9132 duration_ms=3000 result=timeout
```

Удобнее фильтровать, однако нужны правила экранирования значений с пробелами и специальными символами.

### 7.3. Структурированные записи

```json
{"level":"error","service":"payments","order_id":9132,"duration_ms":3000,"result":"timeout"}
```

Позволяют типизированно обрабатывать поля. При формате JSON Lines/NDJSON обычно одна JSON-запись занимает одну строку. Однако структурированность сама по себе не гарантирует единых названий полей, корректных типов и согласованной семантики.

**Важно:** формат записи, транспортный протокол и формат хранения — разные понятия. JSON может передаваться через разные транспорты; Syslog — не синоним обычного текстового файла; journald хранит структурированные поля в собственном журнале.

## 8. Качество и надежность логов

### 8.1. Полнота

Лог может отсутствовать из-за ошибки приложения, отключенной детализации, переполнения буфера, недоступного диска или потерь при передаче. **Отсутствие записи не доказывает отсутствие события.**

### 8.2. Дублирование

При повторной отправке после сбоя подтверждения одно событие может быть доставлено несколько раз. В распределенных системах часто проще обеспечить доставку *как минимум один раз* (at-least-once), чем гарантировать ровно один экземпляр во всех компонентах. При анализе полезны идентификаторы событий и механизмы дедупликации.

### 8.3. Порядок

Порядок поступления записей не всегда равен порядку событий: разные хосты имеют разные часы, а очереди и повторные отправки меняют последовательность. Для расследования нужны исходные временные метки и идентификаторы причинно связанных операций.

### 8.4. Кардинальность

**Кардинальность** — количество различных значений поля или сочетаний полей. `environment=production` имеет низкую кардинальность, а уникальный `request_id` — высокую. Высокая кардинальность полезна для точного поиска, но может дорого обходиться, если такие значения используются как индексируемые метки или измерения. Конкретные ограничения зависят от хранилища; особенно важно учитывать это при проектировании labels в Loki.

### 8.5. Контроль полезности

Проверять не только наличие записей, но и:

- Долю успешно разобранных сообщений.
- Задержку между событием и появлением в поиске.
- Потери и переполнения очередей.
- Объем событий по источникам и уровням.
- Наличие обязательных полей и согласованность времени.
- Способность связать ошибку с запросом, сервисом и версией развертывания.

## 9. Логи, безопасность и конфиденциальность

Логи нередко содержат идентификаторы пользователей, IP-адреса, URL, тела запросов, токены или фрагменты персональных данных. Поэтому журналирование требует отдельной политики безопасности.

**Не следует записывать:** пароли, приватные ключи, access/refresh tokens, cookie сессий, полные платежные реквизиты и другие секреты. По возможности удалять или маскировать чувствительные данные **до записи или отправки**, а не рассчитывать только на последующую очистку в хранилище.

Основные меры:

1. Минимизация данных: фиксировать лишь необходимое для диагностики и аудита.
2. Разделение доступа: оператору приложения не обязательно видеть все поля безопасности.
3. Шифрование передачи и защита хранилища.
4. Политики хранения и удаления, согласованные с требованиями организации и применимым законодательством.
5. Контроль изменений и доступов к чувствительным журналам.
6. Защита от **log injection**: пользовательский ввод может содержать переводы строк, управляющие символы или поддельные поля; его нужно безопасно кодировать.

Не стоит считать журнал «неизменяемым» только потому, что он отправлен на удаленный сервер: для подтверждаемой целостности нужны дополнительные механизмы и разграничение полномочий.

## 10. Объем, стоимость и разумная детализация

Приближенный объем до сжатия:

\[
V_{day} \approx R \times S \times 86400
\]

где `R` — среднее число событий в секунду, `S` — средний размер записи в байтах. Например, при 200 событиях/с и 500 байтах на событие получится около **8,64 ГБ/сутки** (в десятичных единицах), или примерно **259,2 ГБ за 30 суток** до учета репликации, индексов, служебных данных и сжатия.

Это оценка, а не прогноз фактического размера хранилища: реальные затраты зависят от пиков, структуры полей, алгоритмов сжатия, индексации и числа копий.

### 10.1. Что увеличивает объем

- Слишком подробный уровень `DEBUG` в production.
- Запись больших тел HTTP-запросов и ответов.
- Повторяющиеся сообщения в частом цикле.
- Неограниченные stack traces и многострочные события.
- Дублирование на разных этапах конвейера.
- Высокая кардинальность индексируемых полей.

### 10.2. Что помогает

- Стабильные имена событий и разумные уровни логирования.
- Ограничение размера записей и диагностической детализации.
- Выборочное логирование шумных, но малополезных событий.
- Семплирование подходящих технических событий с учетом риска потери редких ошибок.
- Разные сроки хранения для операционных, отладочных и аудиторских журналов.
- Метрики для массовых количественных сигналов вместо потока однотипных логов.

**Важно:** критичные события безопасности и необходимые аудиторские записи нельзя бездумно семплировать или отбрасывать.

## 11. Типичные ошибки проектирования

| Ошибка | Последствие | Более устойчивый подход |
|---|---|---|
| «Записываем вообще всё» | Диск, сеть и поиск перегружены | Определить вопросы и ценность событий |
| Только свободный текст | Хрупкие регулярные выражения | Структурированные поля и стабильный `event_name` |
| Нет `request_id` / `trace_id` | Невозможно связать сервисы | Прокидывать идентификаторы по цепочке запроса |
| Нет временной зоны | Ошибки в хронологии | UTC, синхронизация часов, явные timestamps |
| Секреты в логах | Утечка через журнал | Маскирование и минимизация на источнике |
| Логирование только ошибок | Не виден нормальный ход операций | Добавить ключевые жизненные события |
| Алерт на каждую строку `ERROR` | Шум и ложные срабатывания | Агрегация, контекст и пороги |
| Нет контроля доставки | Потери остаются незамеченными | Мониторить очереди, ошибки и задержку приема |
| Не определены сроки хранения | Рост затрат и рисков | Retention по типам данных |
| Уникальные ID как labels без оценки | Высокая нагрузка на индекс | Разделять индексируемые метки и поля записи |

## 12. Минимальные требования к хорошему событию

Перед добавлением новой записи в приложение полезно проверить:

1. **Назначение:** какой вопрос помогает решить событие?
2. **Контекст:** есть ли сервис, операция, результат и идентификатор корреляции?
3. **Время:** можно ли точно сопоставить его с другими событиями?
4. **Уровень:** соответствует ли важность реальному влиянию?
5. **Структура:** можно ли искать событие без разбора произвольной фразы?
6. **Безопасность:** нет ли секретов и избыточных персональных данных?
7. **Стоимость:** приемлемы ли частота, размер и срок хранения?
8. **Надежность:** понятно ли, что произойдет при недоступности получателя?

Хорошая запись должна быть **понятной человеку, пригодной для машинной обработки и достаточно экономичной для массового использования**.

## 13. Глоссарий

| Термин | Определение |
|---|---|
| Логирование (Logging) | Процесс регистрации событий программной системы |
| Событие (Event) | Значимый факт, произошедший в системе |
| Лог-запись (Log record) | Представление события в виде сообщения и/или набора полей |
| Источник (Source) | Приложение, служба, узел или устройство, формирующее события |
| Observability | Возможность судить о состоянии системы по доступным сигналам |
| Метрика (Metric) | Числовое измерение состояния или поведения во времени |
| Трассировка (Trace) | Связанная последовательность операций обработки запроса |
| Корреляция | Связывание записей, относящихся к одному запросу или инциденту |
| Severity | Уровень важности события |
| Structured logging | Представление записей в виде явно именованных полей |
| Parsing | Извлечение структурированных данных из входной записи |
| Enrichment | Добавление к записи контекста из других источников |
| Ingestion | Прием записей системой сбора или хранения |
| Retention | Политика и срок сохранения данных |
| Cardinality | Число различных значений поля или сочетаний полей |
| Label | Метка для классификации и, в некоторых системах, индексации потоков |
| Event time | Время возникновения события по источнику |
| Ingestion time | Время приема записи системой |
| Multiline | Объединение нескольких физических строк в одно логическое событие |
| Sampling | Выборочная регистрация или сохранение части событий |
| At-least-once | Модель доставки, допускающая дублирование при обеспечении повторных попыток |
| Log injection | Внедрение пользовательского содержимого, способного исказить структуру журнала |
| Audit log | Журнал действий, предназначенный для контроля и последующей проверки |

## Итоги — что было разобрано

- Логирование регистрирует **представления событий**, а не гарантированно полную историю происходящего.
- Логи, метрики и трассировки дополняют друг друга; корреляция повышает ценность каждого сигнала.
- Запись проходит путь от источника через сбор, обработку и доставку до хранения и анализа.
- Качество логов зависит от контекста, структуры, временных меток, уровней и идентификаторов корреляции.
- В распределенных системах нужно учитывать потери, дублирование, задержки и нарушение порядка.
- Полезность логирования определяется вопросами, на которые можно ответить, а не числом записей.
- Безопасность, кардинальность, объем и сроки хранения должны учитываться еще при проектировании событий.
