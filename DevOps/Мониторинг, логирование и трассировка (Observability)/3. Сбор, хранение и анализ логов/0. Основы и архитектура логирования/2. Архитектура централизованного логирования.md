## 1. Назначение и границы централизованного логирования

**Централизованное логирование** — организация сбора событий из нескольких источников, их передачи, обработки, хранения и поиска через общую инфраструктуру. Его цель — не просто скопировать `/var/log` с каждого сервера, а обеспечить управляемый поток событий, доступный для диагностики, анализа и расследований.

Локальное журналирование остается необходимым: если сеть или центральная платформа недоступны, операционная система должна продолжать регистрировать события. Центральная система дополняет локальную, но не должна быть единственной точкой записи критически важных событий.

**Граница этой заметки:** архитектурные компоненты, топологии, маршруты данных, отказоустойчивость и проектные решения. Синтаксис конфигураций конкретных агентов, языки запросов и настройки хранилищ подробно рассматриваются в отдельных заметках.

### 1.1. Какие задачи решает система

- Единый поиск событий по многим серверам и приложениям.
- Сопоставление событий одной операции между сервисами по `trace_id`, `request_id` и другим идентификаторам.
- Расследование ошибок, изменений и инцидентов даже после потери исходного узла.
- Контроль доступности потока логов: обнаружение пропавших источников, ошибок доставки и переполненных очередей.
- Централизованное применение правил доступа, маскирования и сроков хранения.

**Важно:** централизованное логирование не равно мониторингу. Мониторинг отвечает, *что изменилось и когда нужно реагировать*; логи дают подробные сведения о конкретных событиях. Оповещения могут строиться на логах, но сами по себе логи не заменяют метрики и трассировки.

## 2. Логический конвейер событий

```text
Источники               Сбор                 Обработка              Хранение            Потребители
┌────────────────┐   ┌────────────────┐   ┌──────────────────┐   ┌───────────────┐   ┌────────────────┐
│ Linux / systemd│──▶│ Локальный     │──▶│ Парсинг, фильтры │──▶│ Loki /        │──▶│ Поиск и        │
│ Контейнеры     │   │ агент         │   │ нормализация,    │   │ Elasticsearch │   │ дашборды       │
│ Приложения     │   │ или forwarder │   │ обогащение      │   │ ClickHouse    │   │ алерты, анализ │
│ Сетевые узлы   │──▶│ Syslog-прием  │──▶│ маршрутизация   │──▶│               │──▶│                │
└────────────────┘   └────────────────┘   └──────────────────┘   └───────────────┘   └────────────────┘
                            │                      │
                            └──── очереди / буферы ┘
```

Это **логические роли**, а не обязательные отдельные серверы. Например, один агент может одновременно читать файлы, разбирать JSON, добавлять метки и отправлять события. В небольшой системе некоторые роли объединяются; при росте нагрузки их разделяют.

### 2.1. Источник (producer)

Источником бывает приложение, ОС, контейнерный runtime, сетевое устройство или облачная служба. Источник определяет исходный формат события, точность временной метки и объем генерируемых данных.

Примеры:

- Сервис пишет JSON-строки в `stdout`.
- `systemd-journald` принимает сообщения служб и ядра.
- Nginx пишет access/error logs в файлы.
- Маршрутизатор отправляет Syslog по сети.

### 2.2. Коллектор (collector / agent)

Коллектор читает событие и передает его дальше. Его задачи могут включать сохранение позиции чтения файла, объединение многострочных сообщений, локальную буферизацию и повторные попытки передачи.

Распространенные подходы:

- **Агент на узле:** Fluent Bit, Vector, Filebeat, Grafana Alloy.
- **Сетевой приемник:** rsyslog или другой Syslog-сервер.
- **Коллектор платформы:** сервис приема событий на промежуточном узле.
- **Прямая отправка приложением:** возможна, но повышает связанность приложения с системой логирования и требует аккуратной обработки сбоев.

### 2.3. Обработка (processing)

Обработка приводит неоднородные записи к удобному для поиска виду:

1. Декодирование входного формата (JSON, Syslog, обычная строка).
2. Выделение полей (`timestamp`, `severity`, `service`, `host`, `message`).
3. Нормализация имен и типов полей.
4. Добавление контекста (окружение, кластер, namespace).
5. Удаление или маскирование секретов и персональных данных.
6. Отбор, маршрутизация и при необходимости ограничение потока.

Нельзя бездумно удалять «шумные» события: фильтрация может лишить команду данных для расследования. Правила отбора должны быть документированы.

### 2.4. Хранилище (backend)

Хранилище обеспечивает запись, срок хранения и выполнение запросов. Подходы различаются:

| Подход | Типичный пример | Что важно при проектировании |
|---|---|---|
| Индексация множества полей | Elasticsearch | Стоимость индекса, схема полей, ресурсы кластера |
| Индекс по меткам и хранение содержимого логов | Grafana Loki | Кардинальность меток, потоковая организация данных |
| Колоночная аналитика | ClickHouse | Схема таблиц, сортировка, партиционирование, запросы |

Не следует считать, что эти системы имеют одинаковые модели данных, требования к ресурсам или возможности полнотекстового поиска.

### 2.5. Потребители

Пользователями данных выступают администраторы, разработчики, специалисты безопасности, автоматизированные проверки и системы оповещения. Для каждой роли нужны подходящие права и способы доступа.

## 3. Физические топологии

### 3.1. Прямой сбор с каждого узла

```text
server-01 ─ agent ─┐
server-02 ─ agent ─┼──▶ центральное хранилище ──▶ интерфейс поиска
server-03 ─ agent ─┘
```

**Преимущества:** минимум компонентов, простая диагностика, удобен для небольшого числа узлов.

**Ограничения:** каждый агент должен знать конечную точку; при сбое хранилища нагрузка на локальные буферы растет; возможны всплески повторных отправок после восстановления.

### 3.2. Промежуточный слой приема и обработки

```text
узлы ──▶ локальные агенты ──▶ приемники/коллекторы ──▶ хранилище
                                   │
                            обработка и очереди
```

**Преимущества:** централизованная маршрутизация, независимое масштабирование приема, единые правила обработки.

**Ограничения:** дополнительные узлы и точки отказа; необходимо контролировать буферы, пропускную способность и задержки.

### 3.3. Сбор из нескольких площадок

```text
Площадка A: серверы ──▶ локальный сборщик ──┐
                                            ├──▶ защищенный канал ──▶ центральная платформа
Площадка B: серверы ──▶ локальный сборщик ──┘
```

Локальные сборщики полезны при нестабильном WAN, но не обеспечивают сохранность автоматически: требуются устойчивые очереди, достаточный объем диска и политика действий при долгом обрыве связи.

### 3.4. Pull и push

- **Push:** источник или агент сам отправляет события получателю. Типично для Syslog и многих log-forwarders.
- **Pull:** коллектор опрашивает API или читает доступный ресурс. Применимо к отдельным внешним системам и сервисам.

Большинство файловых и journald-агентов *локально читают* записи, а затем *отправляют* их дальше. Это не следует путать с сетевой моделью pull.

## 4. Границы ответственности и выбор места обработки

| Функция | На источнике/агенте | На промежуточном коллекторе | В хранилище |
|---|---|---|---|
| Чтение локального файла | Да | Обычно нет | Нет |
| Склейка многострочных событий | Часто предпочтительно | Возможно | Обычно поздно |
| Удаление секретов | Желательно как можно раньше | Дополнительная защита | Не должно быть единственным рубежом |
| Нормализация общих полей | Базовая | Удобно централизовать | Зависит от продукта |
| Очередь при сбое сети | Желательна | Желательна | Приемные механизмы продукта |
| Индексация и запросы | Нет | Обычно нет | Да |

**Принцип:** чем раньше из потока удалены чувствительные данные, тем меньше мест, где они могут оказаться. Но агрессивная обработка на каждом узле усложняет централизованное изменение правил.

## 5. Метаданные и схема событий

Для корреляции полезно договориться об общей схеме. Минимальный набор полей:

| Поле | Назначение | Пример |
|---|---|---|
| `timestamp` | Время возникновения события | `2026-11-14T18:20:30.123Z` |
| `observed_timestamp` | Время приема коллектором | `2026-11-14T18:20:30.250Z` |
| `severity` | Уровень важности | `ERROR` |
| `service.name` | Имя службы | `api-gateway` |
| `host.name` | Узел-источник | `app-01` |
| `environment` | Среда | `production` |
| `message` | Человекочитаемое сообщение | `upstream timeout` |
| `trace_id` | Связь с распределенной трассировкой | идентификатор трассы |

Пример структурированного события:

```json
{
  "timestamp": "2026-11-14T18:20:30.123Z",
  "severity": "ERROR",
  "service.name": "api-gateway",
  "host.name": "app-01",
  "environment": "production",
  "message": "Upstream request timed out",
  "request_id": "req-6e42",
  "duration_ms": 3000
}
```

Это **пример проектной схемы**, а не обязательный стандарт для всех продуктов. Конкретные платформы могут требовать иные имена полей или формат меток.

### 5.1. Время и порядок событий

В распределенной системе часы разных узлов могут расходиться. Поэтому:

- Синхронизируйте время узлов (NTP/chrony).
- Храните временную зону явно, предпочтительно UTC.
- Отличайте время события от времени его приема.
- Не рассчитывайте, что записи из разных узлов всегда придут в исходном порядке.
- Учитывайте задержку буферизации и повторной отправки.

### 5.2. Метки и кардинальность

Для систем с индексированием меток используйте устойчивые признаки (`service`, `environment`, `cluster`). Не превращайте уникальные `request_id`, `session_id` или пользовательские идентификаторы в индексные метки без понимания последствий: это может резко увеличить число потоков и стоимость хранения. Такие значения часто лучше оставлять в содержимом события или структурированных полях.

## 6. Надежность и семантика доставки

### 6.1. Где теряются события

1. Приложение не записало событие из-за ошибки или завершения процесса.
2. Файл был ротирован до того, как агент дочитал его.
3. Локальный буфер переполнился.
4. Сетевое соединение оборвалось.
5. Приемник отказал или начал ограничивать запросы.
6. Хранилище отклонило запись из-за квот, формата или перегрузки.

Успешная запись в локальный журнал **не доказывает**, что событие оказалось в центральном хранилище.

### 6.2. At-most-once, at-least-once и exactly-once

- **At-most-once:** событие доставляется не более одного раза; при сбое возможна потеря.
- **At-least-once:** повторные попытки уменьшают риск потери, но возможны дубликаты.
- **Exactly-once:** требует специальных гарантий на всем пути; нельзя обещать ее только потому, что агент поддерживает retry.

В реальных конвейерах часто разумно проектировать доставку с повторными попытками и быть готовым к дубликатам. Если устранение дубликатов критично, нужны идентификаторы событий и согласованная логика обработки.

### 6.3. Буферы

**Буфер в памяти** быстрый, но может быть потерян при аварийном завершении. **Дисковый буфер** устойчивее к кратковременным сбоям, но занимает место и тоже имеет предел. Для каждого буфера необходимо задать:

- максимальный размер;
- допустимое время накопления;
- политику при переполнении (блокировать, отбрасывать, деградировать);
- поведение после рестарта;
- метрики глубины очереди и числа ошибок.

Подробные механизмы очередей рассматриваются в отдельной заметке.

## 7. Планирование пропускной способности и емкости

### 7.1. Базовая оценка

Приближенный объем исходных логов в сутки:

\[
V_{day} = N \times R \times S \times 86400
\]

где:

- `N` — количество источников;
- `R` — среднее число событий в секунду на источник;
- `S` — средний размер события в байтах.

**Пример:** 50 серверов, 20 событий/с с каждого, средняя запись 500 байт:

```text
50 × 20 × 500 × 86400 = 43 200 000 000 байт/сутки
≈ 43,2 GB/сутки (десятичные единицы)
```

За 30 суток это примерно **1,296 TB исходных данных** без учета сжатия, индексов, репликации и служебных накладных расходов. Фактическая емкость зависит от выбранного хранилища и характеристик событий.

### 7.2. Что учитывать сверх среднего объема

- Пиковую интенсивность во время ошибок и аварий.
- Дополнительные индексы и метаданные.
- Репликацию и резервные копии.
- Коэффициент сжатия на реальных данных.
- Временные файлы и операции обслуживания.
- Резерв свободного места для восстановления после сбоев.

Средняя нагрузка не определяет максимальную: в момент инцидента логов часто становится значительно больше.

## 8. Безопасность архитектуры

### 8.1. Защита передачи

Передача между узлами должна использовать защищенные каналы там, где это поддерживается: TLS, проверку сертификатов, взаимную аутентификацию при необходимости, ограничения доступа на сетевом уровне. **Syslog поверх UDP** не дает подтверждения доставки и шифрования сам по себе.

### 8.2. Защита содержимого

В логах не должны бесконтрольно появляться пароли, токены, cookies, приватные ключи, полные платежные данные и другие секреты. Маскирование на уровне интерфейса просмотра не устраняет проблему, если исходные значения уже записаны в хранилище.

### 8.3. Разграничение доступа

Разделяйте роли:

- агент может записывать события, но не удалять исторические записи;
- оператор видит только нужные сервисы и окружения;
- администратор платформы управляет конфигурацией;
- доступ к чувствительным журналам аудита ограничивается отдельно.

Сроки хранения и требования к неизменяемости журналов зависят от задач организации и нормативных обязательств; универсального значения нет.

## 9. Отказоустойчивость и масштабирование

### 9.1. Отказ источника

Если сервер недоступен, ранее переданные события остаются в центральной системе. Однако последние события могли не успеть покинуть локальный буфер.

### 9.2. Отказ сети

При наличии дисковой очереди агент может временно накапливать события. Требуется расчет: `скорость генерации × максимальная длительность обрыва`, с запасом на пиковую нагрузку.

### 9.3. Отказ приемника

Несколько приемников и балансировка уменьшают риск единой точки отказа, но сами по себе не гарантируют сохранность данных. Нужны проверка готовности, корректные таймауты, retry и устойчивые очереди.

### 9.4. Отказ хранилища

Репликация, резервное копирование и восстановление решают разные задачи:

- **Репликация** повышает доступность, но может размножить ошибочное удаление.
- **Резервное копирование** позволяет восстановить данные из отдельной копии.
- **Retention** автоматически удаляет старые данные по политике и не заменяет резервное копирование.

## 10. Наблюдаемость самого конвейера

Система логирования тоже должна контролироваться. Минимальный набор показателей:

| Показатель | Что выявляет |
|---|---|
| Входящие события/байты в секунду | Рост нагрузки и резкое снижение потока |
| Ошибки отправки | Проблемы сети, авторизации или приемника |
| Повторные попытки | Нестабильность доставки |
| Заполнение очереди | Риск переполнения и потерь |
| Задержка между событием и приемом | Отставание конвейера |
| Отклоненные события | Ошибки формата, лимиты и квоты |
| Свободное место и скорость роста хранилища | Риск остановки приема |
| Отсутствие событий от ожидаемого источника | Сбой агента, источника или маршрута |

**Важная тонкость:** отсутствие ошибок в логах самого агента не доказывает, что он получает все события. Нужны контроль объема входного потока и проверка наличия ожидаемых источников.

## 11. Выбор архитектуры по масштабу

| Сценарий | Возможная схема | Ключевой риск |
|---|---|---|
| Небольшая лаборатория | Агент на узле → одно хранилище | Единая точка отказа |
| Небольшая инфраструктура | Агенты → централизованное хранилище с резервными копиями | Рост объема и буферов |
| Несколько площадок | Локальные сборщики → защищенная передача → центральная платформа | Долгие обрывы WAN |
| Высокая нагрузка | Масштабируемые приемники/очереди → распределенное хранилище | Сложность эксплуатации и согласованности |

Это **варианты проектирования**, а не жесткие пороги по количеству серверов. Выбор определяется фактической интенсивностью событий, допустимыми потерями, сроками хранения, бюджетом и компетенциями команды.

## 12. Порядок проектирования

1. **Инвентаризировать источники:** ОС, приложения, контейнеры, сетевые устройства, API.
2. **Определить потребителей:** диагностика, безопасность, аудит, эксплуатация.
3. **Согласовать поля:** время, источник, сервис, среда, корреляционные идентификаторы.
4. **Оценить нагрузку:** средние и пиковые события/с, размер записей, рост за сутки.
5. **Определить требования:** допустимые потери, задержка доставки, срок хранения, доступность.
6. **Выбрать топологию:** прямой сбор или промежуточные приемники; локальные буферы.
7. **Выбрать хранилище:** с учетом типа запросов, кардинальности, бюджета и эксплуатационных требований.
8. **Спроектировать безопасность:** шифрование, учетные данные, разграничение доступа, маскирование.
9. **Настроить контроль конвейера:** метрики, алерты, тестовые события и проверка сквозной доставки.
10. **Проверить отказы:** отключение сети, остановка приемника, заполнение буфера, восстановление после рестарта.

## 13. Типичные архитектурные ошибки

**Ошибка 1.** Отправлять логи только напрямую в центральную систему без локального буфера. При недоступности приемника события могут теряться.

**Ошибка 2.** Считать, что TLS обеспечивает надежность доставки. TLS защищает канал, но не гарантирует, что запись сохранена в хранилище.

**Ошибка 3.** Использовать уникальный идентификатор каждого запроса как индексную метку в Loki. Это может привести к высокой кардинальности и росту затрат.

**Ошибка 4.** Ориентироваться только на среднюю скорость генерации. Во время массового сбоя поток логов может многократно возрасти.

**Ошибка 5.** Хранить все события бесконечно. Без retention емкость будет исчерпана; бессистемное удаление может нарушить требования к расследованиям.

**Ошибка 6.** Собирать секреты, рассчитывая скрыть их позднее в интерфейсе. Они уже попадут в транспорт, буферы и хранилище.

**Ошибка 7.** Мониторить только доступность Loki/Elasticsearch, но не поступление событий от конкретных источников.

**Ошибка 8.** Смешивать форматирование, бизнес-логику и сетевую доставку внутри приложения без четкой ответственности.

## 14. Глоссарий

| Термин | Определение |
|---|---|
| **Producer (источник)** | Компонент, создающий событие журнала |
| **Collector (коллектор)** | Компонент, принимающий или считывающий события для дальнейшей обработки |
| **Forwarder** | Агент, пересылающий события другому компоненту |
| **Pipeline (конвейер)** | Последовательность стадий от источника до потребителя |
| **Ingestion** | Прием событий платформой обработки или хранения |
| **Parsing** | Разбор текста или формата записи на поля |
| **Normalization** | Приведение полей и значений к согласованной схеме |
| **Enrichment** | Добавление контекста к событию |
| **Retention** | Правило срока хранения и удаления старых данных |
| **Backpressure** | Ситуация, когда нижестоящий компонент не успевает принимать поток, что требует замедления или буферизации |
| **Retry** | Повторная попытка отправки после ошибки |
| **Durable queue** | Очередь с сохранением данных на устойчивом носителе |
| **At-least-once** | Семантика доставки с возможными повторами, но с попыткой не терять подтвержденные события |
| **Cardinality** | Число уникальных сочетаний значений меток или иных индексируемых признаков |
| **Ingestion lag** | Задержка между созданием события и его поступлением в систему |
| **Correlation ID** | Идентификатор для связывания событий одной операции |
| **Single Point of Failure** | Компонент, отказ которого нарушает работу всей системы |

## Итоги — что было разобрано

- Централизованное логирование состоит из логических ролей: источник, сбор, обработка, хранение и потребление.
- Агенты, промежуточные коллекторы и хранилища можно объединять или масштабировать независимо в зависимости от нагрузки.
- Архитектура должна учитывать сбои, буферизацию, возможные дубликаты, временные метки и контроль доставки.
- Модель данных и метки влияют на стоимость и качество поиска.
- Безопасность, retention и наблюдаемость самого конвейера закладываются при проектировании, а не добавляются после внедрения.
