## Введение

Балансировка нагрузки — это эволюция простого проксирования. Если проксирование направляет весь трафик на один сервер, то балансировка распределяет его между группой серверов (пулом). Это решает две главные задачи современной инфраструктуры: **масштабируемость** (горизонтальное добавление серверов для обработки большего числа запросов) и **высокую доступность** (исключение сбойных узлов из ротации без прерывания обслуживания клиентов).

В Nginx балансировка реализуется через блок `upstream` и тесно интегрирована с механизмами проксирования, описанными в [[Synced/DevOps/Балансировка, проксирование и веб-сервера/1. Классические веб-серверы и обратные прокси/1. Nginx/3. Проксирование.md | Проксировании]].

> [!INFO] Связь с другими темами
> 
> - Эффективность балансировки напрямую зависит от [[Synced/DevOps/Балансировка, проксирование и веб-сервера/1. Классические веб-серверы и обратные прокси/1. Nginx/1. Архитектура.md | Архитектуры Nginx]], так как worker-процессы независимо выбирают серверы из общего пула.
> - Для stateful-приложений балансировка требует настройки [[Synced/DevOps/Глоссарий.md#Липкие сессии (Sticky Sessions / Session Persistence) | липких сессий]], что часто считается антипаттерном в пользу внешних хранилищ сессий (например, Redis).

## 1. Алгоритмы балансировки: как Nginx выбирает сервер

Nginx поддерживает несколько алгоритмов распределения трафика. Выбор алгоритма зависит от архитектуры приложения и характера нагрузки.

### Таблица алгоритмов балансировки

|Алгоритм|Директива|Принцип работы|Когда использовать|
|---|---|---|---|
|**Round Robin**|(по умолчанию)|Запросы распределяются по кругу, с учетом веса (`weight`) каждого сервера.|Stateless-приложения, однородные серверы, стандартный веб-трафик.|
|**Least Connections**|`least_conn;`|Запрос отправляется на сервер с наименьшим количеством _активных_ в данный момент соединений. Учитывает вес.|Долгие запросы (WebSockets, тяжелые API-вычисления), неоднородные по мощности серверы.|
|**IP Hash**|`ip_hash;`|Сервер выбирается на основе хэш-функции от IP-адреса клиента (первые три октета IPv4 или весь IPv6).|Устаревшие приложения, требующие привязки сессии к конкретному серверу (sticky sessions).|
|**Generic Hash**|`hash key [consistent];`|Сервер выбирается на основе хэша произвольной переменной Nginx (например, `$uri`, `$cookie_sessionid`, `$arg_user`).|Кэширующие прокси, шардирование баз данных, строгая привязка по идентификатору.|

### Механизм работы Round Robin и Weight

По умолчанию Nginx использует взвешенный Round Robin. Если у нас есть сервера с весами 3, 2 и 1, Nginx не просто отдает 3 запроса первому, а затем 2 второму. Он использует "виртуальные узлы" для максимально равномерного распределения в коротких промежутках времени.

```nginx
upstream backend_pool {
    server 10.0.0.10:8080 weight=3; # Получит ~50% трафика
    server 10.0.0.11:8080 weight=2; # Получит ~33% трафика
    server 10.0.0.12:8080 weight=1; # Получит ~17% трафика
}
```

## 2. Управление состоянием серверов в пуле

Помимо веса, каждому серверу в блоке `upstream` можно назначить специальные флаги состояния.

```nginx
upstream backend_pool {
    server 10.0.0.10:8080 max_conns=100; # Ограничение: не более 100 активных соединений на этот сервер
    
    server 10.0.0.11:8080 backup;        # Резервный: получает трафик только если все основные серверы недоступны
    
    server 10.0.0.12:8080 down;          # Отключен: временно выведен из ротации (например, для деплоя или обслуживания)
    
    server 10.0.0.13:8080 max_fails=3 fail_timeout=30s; # Пассивная проверка здоровья
}
```

### Как работает пассивная проверка здоровья (`max_fails` и `fail_timeout`)

Это встроенный механизм open-source Nginx.

1. Если Nginx не может соединиться с сервером или получает ошибку (по умолчанию: 502, 503, 504), он увеличивает счетчик неудач.
2. Когда счетчик достигает `max_fails` (по умолчанию 1), сервер помечается как недоступный.
3. Сервер игнорируется в течение `fail_timeout` (по умолчанию 10 секунд).
4. По истечении этого времени Nginx отправит _один_ пробный запрос на этот сервер. Если он успешен, сервер возвращается в строй. Если нет — таймер сбрасывается.

> [!WARNING] Ограничение пассивных проверок
> При сбое сервера первые несколько запросов (до достижения `max_fails`) все равно будут направлены на него и завершатся ошибкой (клиент получит 502 Bad Gateway). Для критичных систем это неприемлемо.

## 3. Проблема липких сессий (Sticky Sessions)

Если приложение хранит данные сессии пользователя в оперативной памяти конкретного сервера (in-memory session), все последующие запросы этого пользователя должны попадать на тот же сервер. Иначе пользователь будет постоянно "вылетать" из системы.

### Способ 1: `ip_hash` (Простой, но ненадежный)

```nginx
upstream app_backend {
    ip_hash;
    server 10.0.0.10:8080;
    server 10.0.0.11:8080;
}
```

**Недостатки**:

- Все пользователи за одним корпоративным NAT (с одним внешним IP) попадут на один сервер, что может вызвать дисбаланс нагрузки.
- При добавлении или удалении сервера из пула хэш-функция пересчитывается, и большинство пользователей "перепрыгнут" на другие серверы, потеряв свои сессии.

### Способ 2: Хэширование по куки (Рекомендуемый для Nginx)

Если приложение выдает уникальный идентификатор сессии (например, в cookie `SESSIONID`), можно балансировать по нему.

```nginx
upstream app_backend {
    # Хэшируем значение куки session_id. 
    # Ключевое слово 'consistent' включает согласованное хэширование (consistent hashing)
    hash $cookie_session_id consistent;
    
    server 10.0.0.10:8080;
    server 10.0.0.11:8080;
}
```

**Преимущество `consistent`**: При добавлении или удалении сервера из пула перераспределяется только та часть трафика, которая хэшировалась именно на этот измененный сервер. Остальные пользователи сохраняют привязку к своим серверам.

> [!TIP] Лучшая практика (Best Practice)
> В современной DevOps-архитектуре липкие сессии на уровне балансировщика считаются антипаттерном. Правильное решение — сделать приложение stateless и вынести хранение сессий во внешнее хранилище (Redis, Memcached или базу данных). Тогда можно смело использовать `least_conn` или `round_robin`.

## 4. Активные проверки здоровья (Active Health Checks)

Как упоминалось, open-source Nginx не умеет сам "пинговать" бэкенды. Для этого есть два пути:

### Путь А: Использование Nginx Plus (коммерческая версия)

```nginx
upstream backend {
    zone backend_pool 64k; # Требуется для разделения состояния между worker-процессами
    server 10.0.0.10:8080;
    server 10.0.0.11:8080;
    
    # Активная проверка каждые 5 секунд
    health_check interval=5s fails=3 passes=2 uri=/healthz match=status_200;
}

match status_200 {
    status 200;
}
```

### Путь Б: Сторонние модули или внешние инструменты

Для open-source Nginx можно скомпилировать сторонний модуль, например, `nginx_upstream_check_module` (от Tencent), или использовать внешний сервис (Consul, HAProxy, или кастомный скрипт на Python/Go), который будет динамически генерировать файл `upstream.conf` и делать `nginx -s reload` при изменении статуса серверов.

## 5. Практические сценарии для DevOps

### Сценарий 1: Canary-деплой (Постепенный rollout) через веса

Задача: выпустить новую версию приложения (v2) на 10% трафика, чтобы проверить стабильность, не затрагивая основную массу пользователей.

```nginx
upstream canary_backend {
    # 9 запросов из 10 идут на стабильную версию
    server 10.0.0.10:8080 weight=9; 
    
    # 1 запрос из 10 идет на новую версию
    server 10.0.0.20:8080 weight=1; 
}

server {
    location / {
        proxy_pass http://canary_backend;
    }
}
```

_После мониторинга метрик (ошибки, latency) веса можно плавно менять: 8/2, 5/5, 0/10, а затем полностью переключить `proxy_pass` на новый upstream._

### Сценарий 2: Обслуживание сервера down time-а (Draining)

Задача: вывести сервер `10.0.0.11` на техническое обслуживание, не разрывая текущие сессии.

```nginx
upstream backend {
    server 10.0.0.10:8080;
    server 10.0.0.11:8080 down; # Новые запросы сюда не идут
    server 10.0.0.12:8080;
}
```

_После применения этой конфигурации (`nginx -s reload`) сервер `10.0.0.11` продолжит обрабатывать уже установленные соединения (благодаря архитектуре graceful reload), но новые запросы будут распределяться только между `.10` и `.12`. Когда активные соединения на `.11` иссякнут, его можно безопасно выключать._

### Сценарий 3: Автоматизация через Ansible (динамический upstream)

```jinja2
# templates/upstream.conf.j2
upstream {{ app_name }}_backend {
    least_conn; # Используем least_conn для неоднородной нагрузки
    
    {% for host in groups['app_servers'] %}
    server {{ hostvars[host]['ansible_default_ipv4']['address'] }}:{{ app_port }} weight={{ hostvars[host].get('weight', 1) }};
    {% endfor %}
    
    # Резервный сервер на случай падения всего основного пула
    server {{ backup_server_ip }}:{{ app_port }} backup;
}
```

## 6. Troubleshooting и типичные проблемы

|Проблема|Причина|Решение|
|---|---|---|
|Все запросы возвращают `502 Bad Gateway`|Все серверы в upstream помечены как недоступные (достигнут `max_fails`).|Проверить доступность бэкендов вручную (`curl`). Увеличить `max_fails` или `fail_timeout`, если сеть нестабильна. Проверить, не заблокировал ли firewall трафик.|
|Неравномерное распределение нагрузки при `ip_hash`|Клиенты находятся за общим прокси/NAT (один внешний IP).|Перейти на хэширование по куки (`hash $cookie_session_id`) или сделать приложение stateless.|
|Сессии пользователей сбрасываются при добавлении сервера|Используется `ip_hash` или обычный `hash` без ключевого слова `consistent`.|Добавить ключевое слово `consistent` к директиве `hash` или перенести сессии в Redis.|
|Ошибка `no live upstreams while connecting to upstream`|В блоке `upstream` не осталось серверов без флага `down` или все они признаны нерабочими.|Проверить конфигурацию на наличие хотя бы одного активного сервера. Убедиться, что `backup` сервер не помечен как `down`.|
|Один сервер перегружен, другие простаивают при `least_conn`|Долгие запросы на одном сервере "заблокировали" его, но Nginx все равно считает его доступным, или веса настроены некорректно.|Проверить метрики самого приложения. Убедиться, что `keepalive` настроен корректно, иначе `least_conn` может работать неэффективно из-за постоянных пересозданий соединений.|
