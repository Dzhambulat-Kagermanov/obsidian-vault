## Введение

Проксирование — это самая частая задача Nginx в DevOps. Nginx выступает посредником: клиент обращается к Nginx, а Nginx передает запрос на реальное приложение (Node.js, Python, Java и т.д.) и возвращает ответ клиенту.

Понимание того, как именно Nginx передает запросы, управляет заголовками и соединениями, позволяет избежать 90% типичных ошибок, таких как "502 Bad Gateway", "504 Gateway Timeout" или ситуаций, когда приложение видит IP-адрес самого Nginx вместо реального клиента.

## 1. Главная ловушка: слеш в конце `proxy_pass`

Поведение директивы `proxy_pass` кардинально меняется в зависимости от того, есть ли в ней URI (путь) после домена или порта. Это самая частая причина ошибок "404 Not Found" на бэкенде.

**Простое правило:**

- Если в `proxy_pass` **нет URI** (просто `http://backend`), Nginx передает исходный запрос клиента **без изменений**.
- Если в `proxy_pass` **есть URI** (например, `http://backend/` или `http://backend/api`), Nginx **заменяет** ту часть запроса, которая совпала с `location`, на указанный URI.

### Таблица примеров

|Конфигурация|Запрос клиента|Что уйдет на бэкенд|Почему?|
|---|---|---|---|
|`location /api/`  <br>`proxy_pass http://backend;`|`/api/users`|`/api/users`|Нет URI в `proxy_pass`. Передается как есть.|
|`location /api/`  <br>`proxy_pass http://backend/;`|`/api/users`|`/users`|Есть URI (`/`). Совпавший `/api/` заменяется на `/`.|
|`location /api/`  <br>`proxy_pass http://backend/v2/;`|`/api/users`|`/v2/users`|Есть URI (`/v2/`). Совпавший `/api/` заменяется на `/v2/`.|

> [!WARNING] Ограничение для регулярных выражений
>Если в `location` используется регулярное выражение (например, `location ~ ^/api/`), указывать URI в `proxy_pass` **запрещено**. Nginx выдаст ошибку. В этом случае передастся исходный URI, а изменить его можно только с помощью директивы `rewrite`.

## 2. Передача реальных данных клиента (Прокси-заголовки)

По умолчанию, когда Nginx делает запрос к бэкенду, он представляется сам собой. Бэкенд видит, что запрос пришел с IP-адреса Nginx, и что используется протокол HTTP (даже если клиент пришел по HTTPS).

Чтобы приложение работало корректно (например, для логирования IP или генерации правильных ссылок), мы должны вручную передать исходные данные через заголовки. Обычно это выносят в отдельный файл `/etc/nginx/proxy_params` и подключают через `include`.

```nginx
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

**Что делает каждая строка:**

1. `Host $host`: Передает оригинальный домен из запроса клиента. Нужно, если на одном бэкенде крутится несколько сайтов.
2. `X-Real-IP $remote_addr`: Прямой IP-адрес того, кто подключился к Nginx.
3. `X-Forwarded-For $proxy_add_x_forwarded_for`: Цепочка всех IP-адресов, через которые прошел запрос. Nginx берет существующий заголовок (если он был) и добавляет через запятую IP клиента.
4. `X-Forwarded-Proto $scheme`: Протокол, который использовал клиент (`http` или `https`). Критично важно для приложений, которые делают редиректы.

## 3. Балансировка нагрузки: блок `upstream`

Блок `upstream` позволяет указать несколько серверов вместо одного в `proxy_pass`.

```nginx
http {
    upstream my_app {
        server 10.0.0.10:8080 weight=3;  # Получит 3 запроса из 5
        server 10.0.0.11:8080 weight=2;  # Получит 2 запроса из 5
        server 10.0.0.12:8080 backup;    # Работает, только если первые два упали
        server 10.0.0.13:8080 down;      # Временно выведен из строя (например, на обслуживание)
    }

    server {
        location / {
            proxy_pass http://my_app;
        }
    }
}
```

### Алгоритмы балансировки

| Метод                 | Директива      | Когда использовать                                                                                                            |
| --------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **Round Robin**       | (по умолчанию) | Стандартный вариант. Запросы идут по кругу. Идеально для одинаковых серверов без состояния (stateless).                       |
| **Least Connections** | `least_conn;`  | Запрос идет на сервер, где сейчас меньше всего активных соединений. Идеально для долгих запросов (WebSockets, тяжелые API).   |
| **IP Hash**           | `ip_hash;`     | Клиент с одним IP всегда попадает на один и тот же сервер. Нужно, если приложение хранит сессии в своей памяти, а не в Redis. |
### Пассивные проверки здоровья (Health Checks)

В бесплатной версии Nginx проверки работают пассивно. Если Nginx не может достучаться до сервера или получает ошибку 5xx, он помечает его как "недоступный" на заданное время и перестает слать туда запросы.

```nginx
upstream my_app {
    # Если 3 раза подряд ошибка или таймаут, исключить сервер на 30 секунд
    server 10.0.0.10:8080 max_fails=3 fail_timeout=30s;
}
```

## 4. Оптимизация: Keepalive и Буферизация

### Keepalive (Переиспользование соединений)

По умолчанию Nginx закрывает соединение с бэкендом после каждого запроса. При высокой нагрузке постоянные TCP-рукопожатия (handshakes) сжигают процессорное время. Мы можем заставить Nginx держать пул открытых соединений.

```nginx
upstream my_app {
    server 10.0.0.10:8080;
    keepalive 32; # Держать до 32 свободных соединений открытыми
}

server {
    location / {
        proxy_pass http://my_app;
        proxy_http_version 1.1;
        proxy_set_header Connection ""; # КРИТИЧНО ВАЖНО!
    }
}
```

>[!WARNING] Ловушка Keepalive
>Строка `proxy_set_header Connection "";` обязательна. По умолчанию Nginx шлет бэкенду `Connection: close`. Если не переопределить это на пустое значение, бэкенд закроет соединение, и весь механизм keepalive не сработает.

### Proxy Buffering (Буферизация)

По умолчанию `proxy_buffering on;`. Nginx считывает ответ от быстрого бэкенда в свою память, а затем отдает его медленному клиенту.

- **Плюс**: Бэкенд мгновенно освобождается и может обрабатывать новые запросы.
- **Минус**: Увеличивается время до получения первого байта (TTFB) для очень больших ответов.

**Когда отключать (`proxy_buffering off;`)**: При проксировании потокового видео, Server-Sent Events (SSE) или больших файловых загрузок, где важно отдавать данные клиенту сразу же, по мере их появления.

## 5. Проксирование WebSocket

WebSocket начинает жизнь как обычный HTTP-запрос, а затем "переключается" (upgrade) на постоянный двусторонний канал связи. Nginx должен явно разрешить это переключение, передав специальные заголовки.

```nginx
location /ws/ {
    proxy_pass http://websocket_backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    
    # Увеличиваем таймауты, так как WebSocket-соединения живут долго
    proxy_read_timeout 86400s;
    proxy_send_timeout 86400s;
}
```

## 6. Внутренняя маршрутизация: Named Locations

Блок `location`, имя которого начинается с `@` (например, `location @fallback`), называется именованным (named location). **Главное правило**: клиент не может обратиться к нему напрямую по URL. Он используется только для внутренних переходов внутри Nginx.

**Сценарий 1: Fallback при ошибке**

```nginx
location / {
    proxy_pass http://primary_backend;
    # Если основной сервер вернул 502 или 504, внутренне перенаправить запрос сюда
    error_page 502 504 = @fallback;
}

location @fallback {
    proxy_pass http://backup_backend;
}
```

**Сценарий 2: Статика с fallback-ом на приложение**

```nginx
location / {
    # 1. Ищем файл. 2. Ищем папку. 3. Если нет, идем в @app
    try_files $uri $uri/ @app;
}

location @app {
    proxy_pass http://nodejs_backend;
}
```

## 7. Динамический DNS (для Kubernetes и облаков)

По умолчанию Nginx преобразует доменное имя в IP-адрес только один раз — при запуске. Если в Kubernetes IP пода изменился, Nginx продолжит стучаться в старый IP до следующей перезагрузки.

**Решение**: использовать переменную в `proxy_pass` и директиву `resolver`.

```nginx
server {
    # Указываем внутренний DNS-сервер (например, CoreDNS в K8s) и время кэширования
    resolver 10.96.0.10 valid=30s;
    
    location /api/ {
        # Присваиваем адрес переменной
        set $backend_url "http://my-service.default.svc.cluster.local";
        # Используем переменную в proxy_pass
        proxy_pass $backend_url;
    }
}
```

>[!WARNING] Ограничение
>При использовании переменной в `proxy_pass` блок `upstream` использовать нельзя. Вы теряете встроенную балансировку и keepalive. Для сложных сценариев в K8s лучше использовать специальные Ingress-контроллеры или Nginx Plus.

## 8. Troubleshooting: типовые проблемы

|Симптом|Вероятная причина|Как проверить и исправить|
|---|---|---|
|**502 Bad Gateway**|Nginx не может установить TCP-соединение с бэкендом (он выключен, порт закрыт, firewall).|Выполнить с сервера Nginx: `curl -v http://ip_бэкенда:порт`. Проверить `error.log`.|
|**504 Gateway Timeout**|Соединение есть, но бэкенд думает дольше, чем разрешает `proxy_read_timeout` (по умолчанию 60с).|Увеличить `proxy_read_timeout 120s;` или оптимизировать медленный запрос в приложении.|
|**413 Request Entity Too Large**|Клиент загружает файл больше, чем разрешает `client_max_body_size` (по умолчанию 1МБ).|Добавить `client_max_body_size 50m;` в нужный блок `location` или `http`.|
|Приложение видит IP Nginx, а не клиента|Не настроены прокси-заголовки.|Добавить `proxy_set_header X-Real-IP $remote_addr;` и `X-Forwarded-For`.|
|**WebSocket отваливается через 60 сек**|Сработал дефолтный таймаут Nginx.|Добавить `proxy_read_timeout 86400s;` и `proxy_send_timeout 86400s;` в блок location.|
