## Введение

Операционная система (ОС) — это фундаментальный слой программного обеспечения, который абстрагирует аппаратные ресурсы компьютера и предоставляет унифицированный интерфейс для выполнения приложений. Для DevOps-инженера глубокое понимание принципов работы ОС критически важно: от диагностики проблем в production-среде до оптимизации контейнеризированных приложений и настройки инфраструктуры как кода.

## 1. Архитектура ОС: Ядро и Пользовательское пространство

### Ring-модель и привилегии

Это архитектурное разделение защиты процессора (x86). Уровни от 0 до 3 — это убывание привилегий. ОС чаще всего использует два крайних, игнорируя Rings 1–2 (они были для драйверов, но оказались неудобны).

- Ring 0 (Kernel Space) — «Режим супервизора».
      Процессор выполняет все инструкции, включая работу с портами ввода-вывода, прерываниями и таблицами страниц памяти. Ошибка здесь — Panic (отказ системы). Работает в едином адресном пространстве с ядром.
- Ring 3 (User Space) — «Режим ограничений».
      Доступ к «опасным» инструкциям (in, out, cli) заблокирован. Каждое приложение живет в своей виртуальной песочнице. При попытке "напрямую" тронуть чужую память или диск процессор выбрасывает исключение (Page Fault / GPF), и ОС убивает процесс.

Ключевой нюанс: Переключение между кольцами — дорогая операция (очистка конвейеров, смена контекста). Именно поэтому частые syscall'ы тормозят систему.

### Системные вызовы (syscalls)

Мост между user space и kernel space. Когда приложению нужен доступ к ресурсу (файл, сеть, память), оно вызывает syscall, который переключает процессор в kernel mode для выполнения операции.

Это не просто функция. Это аппаратно-программный протокол, который переключает режим без краха системы.

Как это работает (упрощенно):

1. Приложение кладет номер системного вызова и аргументы в регистры процессора.
2. Выполняется специальная инструкция (раньше int 0x80, сейчас syscall / sysenter).
3. Процессор мгновенно переключает уровень на Ring 0 и передает управление в фиксированную точку ядра (диспетчер syscalls).
4. Ядро проверяет аргументы (важно: все данные из пользователя копируются в ядро, а не используются напрямую во избежание взломов).
5. Выполняется операция, результат кладется обратно, и инструкция iret / sysexit возвращает процесс в User Space.

Что делает strace в вашем примере:
Он подключается к процессу и перехватывает момент входа и выхода из ядра. Для каждой команды он показывает:

- Имя вызова (openat).
- Аргументы (путь к файлу, флаги).
- Результат (дескриптор файла или код ошибки -1 ENOENT).
```bash
# Просмотр системных вызовов в реальном времени
strace -p <PID>
# Пример: отслеживание открытия файла
strace ls /tmp 2>&1 | grep open
```
`strace ls /tmp 2>&1 | grep open` фильтрует поток, показывая, сколько раз команда ls пыталась открыть папки и файлы, чтобы понять ее поведение.

> [!TIP] Связь с контейнеризацией
> Контейнеры используют те же syscalls, что и хост-ОС, но изолируются через namespaces и cgroups. Это ключевое отличие от [[1. Виртуализация (VM) vs Контейнеризация | Виртуализация (VM) vs Контейнеризация]], где каждая VM имеет своё ядро.

## 2. Управление процессами

### Процесс vs Поток

**Процесс**: Экземпляр программы с собственным адресным пространством, ресурсами и контекстом выполнения. Это не просто запущенная программа, а изолированная песочница для ресурсов.

- Адресное пространство — своя виртуальная память. Процесс №1 не видит переменные процесса №2 (защита через таблицы страниц памяти).
- Ресурсы — собственные дескрипторы открытых файлов, сокетов, буферы ввода-вывода.
- Контекст — полный слепок состояния регистров процессора + счетчик команд.

Ключевой нюанс: Переключение между процессами (Context Switch) — дорогое удовольствие. Процессору приходится:

1. Сохранять состояние текущего процесса.
2. Очищать кэш-память (TLB).
3. Загружать таблицы страниц нового процесса.

**Поток (Thread)**: Легковесная единица выполнения внутри процесса, разделяющая память и ресурсы с другими потоками того же процесса. Это маршрут выполнения внутри процесса.

- Общая память — все потоки видят одни и те же глобальные переменные, кучу и код. Это дает супер-быстрый обмен данными (без syscalls).
- Личное — у каждого потока только свой стек (для локальных переменных) и свой набор регистров.
- Переключение между потоками в 10–100 раз дешевле, чем между процессами, так как виртуальная память и файлы остаются прежними.

| Характеристика | Процесс                                 | Поток                                                                                   |
| -------------- | --------------------------------------- | --------------------------------------------------------------------------------------- |
| Падение        | Упал один процесс — остальные работают  | Упал один поток (Segfault) — падает весь процесс и все его потоки                       |
| Синхронизация  | Почти не нужна (память разделена редко) | Критична — без мьютексов два потока одновременно испортят общие данные (Race Condition) |
| Создание       | Медленное (копирование ресурсов)        | Быстрое (делит ресурсы родителя)                                                        |

### Планировщик (Scheduler)

Планировщик отвечает за распределение процессорного времени. Основные алгоритмы. Его задача — не дать одному процессу "задушить" другие и при этом минимизировать простои CPU (когда процесс ждет диск или сеть).

**CFS (Completely Fair Scheduler)** в Linux: использует "виртуальное время" для обеспечения справедливого распределения CPU. Это алгоритм по умолчанию в Linux для обычных задач (не реального времени). Его философия: "Каждому процессу — поровну процессорного времени, но с поправкой на вес".
- Виртуальное время (vruntime): Счетчик, который показывает, сколько "справедливого" времени процесс уже получил. Чем меньше vruntime у процесса, тем выше его приоритет на запуск.
- Красное дерево: Планировщик хранит все процессы, отсортированные по vruntime. Следующий на запуск — это процесс с наименьшим vruntime (тот, кто меньше всего работал).
- Как работает смена: Когда процесс отрабатывает свой квант (обычно ~4–6 мс), планировщик прибавляет к его vruntime реальное время работы и выбирает нового "бедолагу" из левого края дерева.

Ключевой нюанс: Если процесс уснул (ожидая ввода с клавиатуры), его vruntime не растет. Когда он просыпается, его vruntime оказывается сильно меньше, чем у "вычислителей", и планировщик немедленно дает ему CPU — так система остается отзывчивой (интерактивные задачи в приоритете).


- Приоритеты (nice value, RT-приоритеты) влияют на порядок выполнения.

## 3. Управление памятью

### Виртуальная память

Для приложения оперативная память выглядит как огромная непрерывная лента (адреса от 0 до 2^64). **Физическая** же память — это разрозненные микросхемы с реальными адресами.

**Зачем эта ложь?**

1. **Изоляция:** Процесс А не видит память процесса Б (они работают в своих виртуальных мирах).
2. **Упрощение:** Программисту не нужно думать, где именно лежат данные — компилятор просто ставит адрес 0x00.
3. **Экономия:** Процесс может занять 10 ГБ виртуальной памяти, а физически использовать только 100 МБ активных данных.

### Как это работает (Механика MMU + Paging)

Посредник между виртуальным миром и железом — **MMU** (Memory Management Unit) — аппаратный блок внутри процессора.

1. Процессор получает команду "прочитать по виртуальному адресу X".
2. MMU смотрит в **таблицу страниц** этого процесса (хранится в ядре).
3. Таблица разбита на блоки — **страницы** (обычно 4 КБ). MMU находит запись: "Виртуальная страница №5 → Физическая страница №120".
4. Если записи нет (страница выгружена или не выделена), процессор кидает **Page Fault** (исключение), и ядро решает, как быть.

### Ключевые механизмы:

#### 1. Paging (Страничная организация)

Память дробится на мелкие куски, чтобы не было "дыр". Если процессу нужно 10 МБ, ядро выделяет ему не одну непрерывную область, а множество страниц по 4 КБ, разбросанных по всей физической памяти.  
**Для DevOps:** Если вы видите в `vmstat` колонку `si` (swap in) и `so` (swap out) — это значит, что страницы активно летают на диск, и ваш сервис "тормозит" из-за нехватки физической RAM.

#### 2. Swap (Подкачка)

Это "аварийный резерв" на диске. Когда физическая память переполняется, ядро выбирает страницы, к которым давно не обращались, и записывает их на диск (освобождая RAM для активных задач).  
**DevOps-настройка:** Параметр **`vm.swappiness`** (от 0 до 100) регулирует агрессивность этой выгрузки.

- `0` — ядро почти не трогает swap (использует только при крайней необходимости — хорошо для БД, где важен отклик).
- `60` (по умолчанию) — баланс.
- `100` — агрессивная выгрузка (плохо для серверов, убивает производительность диска).

#### 3. MMU (Аппаратный транслятор)

Чтобы ускорить перевод адресов, процессор использует кэш TLB (Translation Lookaside Buffer). Если MMU не находит нужную страницу в кэше — это TLB miss, и трансляция замедляется.  
**Диагностика:** Если сервер внезапно начал "тормозить" без роста нагрузки — смотрите `dmesg | grep -i "out of memory"`. Там часто видны ошибки MMU или отказ выделения страниц.

#### 4. OOM Killer (Последний довод)

Когда памяти нет вообще, а swap заполнен, ядро запускает **убийцу процессов**. Он присваивает каждому процессу `oom_score` (насколько "жирный" процесс) и убивает того, у кого суммарная память + сброс кэша дает максимум.  
**DevOps-контроль:** Вы можете защитить важный сервис (например, PostgreSQL) от убийства, выставив **`oom_score_adj = -1000`** в настройках systemd — тогда ядро тронет его в последнюю очередь.

```bash
# Просмотр использования памяти
free -h
# Детальная информация о страницах
cat /proc/meminfo
# Мониторинг swap-активности
vmstat 1
```

## 4. Файловая система как абстракция

### VFS (Virtual File System)

Унифицированный интерфейс ядра для работы с разными типами ФС (ext4, XFS, NFS, procfs, sysfs). Это прослойка в ядре, которая делает все файловые системы похожими для пользовательского пространства. Благодаря VFS команда `ls` работает одинаково и с ext4 на жестком диске, и с виртуальной `/proc` (информация о процессах), и с сетевой NFS.

**Суть работы:**

1. Пользователь вызывает `read("/home/file.txt")`.
2. VFS получает запрос и смотрит, к какой файловой системе принадлежит путь.
3. VFS переводит общий вызов в **конкретную функцию-драйвер** этой ФС (например, `ext4_read` или `nfs_read`).
4. Драйвер общается с железом или сетью и возвращает данные обратно через VFS.

**Почему это важно для DevOps:** Системы мониторинга смотрят на **VFS-статистику** (`/proc/stat`), а не на отдельные диски. Если нагрузка на запись высокая, а конкретный диск `iostat` показывает простаивание — возможно, проблема в сетевой ФС (NFS) или в монтировании с неправильными опциями.

### Inode и метаданные

Inode — это **числовая структура**, описывающая объект файловой системы (файл, каталог, устройство). Самое важное: **имя файла — это не inode**. Имена хранятся в директориях, а inode — это "внутренний идентификатор" объектов.

**Что именно лежит в inode:**

1. **Права** (`chmod`) и **владельцы** (`chown`) — отвечают за доступ.
2. **Таймстампы**: `atime` (последнее чтение), `mtime` (изменение содержимого), `ctime` (изменение прав или владельца).
3. **Размер** и **прямые/косвенные указатели** на физические блоки на диске (где реально лежат байты файла).
4. **Счетчик ссылок** (`nlink`) — сколько папок указывают на этот inode. Если счетчик обнуляется, и файл никем не открыт — он физически стирается с диска.

**Ключевой нюанс для администрирования:** Inode — это **ограниченный ресурс**. Файловая система при форматировании выделяет фиксированное количество inode. Если вы создаете миллион микро-файлов (например, кэш изображений), вы можете заполнить **не место на диске**, а именно **таблицу inode**, и система откажется создавать новые файлы, даже если свободные гигабайты еще есть.

```bash
# Просмотр inode
ls -li /path/to/file
# Статистика по inode
df -i
```

- **Mount namespaces**: Изоляция точек монтирования — основа контейнеризации.

## 5. Ввод-Вывод (I/O) и устройства

### Блочные vs Символьные устройства

Это классификация устройств в UNIX-подобных системах, определяющая, как ядро передает им данные.

- **Блочные устройства (`/dev/sda`, `/dev/nvme0n1`)** — это диски.  
    Доступ к ним происходит **блоками** (обычно 4 КБ). Ядро применяет буферизацию и кэширование: запросы складываются в очередь и переупорядочиваются для повышения эффективности (объединение соседних запросов). Для приложения запись на такой диск выглядит как "быстрая", потому что данные сначала попадают в кэш страниц в памяти, а на диск сбрасываются асинхронно.
    
- **Символьные устройства (`/dev/tty`, `/dev/input/mouse0`)** — это терминалы, последовательные порты, мыши.  
    Доступ идет **потоком байтов** без буферизации и кэширования. Каждый символ передается «как есть» сразу же (или с минимальной задержкой). Здесь нет смысла переупорядочивать нажатия клавиш, поэтому данные идут напрямую в приложение.  

**DevOps-нюанс:** Если база данных (например, PostgreSQL) пишет на блочное устройство через `O_DIRECT`, она обходит кэш страниц, чтобы гарантировать сброс на диск. Символьные устройства в облачных средах почти не встречаются — они ушли в виртуальные терминалы (`/dev/pts`) и USB-устройства.

### I/O Schedulers

Планировщик I/O решает, **в каком порядке** отправлять запросы на диск. Это важно для HDD (где перемещение головки — секунды), но почти неактуально для NVMe (где задержки микросекундные):

1. **`mq-deadline`** (по умолчанию в центрах):  
    Дает гарантию, что ни один запрос не будет ждать дольше N секунд (deadline). Делит запросы на чтение и запись, приоритезируя чтение (интерактивность). Хорош для **универсальной нагрузки** и БД с перемешанным чтением/записью.
2. **`kyber`**:  
    Адаптивный планировщик для быстрых SSD/NVMe. Он сам регулирует глубину очереди, чтобы не перегружать контроллер. Рекомендован для **высоконагруженных облачных дисков**.
3. **`bfq`** (Budget Fair Queueing):  
    Балансирует пропускную способность между процессами (как CFS для дисков). Отлично подходит для **десктопов** и мультимедийных систем, где важна плавность, но на серверах может создавать лишнюю нагрузку на CPU.

**Как выбрать:** В современных системах ядро автоматически переключает планировщик при смене типа диска (e.g., `mq-deadline` для HDD, `none` для NVMe). Вмешательство нужно редко — только если вы видите в `iostat` высокое значение `await` (время ожидания) при низком `util`.

```bash
# Просмотр текущего планировщика
cat /sys/block/sda/queue/scheduler
# Мониторинг I/O
iostat -x 1
```

> [!TIP] Оптимизация
> Для баз данных ([[Synced/DevOps/Базы данных и хранилища/1. Реляционные СУБД (OLTP)/1. PostgreSQL/1. Архитектура|PostgreSQL]], [[1. Архитектура движков хранения|MySQL]]) часто рекомендуется `deadline` или `noop` на SSD.

## 6. Модель безопасности ОС

### Пользователи, группы, права

Это базовая модель **DAC (Discretionary Access Control)** — дискреционного управления доступом. Владелец файла сам решает, кто его может читать/писать/исполнять.

- **Права `rwx`** применяются к трем категориям: `user` (владелец), `group` (группа владельца), `others` (остальные). Проверка идет по порядку: если вы совпадаете с владельцем — применяются права `user`, иначе если вы в группе — права `group`, иначе — `others`.
- **SUID/SGID** — специальные биты, меняющие контекст выполнения:
    - **SUID** (4) — файл выполняется с правами **владельца** файла, а не запустившего пользователя. Классика: `/usr/bin/passwd` (владелец `root`) позволяет обычному пользователю менять пароль, записывая в защищенный `/etc/shadow`.
    - **SGID** (2) — выполнение с правами группы файла. На директориях SGID означает, что все новые файлы наследуют группу папки (полезно для общих проектов).
    - **Sticky Bit** (1) — на директориях запрещает удалять чужие файлы (`/tmp`).

### Расширенные механизмы

#### 1. Capabilities — «Дробление root»

Вместо монолитного `root` (все или ничего), Linux ядро делит привилегии на ~40 отдельных флагов. Процесс с `CAP_NET_BIND_SERVICE` может слушать порт 80, не имея других root-прав. Это снижает риски: если процесс взломают, злоумышленник получит только ограниченный набор возможностей.

**DevOps-практика:** Вместо запуска Java-приложений от root, выставляйте `cap_net_bind_service` и запускайте от обычного пользователя.

#### 2. SELinux/AppArmor — MAC (Обязательный контроль)

В отличие от DAC, где решения принимает владелец, **MAC** определяет **системный политик**, который нельзя обойти. Даже `root` ограничен.

- **SELinux** (RedHat/CentOS) — маркирует каждый объект (файл, процесс, сокет) контекстом безопасности (например, `system_u:object_r:httpd_sys_content_t`). Если контекст не совпадает с политикой — доступ блокируется. Сложен в настройке, но надежен.
- **AppArmor** (Ubuntu/Debian) — проще: профили ограничивают программы по путям (разрешено читать только `/etc/nginx/`, запрещено `/root/`).

**Для DevOps:** Если сервис падает с ошибкой "Permission denied", а права `rwx` верны — проверьте SELinux (`ls -Z` и `audit2allow`).

#### 3. Namespaces — «Изоляция ресурсов»

Это легковесная виртуализация на уровне ядра. Каждый namespace создает для процесса **свой вид системы**:

- **PID namespace** — процесс видит только свои дочерние процессы, его PID начинается с 1.
- **Network namespace** — свой сетевой стек (интерфейсы, маршруты, порты).
- **Mount, UTS (hostname), IPC, User** — остальные изоляции.

**Итог:** Контейнер (Docker) — это просто процесс, запущенный в наборе изолирующих namespace'ов.

#### 4. Cgroups — «Ограничение ресурсов»

Cgroups не про безопасность (взлом), а про **стабильность** — не дать процессу съесть всю память или CPU. Они контролируют:

- CPU (доля времени, привязка к ядрам),
- Memory (лимиты и учет),
- I/O (пропускная способность диска).

Каждый контейнер живет в своей cgroup, поэтому если один съедает 100% CPU, другие получают гарантированную долю согласно настройкам.

```bash
# Просмотр capabilities процесса
capsh --print
# Проверка контекста SELinux
ls -Z /path/to/file
```

## 7. Загрузка системы: от BIOS до user space

```mermaid
graph LR
    A[BIOS/UEFI] --> B[Bootloader GRUB2]
    B --> C[Ядро Linux + initramfs]
    C --> D[systemd/init]
    D --> E[Multi-user.target]
```

### Ключевые этапы:

#### Этап 1. BIOS/UEFI — «Включись и найди загрузчик»

После подачи питания процессор начинает выполнение кода из **постоянной памяти** (прошивки).

- **BIOS (Legacy)**: Ищет загрузочный сектор (MBR) на дисках, считывает 512 байт и передает управление загрузчику. Ограничен в размере и не понимает большие разделы (>2 ТБ).
- **UEFI** (современный стандарт): Работает как мини-ОС. Читает специальный раздел (ESP — EFI System Partition) с FAT-файловой системой, где лежит файл загрузчика (например, `grubx64.efi`). Поддерживает безопасную загрузку (Secure Boot) — проверяет подписи загрузчика и ядра.

**Для DevOps:** Если сервер не стартует, первое место проверки — порядок загрузки в UEFI/BIOS и целостность ESP (частый сценарий при восстановлении после сбоя диска).
1. **Ядро**: Инициализация оборудования, монтирование root ФС.
2. **Init (systemd)**: Запуск юнитов, достижение целевого состояния (`target`).

### Этап 2: Bootloader (GRUB2) — «Выбери ядро»

GRUB2 — это интерактивный менеджер загрузки. Он:

1. **Загружает модули**: драйверы для ФС (ext4, XFS, Btrfs) и дисков.
2. **Читает конфиг**: `/boot/grub2/grub.cfg`, где перечислены ядра и параметры.
3. **Загружает ядро** (`vmlinuz-...`) и **initramfs** (сжатый образ временной ФС) в память.
4. **Передает управление** ядру, передавая ему параметры (например, `console=tty0`, `crashkernel=auto`, `ro` для монтирования root в read-only).

**Важный нюанс:** Если вы забыли пароль root или изменили разметку диска, вы можете в GRUB редактировать параметры загрузки (добавить `single` или `systemd.unit=rescue.target`) и попасть в аварийный режим для восстановления.

### Этап 3: Ядро + initramfs — «Подготовка к жизни»

Ядро стартует с минимальным набором драйверов (вшитых в него). Сразу после инициализации процессора и базового оборудования оно **монтирует initramfs в память как root-ФС** (это не настоящий диск, а образ в ОЗУ).

**Зачем это нужно?** Если корневая ФС находится на:

- Сложном RAID (mdadm),
- LVM-томе,
- Зашифрованном диске (LUKS),
- Сетевой NFS (в случае бездисковых станций),

— то ядру _изначально_ не хватает драйверов или утилит, чтобы смонтировать `/`. Initramfs содержит эти модули и скрипты (`/init`), которые:

1. Загружают необходимые драйверы.
2. Собирают RAID/LVM.
3. Монтируют настоящую корневую ФС.
4. Переключают корень (`switch_root`) на реальный диск и запускают процесс `init` (systemd).

**Для понимания:** Без initramfs ядро сможет смонтировать только ФС, чей драйвер встроен в само ядро (не как модуль). Это ограничивает гибкость, поэтому современные системы всегда используют initramfs.

### Этап 4: Init (systemd) — «Король процессов»

Когда ядро переключает корень, оно запускает `systemd` (PID 1). Это первый пользовательский процесс, который заменил классический SysV init. Его работа — развернуть систему из пустого состояния в целевой уровень (`target`).

**Основные объекты systemd:**

- **Units**: сервисы (`.service`), сокеты, таймеры, mount-точки.
- **Targets**: группы юнитов, метки состояния. Например:
    - `multi-user.target` — многопользовательский режим без графики (уровень 3).
    - `graphical.target` — с графикой (уровень 5).
    - `rescue.target` / `emergency.target` — аварийные режимы для восстановления.

**Процесс запуска:** systemd анализирует зависимости, параллельно запуская сервисы (в отличие от последовательного SysV init). Он монтирует ФС из `/etc/fstab`, поднимает сеть, запускает логирование (`journald`), crond, SSH и ваши приложения.

### Где искать проблемы при загрузке

1. **GRUB:** Если система не видит диски — ошибка "no such device". Проверяйте `blkid` и правильность UUID в `/boot/grub2/grub.cfg`.
2. **Initramfs:** Если ядро паникует с "Kernel panic - not syncing: VFS: Unable to mount root fs" — значит, в initramfs нет драйвера для вашего диска или контроллера. Решение: пересобрать initramfs с нужными модулями (`dracut -f` в RedHat, `update-initramfs -u` в Debian).
3. **Systemd:** Если загрузка зависает на 1 мин 30 сек — это таймаут ожидания какого-то mount-юнита. Проверяйте `systemd-analyze blame` и `systemd-analyze critical-chain` для выявления медленного сервиса.

## 8. Межпроцессное взаимодействие (IPC)

### Pipes/FIFOs: «Конвейерная передача»

- **Pipes (анонимные):** Создаются оболочкой через оператор `|` (например, `grep error /var/log/syslog | wc -l`). Данные передаются однонаправленно от stdout одного процесса к stdin другого. Живут только во время выполнения связанных процессов.
- **FIFOs (именованные):** Это файлы в ФС (например, `/tmp/myfifo`), создаваемые `mkfifo`. Разные процессы могут открывать их для чтения/записи, общаясь через файловый интерфейс.

**DevOps-применение:** Часто используется для передачи логов между сервисами в небольших скриптах, но в современных архитектурах уступает место сокетам и очередям сообщений из-за ограниченной масштабируемости.

### Sockets: «Двусторонний диалог»

Сокеты бывают:

- **UNIX Domain Sockets (AF_UNIX):** Локальное IPC внутри одной ОС. Используют файловый путь (например, `/var/run/docker.sock`) и обеспечивают высокую производительность (без сетевых накладных расходов) с контролем доступа через права на файл.
- **Network Sockets (AF_INET):** TCP/UDP для связи между машинами (или внутри одной через localhost).

**Зачем:** Это основа микросервисов, брокеров сообщений (RabbitMQ, Kafka) и баз данных. В отличие от пайпов, сокеты поддерживают асинхронный обмен, несколько клиентов и сохраняют соединение.

**Диагностика:** `ss -lntp` покажет все TCP-сокеты в режиме прослушивания с привязкой к процессам. Если сервис не отвечает, проверяйте, не занят ли порт и не блокирует ли его SELinux/AppArmor.

### Shared Memory: «Общий стол без копирования»

Процессы (обычно родственные) отображают одну и ту же область физической памяти в свои виртуальные адресные пространства. Это самый быстрый IPC, так как **не требуется копирование данных** и системные вызовы нужны только для синхронизации (через семафоры или мьютексы).

**Use-case:** Высоконагруженные системы (базы данных, кэширующие движки типа Redis) используют shared memory для обмена данными между потоками/процессами-воркерами, минимизируя задержки.

**Риски:** Без синхронизации — состояние гонки (data race). И память нельзя контролировать на уровне отдельных приложений — если один процесс упадет, общая память может стать "мусорной" для других.

### Message Queues: «Почтовый ящик»

Системные очереди сообщений (System V или POSIX) хранят структурированные сообщения (с типом и приоритетом). Процесс-отправитель помещает сообщение в очередь, один или несколько получателей забирают его оттуда. Это асинхронное взаимодействие: отправитель не ждет ответа и может продолжать работу.

**Главное отличие от shared memory:** Данные **копируются** между процессами (из ядра в пользовательское пространство), поэтому скорость ниже. Но это дает строгую доставку и изоляцию — один процесс не может "испортить" очередь для другого.

**Use-case:** Используется во встраиваемых системах и некоторых системных компонентах (например, syslog). В современном DevOps вытеснены брокерами сообщений (RabbitMQ, Kafka) и сетевыми очередями.

### Signals: «Асинхронные прерывания»

Сигналы — это уведомления, посылаемые ядром или другим процессом конкретному процессу. Они **не передают данные** (кроме номера сигнала), только факт события.

- **SIGTERM (15):** "Вежливая" просьба завершиться — приложение может сохранить состояние.
- **SIGKILL (9):** "Жесткое" убийство — ядро принудительно завершает процесс без уведомления.
- **SIGHUP (1):** Часто используется для перечитывания конфигурации демонами (например, nginx -s reload использует его).

**DevOps-практика:**

- `kill -l` — список всех сигналов.
- Контейнерные оркестраторы (Kubernetes) отправляют контейнерам SIGTERM, ожидая завершения, и только через таймаут — SIGKILL. Это критично для graceful shutdown (например, завершить активные транзакции БД).

|Механизм|Быстродействие|Простота использования|Надежность|Основное применение|
|---|---|---|---|---|
|**Pipes**|Высокое|Высокая|Низкая (сброс соединения при завершении)|Командная строка, простые сценарии|
|**Sockets**|Высокое (UNIX), Среднее (TCP)|Средняя (API)|Высокая|Микросервисы, сетевые приложения|
|**Shared Mem**|Очень высокое|Низкая (синхронизация)|Низкая (утечки и гонки)|Кэши, БД, обработка данных в реальном времени|
|**Msg Queues**|Высокое|Средняя|Высокая|Структурированная асинхронная связь|
|**Signals**|Почти мгновенно|Высокая|Частичная (могут быть проигнорированы/заблокированы)|Управление процессами|

```bash
# Просмотр IPC-объектов
ipcs -a
# Отправка сигнала
kill -SIGTERM <PID>
```
