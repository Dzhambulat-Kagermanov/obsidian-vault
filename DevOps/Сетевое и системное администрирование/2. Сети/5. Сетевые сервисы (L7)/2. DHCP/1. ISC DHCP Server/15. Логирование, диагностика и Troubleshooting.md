## 1. Как устроена диагностика ISC DHCP

При неисправности последовательно проверяют **пять уровней**:

1. **Служба**: запущен ли `dhcpd`, нет ли ошибок загрузки конфигурации.
2. **Интерфейс и сеть**: слушает ли сервер нужный интерфейс, приходят ли запросы DHCP.
3. **Конфигурация**: определена ли подсеть, есть ли подходящий `pool`, не запрещён ли клиент.
4. **Аренды**: остались ли свободные адреса, нет ли конфликтов и несогласованности базы.
5. **Ответ клиенту**: отправлен ли `DHCPOFFER`/`DHCPACK` и доставлен ли он клиенту.

Не следует начинать с удаления базы аренд или перезапуска сервера: это может ухудшить ситуацию и уничтожить полезные диагностические сведения.

## 2. Где искать журналы

### 2.1. systemd-journald

```bash
sudo systemctl status isc-dhcp-server --no-pager
sudo journalctl -u isc-dhcp-server -n 100 --no-pager
sudo journalctl -u isc-dhcp-server -f
sudo journalctl -u isc-dhcp-server --since '1 hour ago' --no-pager
```

На других дистрибутивах служба может называться `dhcpd`:

```bash
systemctl list-unit-files | grep -E 'dhcp|isc-dhcp'
```

**Важно:** сообщения `dhcpd` могут поступать в системный журнал через syslog и не всегда полностью отображаться при фильтрации `-u`. Поэтому дополнительно смотрят системный журнал и фильтруют сообщения по идентификатору процесса.

```bash
sudo journalctl -t dhcpd -n 100 --no-pager
sudo journalctl --since '30 minutes ago' | grep -i dhcpd
```

### 2.2. rsyslog и файлы журналов

В зависимости от настроек Ubuntu сообщения могут находиться в `/var/log/syslog`, а на других системах — в `/var/log/messages`.

```bash
sudo grep -i dhcpd /var/log/syslog | tail -n 80
sudo tail -f /var/log/syslog | grep --line-buffered dhcpd
```

Если в системе не установлен или не настроен `rsyslog`, файла `/var/log/syslog` может не быть: используйте `journalctl`.

### 2.3. `log-facility`

Директива определяет syslog facility для сообщений ISC DHCP:

```dhcpd
log-facility local7;
```

**`local7` не означает автоматического создания отдельного файла.** Чтобы направить сообщения в отдельный файл, дополнительно настраивают syslog-демон. Например, в `/etc/rsyslog.d/30-dhcp.conf`:

```rsyslog
local7.*    /var/log/dhcpd.log
```

После создания правила:

```bash
sudo systemctl restart rsyslog
sudo tail -f /var/log/dhcpd.log
```

Если используется отдельный файл, предусмотрите ротацию через `logrotate` и ограничение доступа к журналам: в них могут присутствовать идентификаторы устройств.

### 2.4. `log()` внутри конфигурации

В `dhcpd.conf` можно писать диагностические сообщения:

```dhcpd
log(info, concat("DHCP request from ",
    binary-to-ascii(16, 8, ":", substring(hardware, 1, 6))));
```

`log()` выводит сообщение в syslog; уровни включают `debug`, `info`, `error`, `fatal`. Используйте логирование умеренно: чрезмерный объём сообщений мешает поиску ошибок и увеличивает нагрузку на журнал.

## 3. Как читать типичный обмен DHCP

Пример последовательности:

```text
DHCPDISCOVER from aa:bb:cc:dd:ee:ff via ens18
DHCPOFFER on 10.26.1.25 to aa:bb:cc:dd:ee:ff via ens18
DHCPREQUEST for 10.26.1.25 from aa:bb:cc:dd:ee:ff via ens18
DHCPACK on 10.26.1.25 to aa:bb:cc:dd:ee:ff via ens18
```

| Сообщение | Что означает | Что проверить при проблеме |
|---|---|---|
| `DHCPDISCOVER` | Сервер увидел поиск DHCP-сервера | Интерфейс, VLAN, Relay, доступность пула |
| `DHCPOFFER` | Сервер предложил адрес | Дошёл ли ответ до клиента |
| `DHCPREQUEST` | Клиент запросил адрес или продление | Какой сервер выбран, какой адрес запрошен |
| `DHCPACK` | Сервер подтвердил аренду | Получил ли клиент ответ, применил ли настройки |
| `DHCPNAK` | Сервер отклонил запрос адреса | Почему адрес не подходит текущей сети/состоянию |
| `DHCPRELEASE` | Клиент явно освободил адрес | Отправлял ли клиент RELEASE вообще |

**Примечание:** продление существующей аренды может происходить без полного DORA. Поэтому отсутствие `DISCOVER` при успешном `REQUEST`/`ACK` не обязательно является ошибкой.

## 4. Проверка конфигурации до перезапуска

Основной файл Ubuntu обычно `/etc/dhcp/dhcpd.conf`.

```bash
sudo dhcpd -t -cf /etc/dhcp/dhcpd.conf
```

Если используется отдельный файл базы аренд:

```bash
sudo dhcpd -t -cf /etc/dhcp/dhcpd.conf -lf /var/lib/dhcp/dhcpd.leases
```

Проверка `-t` проверяет синтаксис и ряд ошибок конфигурации, **но не гарантирует**, что запросы реально проходят через сеть, что Relay настроен правильно или что политика доступа выдаст нужный адрес.

Проверьте параметры запуска службы:

```bash
systemctl cat isc-dhcp-server
cat /etc/default/isc-dhcp-server
ip -br address
```

Для Ubuntu важно проверить `INTERFACESv4`: сервер должен обслуживать именно те интерфейсы, через которые ожидаются запросы. При использовании Relay DHCP-серверу не обязательно иметь интерфейс в каждой клиентской VLAN, но его конфигурация должна содержать обслуживаемые подсети.

Перезапуск после проверки:

```bash
sudo systemctl restart isc-dhcp-server
sudo systemctl status isc-dhcp-server --no-pager
```

## 5. База аренд `dhcpd.leases`

**Lease database** — файл состояния динамических аренд ISC DHCP. В Ubuntu типичный путь:

```text
/var/lib/dhcp/dhcpd.leases
```

Проверить реальный путь можно по параметрам запуска службы и её конфигурации.

### 5.1. Пример записи

```dhcpd
lease 10.26.1.25 {
  starts 6 2026/11/14 10:00:00;
  ends 6 2026/11/14 12:00:00;
  cltt 6 2026/11/14 10:00:00;
  binding state active;
  next binding state free;
  hardware ethernet aa:bb:cc:dd:ee:ff;
  client-hostname "pc-01";
}
```

| Поле | Назначение |
|---|---|
| `lease` | Выданный IPv4-адрес |
| `starts` / `ends` | Начало и окончание срока аренды |
| `cltt` | Время последней транзакции клиента |
| `binding state` | Текущее состояние аренды |
| `next binding state` | Планируемое следующее состояние |
| `hardware ethernet` | MAC-адрес, связанный с арендой |
| `client-hostname` | Имя, переданное клиентом, если оно присутствовало |

Время в базе ISC DHCP обычно записывается в UTC; учитывайте часовой пояс при сопоставлении с системными журналами.

### 5.2. Почему в файле могут быть повторяющиеся адреса

`dhcpd.leases` — не простая таблица с одной строкой на IP. Сервер дописывает изменения состояния, поэтому **один адрес может встречаться несколько раз**. При интерпретации состояния учитывают более позднюю запись и внутренние правила обработки базы, а не просто количество совпадений `grep`.

```bash
sudo grep -n '^lease 10\.26\.1\.25 ' /var/lib/dhcp/dhcpd.leases
sudo tail -n 80 /var/lib/dhcp/dhcpd.leases
```

Файл может периодически переписываться сервером, а предыдущая версия сохраняться как `dhcpd.leases~`.

**Не редактируйте и не удаляйте активную базу аренд.** Это может привести к повторной выдаче уже используемых адресов и нарушению работы Failover. Для анализа создайте копию:

```bash
sudo cp -a /var/lib/dhcp/dhcpd.leases /root/dhcpd.leases.snapshot
```

При работе с Failover состояние аренды зависит также от синхронизации с партнёром; нельзя рассматривать только локальный файл как единственный источник истины.

## 6. Анализ DHCP-пакетов через tcpdump

DHCPv4 обычно использует UDP-порты **67 (сервер)** и **68 (клиент)**.

```bash
sudo tcpdump -ni ens18 -vvv 'udp port 67 or udp port 68'
```

Захват на всех интерфейсах для первичной диагностики:

```bash
sudo tcpdump -ni any -vvv 'udp port 67 or udp port 68'
```

Запись в файл для анализа в Wireshark:

```bash
sudo tcpdump -ni ens18 -s 0 -w /tmp/dhcp-debug.pcap \
  'udp port 67 or udp port 68'
```

Остановите захват через `Ctrl+C`. PCAP-файл может содержать MAC-адреса, имена устройств и сетевые параметры — не публикуйте его без необходимости.

### 6.1. На какие поля смотреть

- **Message Type (Option 53)** — Discover, Offer, Request, ACK, NAK.
- **Transaction ID (`xid`)** — связывает сообщения одной транзакции.
- **Client MAC (`chaddr`)** — аппаратный адрес клиента.
- **Requested IP (Option 50)** — адрес, запрошенный клиентом.
- **Server Identifier (Option 54)** — сервер, к которому относится запрос/предложение.
- **Relay Agent IP (`giaddr`)** — адрес, используемый сервером для определения сети при Relay.
- **Option 82** — сведения от Relay, если он их добавляет.
- **Parameter Request List (Option 55)** — какие параметры запросил клиент.

### 6.2. Как локализовать потерю пакета

| На сервере видно | Возможная область проблемы |
|---|---|
| Нет `DISCOVER` | VLAN, коммутатор, DHCP Relay, ACL/firewall, клиент |
| Есть `DISCOVER`, нет `OFFER` | Конфигурация сервера, ограничения пула, отсутствие свободных адресов, ошибки службы |
| Есть `OFFER`, нет `REQUEST` | Ответ не дошёл, клиент выбрал другой сервер, проблема в сети |
| Есть `REQUEST`, нет `ACK` | Ошибка политики/состояния аренды, сервер не обработал запрос |
| Есть `ACK`, клиент без адреса | Потеря ответа, ошибка DHCP-клиента, конфликт адреса или применение конфигурации |

Это **диагностические гипотезы**, а не однозначные причины. При необходимости сравнивайте захват на клиенте, Relay и сервере.

## 7. Проверка DHCP Relay и нескольких VLAN

Для удалённых подсетей убедитесь, что:

1. DHCP Relay настроен на интерфейсе **клиентской VLAN**.
2. Relay пересылает запросы на правильный IP DHCP-сервера.
3. Между Relay и сервером разрешён нужный UDP-трафик.
4. В `dhcpd.conf` есть корректное объявление `subnet` клиентской сети.
5. Сервер возвращает ответ Relay, а Relay — клиенту.

Пример:

```dhcpd
subnet 10.26.10.0 netmask 255.255.255.0 {
    option routers 10.26.10.1;
    option domain-name-servers 10.26.250.7, 10.26.250.8;
    range 10.26.10.100 10.26.10.200;
}
```

Если Relay сообщает `giaddr = 10.26.10.1`, сервер должен корректно сопоставить его с обслуживаемой сетью. Не путайте `shared-network` с несколькими VLAN: это разные топологии.

Для расследования сохраните одновременно:

```bash
ip -br addr
ip route
sudo tcpdump -ni any -vvv 'udp port 67 or udp port 68'
```

## 8. Типичные ошибки и способы проверки

### 8.1. `No subnet declaration for ...`

Сервер видит интерфейс, но не находит соответствующего объявления `subnet`.

**Проверка:** сравните IP/маску интерфейса с блоками `subnet` и проверьте список интерфейсов, передаваемый `dhcpd`.

### 8.2. `Not configured to listen on any interfaces!`

Нет пригодных интерфейсов для прослушивания или они не указаны/не соответствуют конфигурации.

**Проверка:** `ip -br addr`, `/etc/default/isc-dhcp-server`, объявления подсетей, журналы запуска.

### 8.3. `No free leases`

Сервер не может подобрать свободный адрес в подходящем пуле. Причины: диапазон исчерпан, аренды заняты, клиент не допущен к пулу или состояние аренд ограничивает выдачу.

**Проверка:** границы `range`, `allow`/`deny`, `class`/`subclass`, записи `dhcpd.leases`, состояние Failover.

### 8.4. `unknown network segment`

Обычно проблема связана с определением сети, из которой пришёл запрос, в том числе с Relay/`giaddr` и объявлениями `subnet`.

**Проверка:** захват DHCP-пакетов, значение `giaddr`, конфигурация маршрутизатора, блоки `subnet`.

### 8.5. `bad range` или ошибка синтаксиса

Причины: неверная маска, диапазон за пределами подсети, опечатка, отсутствие `;`, неправильная вложенность `{}`.

```bash
sudo dhcpd -t -cf /etc/dhcp/dhcpd.conf
```

### 8.6. Клиент получает адрес, но нет интернета

Успешный `DHCPACK` означает выдачу аренды, но **не гарантирует работоспособность маршрутизации или DNS**.

На клиенте проверьте адрес, маршрут и DNS:

```bash
ip -br addr
ip route
resolvectl status
ping -c 3 1.1.1.1
getent hosts example.com
```

Если IP-связность есть, а имена не разрешаются, ищите проблему в DNS, а не в механизме аренды.

### 8.7. Два DHCP-сервера отвечают одновременно

Проверьте `Server Identifier` (Option 54) в ответах и адреса отправителей. Возможно, в сети работает **Rogue DHCP** либо второй легитимный сервер с пересекающимся пулом. Для ISC DHCP Failover нужен согласованный протокол, а не два независимых сервера с одинаковым `range`.

### 8.8. Клиент получает адрес не из ожидаемого пула

Проверьте:

- фактическую подсеть, определённую по интерфейсу/`giaddr`;
- принадлежность клиента к `class`/`subclass`;
- `allow members of` / `deny members of`;
- наличие прежней действующей аренды;
- пересечение диапазонов и объявления `shared-network`.

## 9. Диагностика проблем с DDNS и PXE

### 9.1. DHCP работает, но DNS-запись не появляется

Разделяйте две операции: **выдачу IP-адреса** и **обновление DNS**.

```bash
sudo journalctl -t dhcpd -n 100 --no-pager
dig @10.26.250.7 pc-01.ggkit.local A
dig @10.26.250.7 -x 10.26.1.25
```

Проверьте `ddns-update-style`, `ddns-updates`, настройки зоны и авторизацию обновлений. Если DDNS реализован через внешний обработчик, дополнительно проверяйте его журналы, права и Kerberos/GSS-TSIG. При `ddns-update-style none;` встроенный механизм DDNS отключён.

### 9.2. DHCP работает, но PXE-загрузка не начинается

Проверьте наличие в ответе загрузочных параметров, архитектуру BIOS/UEFI и доступность сервера загрузки:

```bash
sudo tcpdump -ni ens18 -vvv 'udp port 67 or udp port 68'
```

Для TFTP также проверяют UDP/69 и последующие порты передачи данных; для HTTP-загрузки — адрес и доступность веб-сервера. Не все PXE-клиенты одинаково используют Options 66/67 и поля `siaddr`/`file`.

## 10. Безопасная последовательность устранения неисправности

Ниже — порядок действий для реального сервера без необоснованного вмешательства в активные аренды.

```bash
# 1. Состояние службы
sudo systemctl status isc-dhcp-server --no-pager

# 2. Недавние сообщения
sudo journalctl -t dhcpd -n 100 --no-pager

# 3. Сетевые интерфейсы
ip -br addr

# 4. Проверка конфигурации
sudo dhcpd -t -cf /etc/dhcp/dhcpd.conf

# 5. Захват DHCP-пакетов на нужном интерфейсе
sudo tcpdump -ni ens18 -vvv 'udp port 67 or udp port 68'

# 6. Анализ базы аренд (только чтение)
sudo tail -n 100 /var/lib/dhcp/dhcpd.leases
```

**Алгоритм принятия решения:**

1. Служба не запущена → сначала исправьте ошибку запуска.
2. Служба работает, но запросов нет → исследуйте сеть, VLAN и Relay.
3. Запросы есть, ответов нет → исследуйте пул, классы, аренды и сообщения `dhcpd`.
4. Ответы есть, клиент их не получает → сравните захваты по пути доставки.
5. Клиент получил адрес, но сервисы не работают → проверяйте маршрутизацию, DNS, PXE или DDNS отдельно.

**Изменения на production-сервере:** перед правкой сохраните резервную копию конфигурации, выполните `dhcpd -t`, оцените влияние на действующие аренды и только затем применяйте изменения в согласованное окно обслуживания.

## 11. Мониторинг и профилактика

Для предотвращения повторных инцидентов полезно контролировать:

- состояние службы `isc-dhcp-server`;
- ошибки запуска и сообщения об исчерпании адресов;
- заполнение динамических пулов;
- состояние DHCP Failover, если используется;
- доступность DHCP Relay и ключевых VLAN;
- свободное место на файловой системе с журналами и базой аренд;
- время на серверах (NTP), особенно при анализе событий и взаимодействии с Kerberos.

**Осторожно с метрикой «число строк `lease`»:** из-за истории изменений она не равна количеству активных аренд. Для корректного подсчёта нужен разбор актуального состояния каждой аренды, а при Failover — учёт состояния партнёров.

|---|---|
| **Troubleshooting** | Последовательная диагностика и устранение неисправностей |

| **Facility** | Категория сообщений syslog, используемая для их распределения |

| **Option 82** | Дополнительные сведения о точке подключения клиента, передаваемые Relay |
