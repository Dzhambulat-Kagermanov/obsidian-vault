## 1. Целевая архитектура

Рассмотрим организацию с центральным DHCP-сервером и тремя VLAN. DHCP-сервер находится в инфраструктурной сети; DHCP-запросы из пользовательских VLAN передаются маршрутизатором через DHCP Relay.

| Назначение | Сеть / адрес | Примечание |
|---|---|---|
| DHCP-сервер | `10.28.250.6/24` | Ubuntu, интерфейс `ens18` |
| Шлюз инфраструктуры | `10.28.250.1` | L3-маршрутизатор |
| DNS-серверы | `10.28.250.7`, `10.28.250.8` | DNS для `ggkit.local` |
| VLAN 110 — аудитории | `10.28.10.0/24` | Шлюз `10.28.10.1` |
| VLAN 120 — сотрудники | `10.28.20.0/24` | Шлюз `10.28.20.1` |
| VLAN 130 — оборудование | `10.28.30.0/24` | Шлюз `10.28.30.1` |
| PXE/TFTP-сервер | `10.28.250.22` | Файлы загрузки должны реально существовать |

**Схема передачи:** клиент VLAN → DHCPDISCOVER → L3-шлюз с DHCP Relay → `10.28.250.6` → DHCPOFFER → Relay → клиент. Адрес сети определяется по `giaddr`, который указывает Relay, а не по тому, в какой подсети физически расположен DHCP-сервер.

**Предпосылки:** маршрутизатор уже маршрутизирует сети, Relay настроен для всех трёх VLAN, межсетевой экран разрешает необходимый DHCP-обмен, DNS работает. DHCP **не создаёт VLAN, не настраивает маршрутизацию и не обеспечивает доступ к интернету сам по себе**.

## 2. Состав файлов и область ответственности

```text
/etc/dhcp/
├── dhcpd.conf                # Основная конфигурация
└── dhcpd.conf.d/
    ├── 10-reservations.conf  # Статические резервации
    └── 20-classes.conf       # Классы клиентов (при необходимости)

/var/lib/dhcp/dhcpd.leases    # Рабочая база аренд: управляется dhcpd
/etc/default/isc-dhcp-server # Интерфейс, на котором запускается IPv4-служба
```

Файлы `dhcpd.conf.d` **не загружаются автоматически**. Их нужно явно подключать через `include`. База `dhcpd.leases` — не конфигурационный файл; не редактируйте её во время работы службы.

В примере ниже классы и резервации включены непосредственно в основной файл для удобства изучения. В разделе 7 показано, как вынести их в отдельные файлы без изменения логики.

## 3. Подготовка сервера Ubuntu

### 3.1. Сетевые настройки

Пример `/etc/netplan/01-dhcp-server.yaml` для интерфейса `ens18`:

```yaml
network:
  version: 2
  renderer: networkd
  ethernets:
    ens18:
      dhcp4: false
      addresses:
        - 10.28.250.6/24
      routes:
        - to: default
          via: 10.28.250.1
      nameservers:
        addresses:
          - 10.28.250.7
          - 10.28.250.8
        search:
          - ggkit.local
```

```bash
sudo netplan generate
sudo netplan try
ip -br address show ens18
ip route
```

`netplan try` требует подтверждения и помогает избежать потери удалённого доступа. Если сеть управляется другим Netplan-файлом, сначала согласуйте изменения с существующей конфигурацией.

### 3.2. Установка и выбор интерфейса

```bash
sudo apt update
sudo apt install isc-dhcp-server
```

В `/etc/default/isc-dhcp-server`:

```ini
INTERFACESv4="ens18"
INTERFACESv6=""
```

Имя интерфейса проверяют через `ip -br link`. Сервер может слушать только `ens18`, хотя обслуживает другие сети через Relay: ему не нужны отдельные интерфейсы во всех VLAN.

## 4. Полный пример `/etc/dhcp/dhcpd.conf`

Ниже — **рабочая логическая конфигурация для описанной топологии**. Она включает выдачу адресов, резервации, стандартные DHCP Options, PXE для BIOS/UEFI, отдельный пул для зарегистрированных устройств в VLAN оборудования и журналирование. DDNS и Failover сознательно не включены в этот основной файл: они требуют дополнительных компонентов и отдельной проверки, описанной далее.

```dhcpd
# ============================================================
# 1. Глобальные параметры
# ============================================================

authoritative;
log-facility local7;

ddns-update-style none;

default-lease-time 7200;
max-lease-time 14400;

option domain-name "ggkit.local";
option domain-name-servers 10.28.250.7, 10.28.250.8;

# DHCP Option 93: архитектура PXE-клиента.
option architecture-type code 93 = unsigned integer 16;

# ============================================================
# 2. Классификация оборудования по MAC
# ============================================================

class "registered-equipment" {
    match hardware;
}

subclass "registered-equipment" 1:aa:bb:cc:00:00:01;
subclass "registered-equipment" 1:aa:bb:cc:00:00:02;

# ============================================================
# 3. Резервации
# ============================================================

host teacher-pc-01 {
    hardware ethernet 52:54:00:10:00:01;
    fixed-address 10.28.20.10;
}

host printer-01 {
    hardware ethernet 52:54:00:30:00:01;
    fixed-address 10.28.30.10;
}

# ============================================================
# 4. Инфраструктурная сеть DHCP-сервера
# ============================================================

subnet 10.28.250.0 netmask 255.255.255.0 {
    option routers 10.28.250.1;
    # Динамический пул здесь не предусмотрен.
}

# ============================================================
# 5. VLAN 110 — аудитории
# ============================================================

subnet 10.28.10.0 netmask 255.255.255.0 {
    option routers 10.28.10.1;
    option subnet-mask 255.255.255.0;
    option broadcast-address 10.28.10.255;

    # Передача параметров PXE только PXE-клиентам.
    if substring(option vendor-class-identifier, 0, 9) = "PXEClient" {
        next-server 10.28.250.22;

        if option architecture-type = 7 or option architecture-type = 9 {
            filename "uefi/grubx64.efi";
        } else {
            filename "pxelinux.0";
        }
    }

    pool {
        range 10.28.10.100 10.28.10.220;
    }
}

# ============================================================
# 6. VLAN 120 — сотрудники
# ============================================================

subnet 10.28.20.0 netmask 255.255.255.0 {
    option routers 10.28.20.1;
    option subnet-mask 255.255.255.0;

    pool {
        range 10.28.20.100 10.28.20.220;
    }
}

# ============================================================
# 7. VLAN 130 — оборудование
# ============================================================

subnet 10.28.30.0 netmask 255.255.255.0 {
    option routers 10.28.30.1;
    option subnet-mask 255.255.255.0;

    pool {
        allow members of "registered-equipment";
        range 10.28.30.100 10.28.30.150;
    }
}
```

**Проверка важного нюанса:** `allow members of "registered-equipment"` относится к **динамическому пулу**. Резервация `printer-01` с `fixed-address` обрабатывается отдельно. Такой пул не является полноценной защитой от несанкционированного подключения: MAC можно подменить.

**PXE-оговорка:** архитектурные значения `7` и `9` в примере отнесены к UEFI x86-64; на реальном оборудовании следует сверить Option 93 и формат EFI-загрузчика. `grubx64.efi` и `pxelinux.0` — пути на TFTP-сервере, а не на DHCP-сервере. Для Secure Boot может потребоваться другой подписанный загрузчик. Некоторые PXE-клиенты используют иные варианты сетевой загрузки; эта конфигурация не охватывает их автоматически.

## 5. Как сервер выбирает параметры

1. DHCP-пакет приходит напрямую либо через Relay.
2. `dhcpd` определяет сеть клиента по интерфейсу или `giaddr`.
3. Проверяются объявления `host` и применимые классы; вычисляются условия и ключи сопоставления.
4. Сервер определяет доступный пул либо подходящую резервацию и учитывает состояние аренды.
5. Формируется ответ с параметрами из применимых областей действия.

**Наследование:** глобальные параметры доступны нижележащим областям, если не переопределены более конкретным применимым значением. `option routers` задаётся отдельно для каждой VLAN, потому что шлюз у них разный. В одном конфигурационном файле может существовать несколько `subnet`, даже если сервер слушает только один интерфейс.

**Резервация** — не то же самое, что диапазон `range`. Адреса `10.28.20.10` и `10.28.30.10` находятся за пределами динамических пулов, чтобы не создавать пересечений.

## 6. Настройка DHCP Relay на маршрутизаторе

На каждом L3-интерфейсе пользовательской VLAN требуется направить DHCP-запросы к `10.28.250.6`. Синтаксис зависит от маршрутизатора; типичная команда в Cisco-подобном CLI:

```text
interface Vlan110
 ip address 10.28.10.1 255.255.255.0
 ip helper-address 10.28.250.6

interface Vlan120
 ip address 10.28.20.1 255.255.255.0
 ip helper-address 10.28.250.6

interface Vlan130
 ip address 10.28.30.1 255.255.255.0
 ip helper-address 10.28.250.6
```

Это **пример синтаксиса**, не готовая универсальная конфигурация коммутатора. На конкретной платформе проверьте, какие дополнительные UDP-протоколы пересылает `ip helper-address`, и ограничьте пересылку ненужных сервисов.

При нескольких Relay-агентах и сложной маршрутизации убедитесь, что обратный путь от DHCP-сервера к Relay существует. Option 82 может использоваться для идентификации точки подключения, но требует согласованной настройки Relay и политики доверия.

## 7. Разделение конфигурации через `include`

В большой инфраструктуре удобнее хранить резервации и классы отдельно:

```dhcpd
# /etc/dhcp/dhcpd.conf — в глобальной области
include "/etc/dhcp/dhcpd.conf.d/20-classes.conf";
include "/etc/dhcp/dhcpd.conf.d/10-reservations.conf";
```

Содержимое `/etc/dhcp/dhcpd.conf.d/20-classes.conf`:

```dhcpd
class "registered-equipment" {
    match hardware;
}

subclass "registered-equipment" 1:aa:bb:cc:00:00:01;
subclass "registered-equipment" 1:aa:bb:cc:00:00:02;
```

Содержимое `/etc/dhcp/dhcpd.conf.d/10-reservations.conf`:

```dhcpd
host teacher-pc-01 {
    hardware ethernet 52:54:00:10:00:01;
    fixed-address 10.28.20.10;
}

host printer-01 {
    hardware ethernet 52:54:00:30:00:01;
    fixed-address 10.28.30.10;
}
```

**Не дублируйте объявления:** после переноса удалите соответствующие блоки из основного файла. `include` вставляет содержимое файла в место директивы; следовательно, область действия зависит от того, где находится `include`.

Полезная организация изменений: вести конфигурацию в Git, фиксировать автора, дату, причину изменения и сохранять проверенную версию перед развертыванием. Секреты и ключи TSIG не следует помещать в открытый репозиторий.

## 8. DDNS: что включено и что намеренно отключено

В основном примере:

```dhcpd
ddns-update-style none;
```

Это означает, что **встроенные динамические DNS-обновления ISC DHCP отключены**. Обычная выдача адресов продолжает работать, но DHCP-сервер не создаёт A/PTR-записи автоматически.

Для встроенного DDNS с BIND требуется отдельно согласовать режим обновлений, ключи TSIG, права обновления зон и обратную зону. Для Samba AD с Kerberos/GSS-TSIG часто используют отдельную интеграцию с `nsupdate -g` и корректно настроенным keytab; простое добавление `zone { primary ...; }` не обеспечивает Kerberos-аутентификацию.

**Не смешивайте два механизма без необходимости:** встроенный DDNS и внешние скрипты обновления могут конкурировать за одни и те же записи. Не включайте неподтверждённый вызов `execute()` в production-конфигурацию: доступность и поведение этой функции зависят от сборки ISC DHCP, а синтаксис и права исполнения необходимо проверять на конкретном сервере. Подробнее — в тематических заметках про DDNS и обработчики событий.

## 9. Отказоустойчивость: границы основного сценария

Пример содержит **один DHCP-сервер**. Это не отказоустойчивая архитектура.

Для пары ISC DHCP Failover потребуется:

- отдельный второй сервер с собственным адресом;
- согласованная конфигурация `failover peer` на обоих узлах;
- указание партнёра в соответствующих `pool`;
- настройка Relay для доставки запросов обоим DHCP-серверам;
- синхронизация времени, резервирование конфигурации и проверка переходов состояний;
- регламент действий при `communications-interrupted` и `partner-down`.

Нельзя создавать второй независимый DHCP-сервер с тем же динамическим пулом: это может привести к конфликтам адресов. Полная пара конфигураций Failover рассматривается в отдельной заметке №12; здесь она не добавляется, чтобы основной пример оставался последовательным.

## 10. Безопасность production DHCP

### 10.1. На сервере

- Выделите серверу статический адрес; не размещайте его в динамическом пуле.
- Ограничьте административный доступ по SSH и используйте персональные учётные записи.
- Разрешите DHCP-трафик только от доверенных VLAN/Relay и требуемых интерфейсов; не открывайте UDP 67 в интернет.
- Ограничьте доступ к `/etc/dhcp`, файлам секретов и резервным копиям.
- Контролируйте обновления системы и жизненный цикл ISC DHCP.
- Следите за заполнением диска, свободными адресами и доступностью DNS/Relay.

### 10.2. На коммутаторах

- DHCP Snooping: доверенными должны быть только соответствующие uplink/Relay-порты.
- При необходимости — Port Security, 802.1X, сегментация VLAN и контроль DHCP Option 82.
- Не считайте `class` и `subclass` механизмом криптографической аутентификации.

### 10.3. Почему `authoritative;` требует внимания

`authoritative;` означает, что сервер считается авторитетным для обслуживаемых сетей и может отвечать DHCPNAK на некорректные запросы. Включайте его только при уверенности, что сервер действительно отвечает за указанные сегменты. При миграции и сосуществовании нескольких DHCP-серверов эта настройка требует особой осторожности.

## 11. Проверка конфигурации и запуск

### 11.1. Резервная копия

```bash
sudo cp -a /etc/dhcp/dhcpd.conf \
  "/etc/dhcp/dhcpd.conf.bak.$(date +%F-%H%M%S)"
```

### 11.2. Проверка синтаксиса

```bash
sudo dhcpd -4 -t -cf /etc/dhcp/dhcpd.conf
```

Если `dhcpd` возвращает ошибку, исправьте её **до перезапуска службы**. Успешная синтаксическая проверка не доказывает, что Relay, DNS, TFTP и маршрутизация работают корректно.

### 11.3. Запуск

```bash
sudo systemctl enable --now isc-dhcp-server
sudo systemctl restart isc-dhcp-server
sudo systemctl status isc-dhcp-server --no-pager
```

На уже работающем production-сервере сначала согласуйте окно изменений: перезапуск может временно прервать обработку DHCP-запросов.

### 11.4. Проверка журналов

```bash
sudo journalctl -u isc-dhcp-server -n 100 --no-pager
sudo journalctl -t dhcpd -n 100 --no-pager
sudo ss -lunp | grep ':67'
```

Если служба не запускается, проверьте имя интерфейса, синтаксис конфигурации, наличие подходящей `subnet` для локального интерфейса и конкурирующий процесс, занимающий UDP 67.

## 12. Приёмочные проверки после внедрения

| Проверка | Ожидаемый результат | Инструмент |
|---|---|---|
| Синтаксис конфигурации | Нет ошибок | `dhcpd -4 -t` |
| Служба DHCP | `active (running)` | `systemctl status` |
| VLAN 110 | Адрес из `10.28.10.100–220` | Клиент, `journalctl` |
| VLAN 120 | Адрес из `10.28.20.100–220` | Клиент, `journalctl` |
| VLAN 130, известный MAC | Адрес из разрешённого пула | Клиент, `journalctl` |
| VLAN 130, неизвестный MAC | Нет адреса из ограниченного динамического пула | Клиент, `journalctl` |
| Резервация сотрудника | `10.28.20.10` | Клиент, `dhcpd.leases`/журнал |
| DNS-параметры | DNS `10.28.250.7/.8` | Параметры клиента |
| Шлюз VLAN | Соответствующий `.1` | Таблица маршрутизации клиента |
| PXE BIOS/UEFI | Правильный загрузочный файл | DHCP-пакет и TFTP |
| Relay | `giaddr` соответствует клиентской VLAN | `tcpdump` |

Пример захвата DHCP-трафика на сервере:

```bash
sudo tcpdump -ni ens18 -vvv 'udp port 67 or udp port 68'
```

В выводе проверяют `giaddr`, `yiaddr`, DHCP Message Type, Server Identifier, Option 93, Option 66/67 (если применяются) и адреса отправителя/получателя. При проблемах PXE отдельно проверяют доступность TFTP/HTTP-сервера и корректность файла загрузки.

## 13. Эксплуатация, изменения и резервное копирование

### 13.1. Что сохранять

- `/etc/dhcp/dhcpd.conf` и подключаемые конфигурационные файлы;
- `/etc/default/isc-dhcp-server`;
- сетевые настройки сервера (Netplan);
- актуальную копию базы аренд `/var/lib/dhcp/dhcpd.leases`;
- ключи/скрипты DDNS — **отдельно и с ограниченным доступом**, если они используются;
- документацию по VLAN, Relay, диапазонам, резервациям и PXE.

Для согласованной копии базы аренд используйте согласованный процесс резервирования: учтите возможную запись в `dhcpd.leases` во время копирования. Восстановление аренд требует особой осторожности, особенно в Failover-паре.

### 13.2. Безопасное изменение пула

1. Убедиться, что новый диапазон не пересекается со статическими адресами и чужими DHCP-пулами.
2. Проверить маршрутизацию и адрес шлюза.
3. Изменить `range` в нужной `subnet`/`pool`.
4. Выполнить `dhcpd -4 -t`.
5. Применить изменения в согласованное окно.
6. Проверить журналы и тестового клиента.

Сокращение пула не означает мгновенного отзыва уже выданных аренд. Для масштабной перенумерации сети требуется отдельный план миграции.

### 13.3. Мониторинг

Контролируйте доступность службы, ошибки парсинга, количество свободных адресов в пулах, частоту DHCPDISCOVER без DHCPOFFER, загрузку диска, события Relay, а при использовании Failover — состояния партнёров. Для важных сегментов полезен тестовый DHCP-клиент, проверяющий фактическую выдачу адреса, а не только наличие процесса `dhcpd`.

## 14. Частые ошибки в целостной конфигурации

| Ошибка | Причина / следствие | Как исправить |
|---|---|---|
| Не объявлена локальная подсеть сервера | `dhcpd` не может корректно привязаться к интерфейсу | Добавить `subnet` инфраструктурного интерфейса |
| В `range` попали шлюзы и статические IP | Возможны конфликты адресов | Исключить статические адреса из пулов |
| Одинаковый `option routers` для всех VLAN | Клиенты получают неверный шлюз | Указать шлюз в каждой `subnet` |
| Нет Relay на VLAN | Запрос не доходит до сервера | Настроить DHCP Relay на L3-шлюзе |
| Неверный `giaddr` | Сервер выбирает не ту сеть | Проверить интерфейс Relay и маршрутизацию |
| `subclass` без подходящего `match` | Клиент не попадает в ожидаемый класс | Сопоставить байтовый ключ с `match` |
| `filename` для UEFI указывает на BIOS-загрузчик | PXE не стартует | Разделить загрузчики по Option 93 |
| `ddns-update-style none` при ожидании DDNS | DNS-записи не обновляются | Настроить отдельный поддерживаемый механизм DDNS |
| Два независимых сервера с одним пулом | Возможны дублирующиеся аренды | Настроить Failover или непересекающиеся пулы |
| `include` в неправильной области | Неожиданное наследование параметров | Перенести `include` в нужный блок |
| Ограничение по MAC принято за защиту | Возможна подмена MAC | Применить DHCP Snooping/802.1X и сегментацию |

## 15. Глоссарий

| Термин | Определение |
|---|---|
| **ISC DHCP Server** | DHCP-сервер проекта ISC, исполняемый процесс `dhcpd` |
| **`dhcpd.conf`** | Основной файл конфигурации ISC DHCP |
| **DHCP Relay** | Устройство/служба, передающая DHCP-сообщения между L3-сетями |
| **`giaddr`** | Поле DHCP-пакета с адресом Relay, используемое для определения клиентской сети |
| **`subnet`** | Объявление обслуживаемой IPv4-подсети |
| **`pool`** | Область с динамическими диапазонами и политиками выдачи |
| **`range`** | Диапазон адресов, доступных для динамической аренды |
| **`host`** | Объявление конкретного клиента, часто для резервации |
| **`fixed-address`** | Фиксированный IPv4-адрес, назначаемый соответствующему клиенту |
| **DHCP Option** | Параметр, передаваемый в DHCP-сообщении (DNS, шлюз, PXE и др.) |
| **`class`** | Категория клиентов с правилами классификации |
| **`subclass`** | Зарегистрированное значение ключа `match`, позволяющее отнести клиента к классу |
| **PXE** | Механизм сетевой загрузки компьютера |
| **TFTP** | Простой протокол передачи файлов, часто используемый в PXE |
| **DDNS** | Динамическое обновление DNS-записей |
| **TSIG** | Подпись DNS-обновлений с общим секретным ключом |
| **GSS-TSIG** | Аутентификация DNS-обновлений с использованием GSS-API/Kerberos |
| **Failover** | Согласованная работа пары DHCP-серверов с обменом состояниями аренд |
| **Lease** | Аренда IPv4-адреса на ограниченное время |
| **`authoritative`** | Объявление сервера авторитетным для обслуживаемых сетей |
| **DHCP Snooping** | Функция коммутатора для контроля DHCP-трафика и доверенных портов |
