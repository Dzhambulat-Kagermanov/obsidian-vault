## 1. Зачем DHCP Relay нужен в маршрутизируемой сети

**DHCP Relay Agent** — промежуточный узел (обычно маршрутизатор или L3-коммутатор), который принимает широковещательные DHCP-запросы клиентов в одной подсети и пересылает их DHCP-серверу в другой.

Обычный DHCPDISCOVER отправляется широковещательно и не проходит через маршрутизатор как обычный IP-пакет. Поэтому в сети с несколькими VLAN DHCP-сервер необязательно устанавливать в каждой VLAN: на L3-шлюзах можно настроить ретрансляцию на один центральный сервер.

Пример:

```text
VLAN 10: 192.168.10.0/24 ──┐
                            ├── L3-маршрутизатор ── 192.168.100.10 (ISC DHCP)
VLAN 20: 192.168.20.0/24 ──┘
        DHCP Relay на интерфейсах VLAN
```

Маршрутизатор должен иметь интерфейс в клиентской VLAN и маршрут к DHCP-серверу. DHCP-серверу также требуется обратная маршрутизация к relay-агенту.

## 2. Как работает пересылка DHCP-пакетов

Типичная последовательность для клиента в VLAN 10:

1. Клиент рассылает `DHCPDISCOVER` в своей VLAN.
2. Relay принимает запрос, устанавливает поле `giaddr` (адрес интерфейса relay в клиентской сети) и отправляет пакет серверу.
3. Сервер по `giaddr` определяет сеть, из которой пришел клиент, и подбирает подходящую конфигурацию адресации.
4. Сервер направляет `DHCPOFFER` relay-агенту.
5. Relay доставляет ответ клиенту в исходной VLAN.
6. Аналогично передаются `DHCPREQUEST` и `DHCPACK`.

**Важно:** адрес источника IP-пакета и `giaddr` — разные вещи. Для выбора клиентской сети ISC DHCP обычно использует именно `giaddr` при ретрансляции. Если запрос поступил непосредственно на интерфейс DHCP-сервера без relay, сервер определяет сеть по принимающему интерфейсу.

## 3. Поле giaddr и выбор подсети

**`giaddr` (Gateway IP Address)** — поле BOOTP/DHCP-пакета, которое relay использует для обозначения сети клиента и маршрута возврата ответа.

Пример:

```text
Клиент:           DHCPDISCOVER, giaddr = 0.0.0.0
Relay (VLAN 10):  DHCPDISCOVER, giaddr = 192.168.10.1
Сервер:          ищет subnet, содержащий 192.168.10.1
```

Серверная конфигурация:

```dhcpd
subnet 192.168.10.0 netmask 255.255.255.0 {
    option routers 192.168.10.1;
    range 192.168.10.100 192.168.10.200;
}

subnet 192.168.20.0 netmask 255.255.255.0 {
    option routers 192.168.20.1;
    range 192.168.20.100 192.168.20.200;
}
```

Для запроса с `giaddr = 192.168.20.1` сервер выбирает конфигурацию VLAN 20. Он **не выбирает подсеть по MAC-адресу клиента** и не предполагает, что клиент находится в сети самого DHCP-сервера.

При использовании специальных relay-механизмов, например link-selection suboption, правила выбора сети могут отличаться. Такие механизмы следует проверять на совместимость с конкретной версией ISC DHCP и сетевым оборудованием.

## 4. Полная базовая конфигурация центрального ISC DHCP

Предположим:

| Назначение | Адрес / сеть |
|---|---|
| DHCP-сервер | `192.168.100.10/24` |
| Шлюз VLAN 10 | `192.168.10.1/24` |
| Шлюз VLAN 20 | `192.168.20.1/24` |
| DNS | `192.168.100.53` |

Пример `/etc/dhcp/dhcpd.conf`:

```dhcpd
# Центральный DHCP-сервер для нескольких VLAN.
authoritative;
log-facility local7;

default-lease-time 3600;
max-lease-time 7200;

option domain-name "example.internal";
option domain-name-servers 192.168.100.53;

# Подсеть интерфейса самого DHCP-сервера.
# Динамический пул здесь не нужен.
subnet 192.168.100.0 netmask 255.255.255.0 {
}

# Клиенты VLAN 10, запросы приходят через relay 192.168.10.1.
subnet 192.168.10.0 netmask 255.255.255.0 {
    option routers 192.168.10.1;
    option broadcast-address 192.168.10.255;
    range 192.168.10.100 192.168.10.200;
}

# Клиенты VLAN 20, запросы приходят через relay 192.168.20.1.
subnet 192.168.20.0 netmask 255.255.255.0 {
    option routers 192.168.20.1;
    option broadcast-address 192.168.20.255;
    range 192.168.20.100 192.168.20.200;
}
```

**Почему указан пустой `subnet 192.168.100.0/24`?** ISC DHCP обычно требует описание подсети, к которой принадлежит обслуживаемый локальный интерфейс, даже если выдавать адреса в ней не планируется. Пустой блок описывает подключенную сеть, но не создает динамический пул.

**Почему `option routers` различается?** Клиенту нужен шлюз именно его VLAN. Центральный DHCP-сервер не должен выдавать всем клиентам адрес своего локального маршрутизатора.

**Почему `authoritative;`?** Сервер объявляется авторитетным для обслуживаемых сетей. Применять директиву следует только там, где администратор действительно управляет DHCP-адресацией; иначе можно мешать работе другого сервера.

Проверка синтаксиса:

```bash
sudo dhcpd -t -4 -cf /etc/dhcp/dhcpd.conf
```

Проверка, что служба запущена и слушает нужный интерфейс:

```bash
systemctl status isc-dhcp-server
sudo ss -lunp | grep ':67'
```

Фактическое имя службы и способ указания интерфейсов зависят от дистрибутива и установленного пакета.

## 5. Где настраивается DHCP Relay

**Relay настраивается на маршрутизаторе или L3-коммутаторе**, а не в блоке `subnet` DHCP-сервера. На оборудовании Cisco-подобного синтаксиса это часто выглядит так:

```text
interface Vlan10
 ip address 192.168.10.1 255.255.255.0
 ip helper-address 192.168.100.10

interface Vlan20
 ip address 192.168.20.1 255.255.255.0
 ip helper-address 192.168.100.10
```

Это **иллюстрация синтаксиса конкретного семейства сетевых устройств**, а не универсальная команда для всех маршрутизаторов.

В Linux отдельным relay-процессом может выступать `dhcrelay` из ISC DHCP. Его конфигурация зависит от версии пакета, интерфейсов и схемы сети. Важно не запускать relay без необходимости на DHCP-сервере: это две разные роли.

## 6. Что такое shared-network и какую проблему он решает

**`shared-network`** — объявление ISC DHCP, объединяющее несколько IP-подсетей, находящихся в **одном общем канальном сегменте (одном L2 broadcast domain)**.

Это не синоним «нескольких VLAN», «нескольких офисов» или «нескольких подсетей, обслуживаемых одним сервером».

Типичная ситуация: в одном VLAN исторически используется `192.168.10.0/24`, но адресов стало мало; на тот же L2-сегмент добавляют вторую логическую IP-подсеть `192.168.11.0/24`. Обе подсети обслуживаются через один физический/виртуальный сегмент, а маршрутизатор должен иметь адреса в обеих подсетях.

```text
                 ОДИН VLAN / ОДИН L2-СЕГМЕНТ
                ┌───────────────────────────┐
                │ ПК A: 192.168.10.101      │
                │ ПК B: 192.168.11.101      │
                │ Шлюзы: .10.1 и .11.1      │
                └───────────────────────────┘
```

**Ключевое отличие:** `shared-network` описывает совместное расположение подсетей на одном канальном сегменте; `DHCP Relay` пересылает запросы через границы L3-сетей.

## 7. Синтаксис shared-network

```dhcpd
shared-network "campus-lan" {
    option domain-name "example.internal";
    option domain-name-servers 192.168.100.53;

    subnet 192.168.10.0 netmask 255.255.255.0 {
        option routers 192.168.10.1;
        pool {
            range 192.168.10.100 192.168.10.200;
        }
    }

    subnet 192.168.11.0 netmask 255.255.255.0 {
        option routers 192.168.11.1;
        pool {
            range 192.168.11.100 192.168.11.200;
        }
    }
}
```

Здесь обе подсети входят в один `shared-network`. Сервер рассматривает их как относящиеся к одной физической сети и может выделять динамические адреса из доступных пулов соответствующей общей сети.

**Нюанс:** настройки, специфичные для IP-подсети, например шлюз `option routers`, должны соответствовать реально назначенному клиенту адресу. Нельзя бездумно помещать один `option routers` на уровень `shared-network`, если у подсетей разные шлюзы.

### Как действует наследование

```text
Глобальные параметры
└── shared-network "campus-lan"
    ├── subnet 192.168.10.0/24
    │   └── pool 192.168.10.100–200
    └── subnet 192.168.11.0/24
        └── pool 192.168.11.100–200
```

Общие параметры можно задать на уровне `shared-network`, а различающиеся — внутри конкретных `subnet` или `pool`. При этом действуют общие правила областей действия ISC DHCP; нельзя считать, что любое объявление в `shared-network` автоматически корректно для каждого клиента.

## 8. Когда shared-network использовать нельзя

**Неверный пример:**

```dhcpd
# НЕПРАВИЛЬНО для двух изолированных VLAN:
shared-network "all-vlans" {
    subnet 192.168.10.0 netmask 255.255.255.0 {
        range 192.168.10.100 192.168.10.200;
    }
    subnet 192.168.20.0 netmask 255.255.255.0 {
        range 192.168.20.100 192.168.20.200;
    }
}
```

Если VLAN 10 и VLAN 20 — **разные L2-сегменты**, объединять их в `shared-network` нельзя. В противном случае DHCP-сервер может считать их общим сегментом и неправильно выбирать адресный пул.

Для отдельных VLAN нужны отдельные `subnet` и корректно настроенный relay на каждом L3-интерфейсе.

## 9. DHCP Relay Option 82

**Option 82 (Relay Agent Information)** — дополнительные сведения, которые relay может включать в DHCP-запрос. Часто встречаются:

- **Circuit ID** — идентификатор порта, интерфейса или логического канала, через который пришел клиент.
- **Remote ID** — идентификатор relay-устройства или другой уникальный идентификатор, назначенный оборудованием.

С помощью этих данных можно различать клиентов не только по IP-сети, но и по месту подключения. Формат содержимого Option 82 зависит от производителя и настроек relay.

Пример классификации по содержимому подопции (значение показано условно):

```dhcpd
class "building-a" {
    match if option agent.circuit-id = "SW1-PORT10";
}
```

Этот пример будет работать **только если relay действительно передает именно такие байты**. На практике сначала снимают DHCP-пакет и выясняют точный формат Circuit ID.

Важное ограничение: Option 82 полезна для политики выдачи адресов, но ее достоверность зависит от доверия к relay и защиты портов. Не следует воспринимать ее как самостоятельную криптографическую аутентификацию.

## 10. Relay, классы и пулы: как взаимодействуют механизмы

В сложной топологии сервер последовательно решает разные задачи:

1. **Откуда клиент?** Сеть определяется по интерфейсу получения запроса или по данным relay (`giaddr`, а при поддерживаемой специальной конфигурации — по дополнительным механизмам).
2. **К каким классам относится клиент?** Вычисляются условия `class`, `match if`, `match` и `subclass`.
3. **Какие адреса допустимы?** Учитываются соответствующие `subnet`, `shared-network`, `pool`, правила `allow`/`deny`, резервации и существующие аренды.
4. **Какие параметры отправить?** Применяются правила областей действия и параметры подходящего объявления.

Это логическая модель для понимания решения сервера, а не буквальный список внутренних функций в порядке их вызова.

Пример ограничения отдельного пула в VLAN 10:

```dhcpd
class "managed-pcs" {
    match hardware;
}
subclass "managed-pcs" 1:aa:bb:cc:dd:ee:ff;

subnet 192.168.10.0 netmask 255.255.255.0 {
    option routers 192.168.10.1;

    pool {
        allow members of "managed-pcs";
        range 192.168.10.100 192.168.10.150;
    }

    pool {
        deny members of "managed-pcs";
        range 192.168.10.151 192.168.10.200;
    }
}
```

Relay определяет **клиентскую сеть**, а класс — **допустимый пул внутри нее**. Один механизм не заменяет другой.

## 11. Особенности маршрутизации, firewall и NAT

Для успешной работы нужно проверить всю цепочку:

- Relay принимает клиентские DHCP-пакеты на нужном VLAN-интерфейсе.
- Между relay и сервером разрешен необходимый UDP-трафик DHCP (серверный порт 67; клиентский порт 68 используется в клиентском сегменте).
- Relay может отправлять запросы на IP DHCP-сервера и получать ответы.
- Сервер содержит объявления всех обслуживаемых клиентских подсетей.
- Клиенты получают корректные `option routers`, DNS и маску подсети.
- На маршрутизаторе существуют нужные интерфейсы и маршруты.

**NAT обычно не нужен** для DHCP Relay в маршрутизируемой внутренней сети. NAT или промежуточные устройства, изменяющие поля и адреса, могут усложнить диагностику; особенно важно сохранять корректный `giaddr`.

## 12. Диагностика DHCP Relay

### 12.1. Проверка синтаксиса

```bash
sudo dhcpd -t -4 -cf /etc/dhcp/dhcpd.conf
```

### 12.2. Журнал сервера

```bash
sudo journalctl -u isc-dhcp-server -n 100 --no-pager
sudo journalctl -u isc-dhcp-server -f
```

В зависимости от дистрибутива сообщения могут также находиться в syslog.

### 12.3. Захват DHCP-пакетов

```bash
sudo tcpdump -ni any -vvv 'udp port 67 or udp port 68'
```

Обратить внимание на:

- `giaddr`: совпадает ли он с интерфейсом клиентской сети;
- наличие `Option 82`, если она ожидается;
- `DHCPOFFER`: отправляет ли сервер ответ;
- отсутствие ошибок «no subnet declaration» или «no free leases» в журнале.

### 12.4. Таблица типичных неисправностей

| Симптом | Возможная причина | Что проверить |
|---|---|---|
| В другой VLAN нет DHCP-ответа | Relay не настроен или недоступен сервер | IP helper, маршруты, ACL, tcpdump |
| Сервер видит запрос, но не выдает адрес | Нет соответствующей подсети или свободного пула | `giaddr`, `subnet`, `pool`, журнал |
| Клиент получает адрес не той сети | Ошибочная модель `shared-network` или некорректный relay | L2-топологию, `giaddr`, объявления |
| Клиент получает IP, но нет связи | Неверный шлюз, маска, DNS или VLAN | `option routers`, L3-интерфейсы, маршруты |
| Не работает классификация по Option 82 | Неверные байты или relay не добавляет опцию | `tcpdump -vvv`, формат Circuit ID |
| Только часть устройств получает адрес | Политика классов, резервации или исчерпание пула | `allow`/`deny`, leases, диапазоны |

## 13. Рекомендации по проектированию

1. **Одна VLAN — отдельное объявление `subnet`**, если VLAN действительно представляет самостоятельный L2-сегмент.
2. Использовать `shared-network` только при реальном совместном L2-размещении нескольких IP-подсетей.
3. Настраивать relay на L3-шлюзах клиентских сетей, а не пытаться заменить его параметрами `dhcpd.conf`.
4. Документировать соответствие «VLAN → подсеть → шлюз → DHCP-пул → relay».
5. Проверять точный формат Option 82 на реальном оборудовании до написания правил классификации.
6. Не полагаться на MAC или Option 82 как на единственную меру безопасности; применять сетевые механизмы контроля доступа.
7. Перед изменением конфигурации сохранять резервную копию и выполнять `dhcpd -t`.

## 14. Глоссарий

| Термин | Определение |
|---|---|
| **DHCP Relay Agent** | Устройство или служба, пересылающая DHCP-сообщения между клиентской сетью и удаленным DHCP-сервером. |
| **L2 broadcast domain** | Канальный сегмент, внутри которого распространяются широковещательные Ethernet-кадры. |
| **VLAN** | Логическое разделение L2-сети на независимые широковещательные домены. |
| **L3-интерфейс / SVI** | Интерфейс маршрутизатора или коммутатора, обслуживающий IP-подсеть VLAN. |
| **`giaddr`** | Поле DHCP/BOOTP-пакета с адресом relay-агента, используемое для определения клиентской сети и возврата ответа. |
| **`subnet`** | Объявление IP-подсети в конфигурации ISC DHCP. |
| **`pool`** | Группа адресов и правил их выдачи внутри подходящей сетевой области. |
| **`shared-network`** | Объявление нескольких IP-подсетей, совместно использующих один L2-сегмент. |
| **Option 82** | DHCP-опция с информацией, добавляемой relay-агентом. |
| **Circuit ID** | Подопция Option 82, идентифицирующая канал/порт подключения клиента. |
| **Remote ID** | Подопция Option 82, идентифицирующая relay или другой назначенный устройством объект. |
| **IP helper** | Распространенное название настройки ретрансляции UDP/DHCP на сетевом оборудовании. |
| **DHCPDISCOVER** | Сообщение поиска DHCP-сервера клиентом. |
| **DHCPOFFER** | Предложение IP-адреса и параметров от DHCP-сервера. |

## Итоги — что было разобрано

- DHCP Relay позволяет централизованно обслуживать разные маршрутизируемые подсети.
- `giaddr` помогает серверу определить клиентскую сеть при ретрансляции.
- `shared-network` объединяет **несколько IP-подсетей в одном L2-сегменте**, а не отдельные VLAN.
- Классификация и политики пулов работают совместно с определением клиентской сети.
- Option 82 добавляет сведения о точке подключения, но требует проверки формата и доверия к relay.
- Для диагностики полезны `dhcpd -t`, журналы сервера и `tcpdump`.
