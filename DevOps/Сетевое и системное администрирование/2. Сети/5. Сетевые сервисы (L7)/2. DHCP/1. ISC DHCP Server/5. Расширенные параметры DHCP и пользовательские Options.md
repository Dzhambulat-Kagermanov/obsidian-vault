## 1. Что такое DHCP Option и чем она отличается от директивы

**DHCP Option** — параметр, передаваемый в DHCP-сообщении, который сообщает клиенту сведения о сетевой среде или дополнительных сервисах. У опции есть **числовой код**, **формат данных** и **значение**.

В `dhcpd.conf` нужно различать:

```dhcpd
option domain-name-servers 10.26.250.7, 10.26.250.8;
default-lease-time 7200;
```

- `option domain-name-servers` — параметр DHCP, который может попасть в ответ клиенту (код 6).
- `default-lease-time` — директива поведения самого сервера, а не самостоятельная DHCP Option с таким названием.

Сервер не обязан отправлять клиенту все заданные опции: на результат влияют запрос клиента (Parameter Request List), условия конфигурации и логика реализации.

## 2. Основные и расширенные стандартные опции

| Опция в `dhcpd.conf` | Код DHCPv4 | Назначение | Пример |
|---|---:|---|---|
| `subnet-mask` | 1 | Маска сети | `255.0.0.0` |
| `routers` | 3 | Шлюз(ы) по умолчанию | `10.0.0.1` |
| `domain-name-servers` | 6 | DNS-серверы | `10.26.250.7, 10.26.250.8` |
| `host-name` | 12 | Имя хоста | `"pc-01"` |
| `domain-name` | 15 | DNS-суффикс | `"ggkit.local"` |
| `broadcast-address` | 28 | Broadcast-адрес IPv4 | `10.255.255.255` |
| `ntp-servers` | 42 | NTP-серверы | `10.26.250.6` |
| `vendor-encapsulated-options` | 43 | Вендорские вложенные данные | Зависит от вендора |
| `requested-address` | 50 | IP, запрашиваемый клиентом | Обычно задается клиентом |
| `dhcp-lease-time` | 51 | Срок аренды в секундах | Обычно формирует сервер |
| `dhcp-message-type` | 53 | Тип DHCP-сообщения | Служебное поле протокола |
| `dhcp-server-identifier` | 54 | Идентификатор сервера | Формирует сервер |
| `parameter-request-list` | 55 | Список желаемых опций | Отправляет клиент |
| `vendor-class-identifier` | 60 | Тип/класс клиента по данным клиента | `"PXEClient"` и др. |
| `client-identifier` | 61 | Идентификатор клиента | Обычно отправляет клиент |
| `user-class` | 77 | Пользовательский класс | Зависит от клиента |
| `domain-search` | 119 | Список поисковых DNS-суффиксов | `"ggkit.local"` |
| `classless-static-routes` | 121 | Маршруты CIDR | Специальный формат |
| `architecture-type` | 93 | Архитектура PXE-клиента | Обычно отправляет клиент |

> [!warning] Не все опции предназначены для задания на сервере
> Например, `parameter-request-list` и `vendor-class-identifier` обычно приходят **от клиента** и используются сервером для принятия решений. Наличие имени в справочнике не означает, что следует отправлять его в DHCP Offer.

### 2.1. Пример расширенного набора параметров

```dhcpd
option domain-name "ggkit.local";
option domain-name-servers 10.26.250.7, 10.26.250.8;
option domain-search "ggkit.local";
option ntp-servers 10.26.250.6;

subnet 10.0.0.0 netmask 255.0.0.0 {
    option routers 10.0.0.1;

    pool {
        range 10.26.1.10 10.26.1.254;
    }
}
```

Здесь DNS, доменный суффикс и NTP заданы глобально, а шлюз — для конкретной подсети. Общие правила наследования рассматриваются в предыдущей заметке.

## 3. Типы данных DHCP Options

При определении пользовательской опции необходимо указать, **как интерпретировать байты ее значения**.

| Тип | Что хранит | Пример объявления |
|---|---|---|
| `ip-address` | IPv4-адрес | `option site-server code 224 = ip-address;` |
| `text` | Текст | `option site-label code 225 = text;` |
| `string` | Произвольные байты | `option site-token code 226 = string;` |
| `boolean` | Логическое значение | `option site-enabled code 227 = boolean;` |
| `unsigned integer 8` | Число 0–255 | `option site-level code 228 = unsigned integer 8;` |
| `unsigned integer 16` | Число 0–65535 | `option site-port code 229 = unsigned integer 16;` |
| `unsigned integer 32` | 32-битное число | `option site-time code 230 = unsigned integer 32;` |
| `array of ip-address` | Несколько IPv4-адресов | `option site-dns code 231 = array of ip-address;` |

**`text` и `string` не взаимозаменяемы:** первый предназначен для текстовых данных, второй — для произвольной последовательности байтов. Тип должен соответствовать спецификации принимающего клиента.

## 4. Создание пользовательских опций

Формат объявления:

```dhcpd
option <имя> code <код> = <тип>;
```

Затем задается значение:

```dhcpd
option site-server code 224 = ip-address;
option site-label code 225 = text;
option site-dns code 231 = array of ip-address;

option site-server 10.26.250.20;
option site-label "ggkit-lab";
option site-dns 10.26.250.7, 10.26.250.8;
```

Коды **224–254** выделены для локальных DHCPv4-опций организации (*site-local*). Их нельзя без согласования использовать для параметров конкретного производителя, если тот ожидает другой код и формат.

> [!important] Совместимость
> Создание опции на DHCP-сервере **не заставляет клиента ее использовать**. Клиент должен поддерживать соответствующий код и формат; иногда он должен явно запросить эту опцию.

### 4.1. Как избежать конфликтов кодов

Перед введением пользовательской опции проверьте:

1. Не занят ли код стандартной опцией.
2. Не использует ли этот код программное обеспечение клиента.
3. Соответствует ли тип данных документации клиента.
4. Не требуется ли вместо глобального кода вложенная вендорская опция.

## 5. Пространства опций (`option space`)

**Option Space** — именованное пространство, в котором определяются собственные коды подопций. Оно помогает описывать вложенные параметры производителей и не смешивать их с обычными кодами DHCPv4.

```dhcpd
option space PXELINUX;
option PXELINUX.magic code 208 = string;
option PXELINUX.configfile code 209 = text;
option PXELINUX.pathprefix code 210 = text;
option PXELINUX.reboottime code 211 = unsigned integer 32;
```

Здесь `PXELINUX` — имя пространства, а `magic`, `configfile` и другие — определения параметров внутри него. **Само определение не означает автоматическую передачу опции клиенту.** Нужно отдельно задать значение и, при необходимости, механизм инкапсуляции. В конфигурациях PXELINUX исторически используются коды 208–211; их нельзя считать свободными универсальными site-local кодами.

### 5.1. Настройка формата пространства

```dhcpd
option space vendor-demo code width 1 length width 1;
option vendor-demo.endpoint code 1 = ip-address;
option vendor-demo.mode code 2 = unsigned integer 8;
```

- `code width` — число байтов для кода вложенной опции.
- `length width` — число байтов для длины ее значения.
- Для многих DHCPv4-вендорских подопций используются значения `1` и `1`, но формат всегда определяется протоколом или документацией производителя.

## 6. Инкапсуляция: вложенные опции производителя

Некоторые устройства ожидают не отдельную опцию с произвольным кодом, а **набор подопций внутри DHCP Option 43**.

Упрощенный пример для условного устройства, которое документированно ожидает две подопции:

```dhcpd
option space vendor-demo;
option vendor-demo.endpoint code 1 = ip-address;
option vendor-demo.mode code 2 = unsigned integer 8;

class "vendor-demo-clients" {
    match if option vendor-class-identifier = "DemoDevice";
    vendor-option-space vendor-demo;
    option vendor-demo.endpoint 10.26.250.20;
    option vendor-demo.mode 2;
}
```

**Что происходит:**

1. Клиент присылает Option 60 со значением `DemoDevice`.
2. Условие класса сопоставляет его с этим значением.
3. `vendor-option-space` сообщает `dhcpd`, какие подопции собрать в Option 43.
4. Клиент получает вложенные значения в формате, который должен понимать.

> [!warning] Демонстрационный формат
> `DemoDevice`, коды подопций `1`/`2` и их типы — учебный пример, а не стандарт конкретного оборудования. Для реальных телефонов, точек доступа, контроллеров и тонких клиентов следует использовать документацию производителя.

Классы клиентов и сложные условия будут подробно разобраны в следующей заметке; здесь они нужны только для понимания доставки вендорских параметров.

### 6.1. VIVSO и Enterprise Number

**VIVSO (Option 125)** позволяет передавать данные, привязанные к идентификатору производителя (*Enterprise Number*). В отличие от Option 43, этот формат предусматривает явное указание производителя и может содержать несколько вендорских блоков.

Не следует заменять Option 43 на Option 125 без проверки поддержки клиентом: это **разные форматы**, а не две записи одного параметра.

## 7. Сложные структуры: массивы и записи

**Массив (`array`)** содержит несколько элементов одного формата:

```dhcpd
option site-dns code 231 = array of ip-address;
option site-dns 10.26.250.7, 10.26.250.8;
```

**Запись (`record`)** объединяет поля разных типов в фиксированном порядке:

```dhcpd
option site-profile code 232 = { boolean, unsigned integer 16, text };
option site-profile on 8080 "managed";
```

Здесь значение состоит из трех последовательных полей: логического признака, 16-битного числа и текста. Клиент должен разбирать их в том же порядке.

**Массивы текстовых и произвольных байтовых строк** в синтаксисе ISC DHCP не поддерживаются как обычный `array of text` / `array of string`; для таких форматов используют специально описанную структуру или бинарное представление по спецификации.

## 8. Опции маршрутизации: статические маршруты через DHCP

**Option 121 (`classless-static-routes`)** передает клиенту маршруты с длиной префикса и следующим переходом. Это не заменяет маршрутизатор и не гарантирует поддержку у всех DHCP-клиентов.

Пример для маршрута к сети `172.16.0.0/16` через `10.0.0.1`:

```dhcpd
option classless-static-routes 16, 172, 16, 10, 0, 0, 1;
```

В этом примере байты кодируют: длину префикса `/16`, два значимых байта адреса сети (`172.16`) и четыре байта IPv4-адреса шлюза (`10.0.0.1`). **Для других префиксов количество байтов сети меняется**. В production следует сверять кодирование с RFC 3442 и проверять полученные маршруты на клиенте.

Сама маршрутизация IPv4 рассматривается в профильных заметках сетевого уровня; здесь важно лишь знать механизм доставки маршрутов через DHCP.

## 9. Option 82: данные DHCP Relay

**Option 82 (`relay-agent-information`)** добавляется DHCP Relay Agent и может содержать:

- `circuit-id` — идентификатор порта, интерфейса или сегмента;
- `remote-id` — идентификатор оборудования или другого контекста, заданный Relay.

На стороне `dhcpd` эти данные могут использоваться для выбора настроек или классификации клиентов:

```dhcpd
class "uplink-a" {
    match if option agent.circuit-id = "uplink-a";
}
```

Значение `uplink-a` условное: реальный формат `circuit-id` определяется коммутатором или Relay и нередко представляет собой **бинарные данные**, а не текст.

Важно: Option 82 не является надежным подтверждением личности клиента сама по себе. Доверие к ней зависит от сетевой архитектуры и контроля Relay-портов.

## 10. Получение опций клиентом и проверка результата

### 10.1. Parameter Request List

В Option 55 клиент сообщает, какие параметры хочет получить. Сервер учитывает этот список при формировании ответа. Некоторые опции могут передаваться независимо от него в соответствии с правилами протокола и реализации.

Поэтому возможна ситуация: **опция определена правильно, но клиент ее не запрашивает, не получает или игнорирует**.

### 10.2. Проверка конфигурации

```bash
sudo dhcpd -t -cf /etc/dhcp/dhcpd.conf
```

Команда проверяет синтаксис конфигурации. Успешная проверка **не доказывает**, что клиент понимает пользовательские опции.

### 10.3. Анализ DHCP-пакетов

```bash
sudo tcpdump -ni enp1s0 -vvv -s0 'udp port 67 or udp port 68'
```

В выводе нужно проверить:

- отправил ли клиент Option 55, 60, 77 или 93;
- присутствует ли нужная опция в DHCP Offer/ACK;
- правильно ли сформировано ее значение;
- не обрезаны ли данные из-за ограничений размера DHCP-пакета.

`enp1s0` — пример имени интерфейса; в реальной системе используйте интерфейс, на котором проходит DHCP-трафик.

### 10.4. Частые ошибки

| Симптом | Возможная причина | Проверка |
|---|---|---|
| Клиент не получает пользовательскую опцию | Не запрашивает ее или не поддерживает | Option 55 и документация клиента |
| Опция передается, но не работает | Неверный тип/код/кодировка | Сопоставить с документацией производителя |
| Option 43 не распознается | Неверный формат подопций или не выбран `vendor-option-space` | Захват DHCP-пакета |
| Класс не применяется | Отличается значение Option 60 | Посмотреть фактический пакет клиента |
| Option 82 не видна | Relay ее не добавляет | Захват пакетов между Relay и сервером |
| `dhcpd` не запускается | Ошибка определения или конфликт имен | `dhcpd -t` и журнал |

## 11. Глоссарий

| Термин | Определение |
|---|---|
| **DHCP Option** | Параметр с числовым кодом и определенным форматом данных в DHCP-сообщении. |
| **Option Code** | Числовой идентификатор DHCP Option. |
| **Option Space** | Именованное пространство определений опций или подопций. |
| **Encapsulation** | Упаковка нескольких подопций внутрь другой DHCP Option. |
| **Vendor-specific Option** | Опция или подопция, формат которой определяет производитель оборудования или ПО. |
| **Option 43** | DHCPv4 Vendor-Specific Information, контейнер вендорских данных. |
| **Option 55 / PRL** | Parameter Request List — перечень опций, запрашиваемых клиентом. |
| **Option 60 / VCI** | Vendor Class Identifier — идентификатор типа клиента, который он сообщает серверу. |
| **Option 82** | Relay Agent Information — сведения, добавляемые DHCP Relay. |
| **Option 93** | Client System Architecture Type — идентификатор архитектуры, используемый в том числе PXE. |
| **Option 121** | Classless Static Route — доставка статических маршрутов клиенту. |
| **Option 125 / VIVSO** | Vendor-Identifying Vendor-Specific Information — вендорские данные с Enterprise Number. |
| **Record** | Составной формат опции с несколькими полями разных типов. |
| **Array** | Последовательность однотипных значений внутри опции. |
