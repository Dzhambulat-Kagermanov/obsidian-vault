## 1. Зачем нужны обработчики событий

Обычная конфигурация DHCP определяет адреса и параметры, которые сервер предлагает клиентам. Обработчики событий выполняют дополнительные действия **при изменении состояния аренды**.

Типичные задачи:

- записать сведения о выданном адресе в системный журнал;
- сообщить внешней системе об изменении аренды;
- добавить или удалить DNS-запись через отдельный интеграционный скрипт;
- обновить инвентаризацию или учет подключений.

Обработчик не заменяет штатную выдачу IP-адресов. Ошибка внешней интеграции не должна становиться причиной недоступности DHCP.

## 2. Три основных события: `on commit`, `on release`, `on expiry`

| Событие | Когда срабатывает | Пример задачи |
|---|---|---|
| `on commit` | Когда сервер фиксирует аренду за клиентом | Отправить событие о выдаче адреса |
| `on release` | Когда клиент явно освобождает аренду (`DHCPRELEASE`) | Уведомить систему учета |
| `on expiry` | Когда срок аренды истек и сервер обрабатывает ее истечение | Удалить устаревшую запись из внешней системы |

**Важные ограничения:**

1. `on release` **не сработает**, если компьютер просто выключился или пропал из сети, не отправив DHCPRELEASE.
2. `on expiry` не следует трактовать как точный таймер отключения клиента: обработка истечения зависит от внутренней работы сервера.
3. `on commit` не означает, что устройство доступно по сети или что оно успешно применило полученные параметры.
4. Обновление аренды и повторные DHCP-обмены могут порождать повторные события. Внешние действия следует проектировать **идемпотентными**.

## 3. Синтаксис блока `on`

```dhcpd
on commit {
    log(info, "DHCP: lease committed");
}

on release {
    log(info, "DHCP: lease released");
}

on expiry {
    log(info, "DHCP: lease expired");
}
```

Общий вид:

```dhcpd
on <событие> {
    <инструкция>;
    <инструкция>;
}
```

Внутри допустимы поддерживаемые исполняемые инструкции языка `dhcpd.conf`, например `set`, `if`, `log` и, при наличии поддержки, `execute`. Это не shell: команды Linux нельзя писать прямо внутри фигурных скобок.

## 4. Где размещать обработчики и как работает область действия

Обработчики могут быть заданы в подходящих областях конфигурации, например в контексте подсети или объявления хоста. Конкретное размещение следует проверять по `dhcpd.conf(5)` установленной версии; не все декларации принимают одинаковые инструкции.

Пример для подсети:

```dhcpd
subnet 192.168.50.0 netmask 255.255.255.0 {
    option routers 192.168.50.1;

    pool {
        range 192.168.50.100 192.168.50.200;
    }

    on commit {
        log(info, "DHCP: commit in subnet 192.168.50.0/24");
    }
}
```

Не путайте **наследование параметров DHCP Options** и **выполнение событийных инструкций**. Для событий важно, к какому контексту относится аренда и какие обработчики действуют для нее. Нельзя автоматически предполагать, что обработчики из разных вложенных блоков будут выполнены последовательно: это нужно проверять по документации и на тестовом сервере.

## 5. Данные, доступные в обработчике

Наиболее полезные выражения:

| Выражение | Что возвращает | Применение |
|---|---|---|
| `leased-address` | IP-адрес текущей аренды | Передать адрес интеграции |
| `hardware` | Тип оборудования и аппаратный адрес | Идентифицировать устройство |
| `option host-name` | Имя, присланное клиентом, если оно есть | Сформировать имя узла |
| `option dhcp-client-identifier` | Идентификатор клиента, если он передан | Дополнительная идентификация |
| `binary-to-ascii(...)` | Текстовое представление байтов или чисел | Преобразовать IP/MAC в строку |
| `pick-first-value(...)` | Первое доступное значение | Резервное имя при отсутствии host-name |
| `concat(...)` | Конкатенация строк/данных | Сформировать сообщение |

Пример записи IP-адреса в журнал:

```dhcpd
on commit {
    set lease_ip = binary-to-ascii(10, 8, ".", leased-address);
    log(info, concat("DHCP COMMIT: ", lease_ip));
}
```

Разбор `binary-to-ascii(10, 8, ".", leased-address)`:

- `10` — десятичная система счисления;
- `8` — размер одного преобразуемого элемента в битах;
- `"."` — разделитель между октетами;
- `leased-address` — четыре байта IPv4-адреса.

Для аренды `192.168.50.120` результатом будет строка `"192.168.50.120"`.

## 6. Получение MAC-адреса и имени клиента

`hardware` включает **тип оборудования**, поэтому для Ethernet-адреса из него обычно извлекают шесть байтов, начиная со второго:

```dhcpd
on commit {
    set mac = binary-to-ascii(
        16, 8, ":", substring(hardware, 1, 6)
    );

    set ip = binary-to-ascii(10, 8, ".", leased-address);

    log(info, concat("DHCP COMMIT: ip=", ip, " mac=", mac));
}
```

`binary-to-ascii()` может выводить шестнадцатеричные элементы без ведущих нулей. Например, `0a` может превратиться в `a`. Для человекочитаемого журнала это допустимо, но для сравнения с канонической формой MAC или использования в DNS-именах потребуется нормализация.

Имя, присланное клиентом, может отсутствовать:

```dhcpd
on commit {
    set client_name = pick-first-value(
        option host-name,
        "unknown-client"
    );

    log(info, concat("DHCP client: ", client_name));
}
```

Имя из DHCP-пакета **нельзя считать доверенным**: клиент может прислать произвольное значение. Для DNS и внешних команд нужно применять строгую валидацию.

## 7. Условные инструкции в обработчиках

Можно выполнять разные действия в зависимости от данных клиента:

```dhcpd
on commit {
    if exists host-name {
        log(info, concat("DHCP host-name: ", option host-name));
    } else {
        log(info, "DHCP: client did not send host-name");
    }
}
```

`exists host-name` проверяет наличие опции. Это не проверка подлинности и не гарантия, что значение подходит для имени DNS.

Отдельно различайте:

- `match if` — классификация клиентов;
- `if` в обработчике — условное выполнение инструкций при наступлении события.

## 8. `execute()` — вызов внешней программы

В некоторых сборках ISC DHCP поддерживается инструкция:

```dhcpd
execute("/usr/local/sbin/dhcp-event.sh", "commit", "192.168.50.120");
```

Здесь:

- первый аргумент — **абсолютный путь** к исполняемому файлу;
- следующие аргументы — строки, передаваемые программе как аргументы командной строки;
- `execute()` не является оболочкой Bash и не интерпретирует `|`, `>`, `&&` и другие shell-операторы;
- выполняемая программа наследует ограничения учетной записи, под которой работает `dhcpd`, а также ограничения AppArmor/SELinux/systemd, если они применяются.

**Проверка поддержки:** добавьте тестовый вызов только на отдельном тестовом сервере и выполните `dhcpd -t -cf /etc/dhcp/dhcpd.conf`. Успешная проверка синтаксиса сама по себе не гарантирует, что скрипт будет успешно запущен: необходимо проверить журнал и фактическое событие.

Пример динамической передачи адреса:

```dhcpd
on commit {
    set ip = binary-to-ascii(10, 8, ".", leased-address);
    execute("/usr/local/sbin/dhcp-event.sh", "commit", ip);
}
```

Не все версии и дистрибутивные сборки имеют одинаковую поддержку внешнего исполнения. Если `execute()` недоступен или запрещен политикой безопасности, используйте **внешний обработчик журналов или событий** вместо изменения исходного кода DHCP-сервера.

## 9. Пример внешнего Bash-скрипта

Создадим простой скрипт, который пишет событие в системный журнал. Он **не изменяет DNS**, не делает сетевых запросов и подходит для проверки механизма.

Файл `/usr/local/sbin/dhcp-event.sh`:

```bash
#!/usr/bin/env bash
set -euo pipefail

EVENT="${1:-}"
IP="${2:-}"

case "$EVENT" in
    commit|release|expiry) ;;
    *) exit 2 ;;
esac

if [[ ! "$IP" =~ ^([0-9]{1,3}\.){3}[0-9]{1,3}$ ]]; then
    exit 2
fi

logger -t dhcp-event -- "event=$EVENT ip=$IP"
```

Установка и проверка:

```bash
sudo install -o root -g root -m 0755 dhcp-event.sh /usr/local/sbin/dhcp-event.sh
sudo /usr/local/sbin/dhcp-event.sh commit 192.168.50.120
journalctl -t dhcp-event -n 20 --no-pager
```

Регулярное выражение проверяет **форму** IPv4-адреса, но не диапазон каждого октета. Для внешних интеграций, изменяющих инфраструктуру, нужна полноценная проверка адреса и разрешенной подсети.

Пример обработчиков в `dhcpd.conf`:

```dhcpd
on commit {
    set ip = binary-to-ascii(10, 8, ".", leased-address);
    execute("/usr/local/sbin/dhcp-event.sh", "commit", ip);
}

on release {
    set ip = binary-to-ascii(10, 8, ".", leased-address);
    execute("/usr/local/sbin/dhcp-event.sh", "release", ip);
}

on expiry {
    set ip = binary-to-ascii(10, 8, ".", leased-address);
    execute("/usr/local/sbin/dhcp-event.sh", "expiry", ip);
}
```

Этот пример следует использовать **только после подтверждения поддержки `execute()`**. При проверке нужно отдельно убедиться, что контекст события предоставляет ожидаемые данные.

## 10. Интеграция с Dynamic DNS

В инфраструктуре с Samba AD часто требуется создавать и удалять записи DNS при выдаче адреса. Возможная цепочка:

```text
DHCP-событие
    ↓
Получение IP, MAC и имени клиента
    ↓
Валидация имени и адреса
    ↓
Внешняя очередь или скрипт интеграции
    ↓
Аутентифицированное DNS-обновление
    ↓
Проверка результата и запись в журнал
```

Для обновления DNS могут применяться `nsupdate` и GSS-TSIG с Kerberos-учетными данными. **Детальную настройку DNS и Kerberos здесь не дублируем**: она относится к отдельной заметке о Dynamic DNS.

Нужно различать два подхода:

1. **Встроенный DDNS ISC DHCP** — управляется параметрами `ddns-update-style`, `ddns-updates`, `zone` и связанными настройками.
2. **Внешний DDNS через события** — обработчики запускают собственную интеграцию, если соответствующая функция доступна.

Если задано `ddns-update-style none;`, встроенные обновления DNS отключены. Само по себе `ddns-updates on;` не превращает режим `none` в работающий встроенный DDNS. Внешние скрипты — отдельный механизм.

**Опасность удаления записей:** при `release` или `expiry` нельзя безусловно удалять DNS-запись только по имени: адрес мог быть переиспользован, а запись — обновлена другим событием. Сначала следует проверять, что удаляемая запись по-прежнему относится к исходной аренде.

## 11. Производительность, надежность и безопасность

`dhcpd` — сетевой сервис, от которого зависит получение адресов. Вызов медленного внешнего процесса может повлиять на обработку DHCP-событий.

Рекомендуемые принципы:

- **Минимальная работа в обработчике.** Предпочтительно записать событие в журнал или локальную очередь, а тяжелые операции выполнять отдельным сервисом.
- **Идемпотентность.** Повторное событие `commit` не должно создавать дубли или повреждать состояние.
- **Ограничение времени.** Внешние интеграции не должны бесконечно ждать DNS, БД или API.
- **Безопасность входных данных.** Не подставлять непроверенные `host-name` и `client-identifier` в shell-команды или DNS-операции.
- **Принцип минимальных привилегий.** Не давать DHCP-сервису лишние права на изменение DNS, файлов или БД.
- **Контроль частоты.** Защищаться от потока событий, порождаемого нестабильными или злонамеренными клиентами.
- **Наблюдаемость.** Логировать тип события, IP, идентификатор аренды и результат внешней обработки без раскрытия секретов.

Для production-интеграции предпочтительнее архитектура `dhcpd → журнал/очередь → отдельный агент → DNS/API`, чем длительный синхронный вызов сетевого сервиса непосредственно из `dhcpd`.

## 12. Проверка конфигурации и диагностика

Проверка синтаксиса:

```bash
sudo dhcpd -t -cf /etc/dhcp/dhcpd.conf
```

Просмотр состояния сервиса:

```bash
systemctl status isc-dhcp-server --no-pager
```

Журнал ISC DHCP (имя службы зависит от дистрибутива):

```bash
journalctl -u isc-dhcp-server -n 100 --no-pager
```

Журнал внешнего скрипта:

```bash
journalctl -t dhcp-event -n 50 --no-pager
```

Для анализа DHCP-пакетов:

```bash
sudo tcpdump -ni any -vv 'udp port 67 or udp port 68'
```

Что проверять при ошибках:

| Симптом | Возможная причина | Что проверить |
|---|---|---|
| `on commit` не срабатывает | Обработчик не применяется к аренде | Контекст объявления, фактический DHCP-обмен |
| `execute()` отвергается | Не поддерживается данной сборкой | `dhcpd -t`, установленная версия, документация пакета |
| Скрипт не запускается | Права, путь, ограничения безопасности | `chmod`, AppArmor/SELinux, журнал |
| Имя клиента пустое | Клиент не прислал Option 12 | `exists host-name`, резервное значение |
| Дубли в журнале | Повторные события или обновления аренды | Тип события, временные метки, идемпотентность |
| DNS-запись удалена ошибочно | Удаление без проверки актуального владельца | Сопоставление имени, адреса и аренды |

## 13. Глоссарий

| Термин | Определение |
|---|---|
| **Обработчик события** | Блок инструкций, выполняемых при определенном изменении состояния аренды |
| **`on commit`** | Обработчик фиксации аренды |
| **`on release`** | Обработчик явного освобождения аренды клиентом |
| **`on expiry`** | Обработчик истечения срока аренды |
| **`leased-address`** | Выражение, возвращающее IP-адрес текущей аренды |
| **`set`** | Инструкция присваивания значения переменной |
| **`log()`** | Инструкция записи диагностического сообщения в журнал |
| **`execute()`** | Инструкция вызова внешней программы в сборках, где она поддерживается |
| **Идемпотентность** | Свойство операции давать корректный итог при повторном выполнении |
| **DDNS** | Динамическое обновление записей DNS |
| **GSS-TSIG** | Механизм аутентификации DNS-обновлений с использованием GSS-API, часто совместно с Kerberos |
| **DHCPRELEASE** | Сообщение DHCPv4, которым клиент явно освобождает аренду |
| **Lease** | Аренда IP-адреса с определенным сроком действия |

## Итоги — что было разобрано

- ISC DHCP поддерживает обработчики изменения состояния аренды: `on commit`, `on release`, `on expiry`.
- В обработчиках можно получать данные клиента, вычислять выражения и писать сообщения в журнал.
- Вызов внешних программ через `execute()` зависит от конкретной сборки и должен проверяться отдельно.
- Внешние интеграции требуют проверки входных данных, идемпотентности и ограничения привилегий.
- DDNS через собственный скрипт и встроенный механизм DDNS — разные подходы.
