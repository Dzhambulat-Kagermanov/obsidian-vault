## 1. Зачем нужен DHCP Failover

**DHCP Failover** — механизм взаимодействия двух DHCPv4-серверов, которые обслуживают общий набор динамических адресов и обмениваются сведениями о состоянии аренд.

Без согласования два независимых сервера, которым назначен один и тот же диапазон, могут предложить один IP разным клиентам. Failover помогает избежать такой ситуации: партнеры обмениваются состояниями адресов и согласуют, кто может их выдавать.

**Что обеспечивает механизм:**

- продолжение выдачи и продления адресов при недоступности одного партнера — с ограничениями протокола;
- распределение нагрузки между двумя работающими DHCP-серверами;
- синхронизацию изменений в базе аренд;
- возврат к нормальной работе после восстановления соединения.

**Чего не обеспечивает:**

- автоматическую синхронизацию файла `dhcpd.conf` между узлами;
- защиту от ошибок одинаковой конфигурации на обоих серверах;
- работу без исправной сети, DHCP Relay и доступности соответствующего интерфейса;
- мгновенную и неограниченную выдачу любых адресов после отказа партнера.

## 2. Архитектура: Primary и Secondary

В одной failover-паре есть **два участника**: `primary` и `secondary`. Эти слова обозначают роли протокола, **а не активный и пассивный сервер**. При исправном соединении оба могут отвечать клиентам.

```text
                    Клиенты VLAN 10 / VLAN 20
                              |
                         DHCP Relay
                              |
                 +------------+------------+
                 |                         |
       DHCP-1 (Primary)            DHCP-2 (Secondary)
       10.10.0.10                  10.10.0.11
       UDP 67                      UDP 67
                 |                         |
                 +---- TCP 647 (peer) -----+
                        Состояния аренд
```

- **Клиентский DHCP-трафик:** UDP 67/68 (при наличии Relay пересылается маршрутизатором).
- **Соединение между партнерами:** TCP, в примерах используется порт `647`.
- **DHCP Relay:** для отказоустойчивости должен пересылать запросы на **оба** сервера, если они находятся вне клиентской сети.
- **Время:** синхронизация часов через NTP крайне желательна: существенное расхождение времени приводит к ошибкам failover.

Взаимодействие с DHCP Relay подробно рассматривается в [[Synced/DevOps/Сетевое и системное администрирование/2. Сети/5. Сетевые сервисы (L7)/2. DHCP/1. ISC DHCP Server/11. DHCP Relay, shared-network и сложные топологии.md]].

## 3. Как распределяются запросы клиентов

При нормальной работе оба сервера способны обслуживать клиентов. Для распределения запросов используется **load balancing** — согласованное решение о том, какой партнер должен ответить конкретному клиенту.

В конфигурации **primary** задается один из вариантов:

- `split 128;` — ориентировочное деление ответственности за новые запросы поровну (значение от 0 до 255);
- `hba ...;` — явная битовая карта распределения, более сложный вариант.

В типовой конфигурации достаточно `split 128`. На стороне `secondary` эту директиву не дублируют.

**Важно:** `split 128` **не означает**, что первому серверу навсегда принадлежит первая половина IP-диапазона, а второму — вторая. Это механизм выбора партнера для обслуживания запросов, а не разделение `range` на две непересекающиеся половины.

`load balance max seconds 3;` позволяет серверу при определенных условиях обслужить запрос, если ожидание клиента превысило заданный порог. Это не гарантия мгновенного переключения и не заменяет корректную настройку failover.

## 4. Состояния failover-партнеров

У каждого сервера есть локальное состояние и представление о состоянии партнера. На практике встречаются следующие состояния:

| Состояние | Значение |
|---|---|
| `normal` | Партнеры обмениваются состояниями и работают согласованно |
| `communications-interrupted` | Связь с партнером нарушена; действуют ограничения безопасной выдачи |
| `partner-down` | Администратор или механизм управления объявил партнера неработающим; это особый режим восстановления |
| `recover` | Узел восстанавливает сведения о состояниях аренд |
| `recover-done` | Восстановление данных завершено; ожидается согласованный переход |
| `startup` | Запуск и инициализация состояния |
| `shutdown` | Остановка участника |
| `paused` | Обслуживание приостановлено в рамках протокола |
| `potential-conflict` | Возможен конфликт состояний, требуется согласование |
| `resolution-interrupted` | Процесс разрешения конфликтов прерван |

**Критическое различие:** `communications-interrupted` и `partner-down` — не одно и то же. Потеря TCP-соединения сама по себе не дает администратору оснований считать другой сервер окончательно выключенным: возможен сетевой разрыв, при котором оба узла продолжают работать.

## 5. MCLT: почему восстановление не всегда мгновенное

**MCLT (Maximum Client Lead Time)** — максимальное время, на которое один партнер может опередить другого в предоставлении клиенту срока аренды без подтверждения обновления от партнера.

Пример:

```dhcpd
mclt 3600;
```

Значение — **3600 секунд (1 час)**. Оно задается на `primary` и влияет на безопасную работу при потере связи и на переходы между состояниями. Это **не** интервал проверки доступности второго сервера и **не** срок, через который клиент автоматически получает новый IP.

MCLT важно учитывать при планировании восстановления, особенно при ручном переводе в `partner-down` и последующем возвращении второго сервера. Не следует обещать, что через ровно один MCLT произойдет полное восстановление: фактические переходы зависят от текущих состояний и базы аренд.

## 6. Подготовка двух серверов

**Учебная топология:**

| Параметр | DHCP-1 | DHCP-2 |
|---|---|---|
| Роль | Primary | Secondary |
| IP | `10.10.0.10` | `10.10.0.11` |
| Клиентская сеть | `192.168.10.0/24` | `192.168.10.0/24` |
| Пул | `192.168.10.100–192.168.10.200` | тот же пул |
| Имя peer | `college-failover` | `college-failover` |
| Peer TCP-порт | `647` | `647` |

**Перед настройкой:**

1. Установить совместимые версии ISC DHCP Server на обоих узлах.
2. Назначить **постоянные** IP-адреса серверам.
3. Обеспечить связь между `10.10.0.10` и `10.10.0.11` по TCP 647.
4. Разрешить клиентские DHCP-запросы (или настроить DHCP Relay на оба адреса).
5. Синхронизировать время и согласовать конфигурации подсетей, пулов и опций.
6. Убедиться, что для одной и той же сети нет третьего неконтролируемого DHCP-сервера.

> Если серверы находятся в другой подсети, они не обязаны иметь интерфейс в `192.168.10.0/24`, но должны получать корректно пересылаемые DHCP Relay запросы. Для непосредственного обслуживания без Relay потребуется соответствующее сетевое подключение.

## 7. Конфигурация Primary

Пример `/etc/dhcp/dhcpd.conf` на **DHCP-1 (`10.10.0.10`)**:

```dhcpd
# Общие параметры
 authoritative;
 default-lease-time 3600;
 max-lease-time 7200;
 option domain-name "college.example";
 option domain-name-servers 192.168.10.10;

# Описание партнера (только Primary)
failover peer "college-failover" {
    primary;
    address 10.10.0.10;
    port 647;
    peer address 10.10.0.11;
    peer port 647;
    max-response-delay 60;
    max-unacked-updates 10;
    mclt 3600;
    split 128;
    load balance max seconds 3;
}

subnet 192.168.10.0 netmask 255.255.255.0 {
    option routers 192.168.10.1;
    option subnet-mask 255.255.255.0;

    pool {
        failover peer "college-failover";
        range 192.168.10.100 192.168.10.200;
    }
}
```

**Обратите внимание на два уровня:**

- `failover peer "college-failover" { ... }` **объявляет** партнерское соединение;
- `failover peer "college-failover";` **подключает** его к конкретному `pool`.

Само объявление пары не делает автоматически все пулы отказоустойчивыми. Динамический диапазон, участвующий в failover, должен быть в пуле, связанном с peer.

## 8. Конфигурация Secondary

Пример `/etc/dhcp/dhcpd.conf` на **DHCP-2 (`10.10.0.11`)**:

```dhcpd
 authoritative;
 default-lease-time 3600;
 max-lease-time 7200;
 option domain-name "college.example";
 option domain-name-servers 192.168.10.10;

failover peer "college-failover" {
    secondary;
    address 10.10.0.11;
    port 647;
    peer address 10.10.0.10;
    peer port 647;
    max-response-delay 60;
    max-unacked-updates 10;
    load balance max seconds 3;
}

subnet 192.168.10.0 netmask 255.255.255.0 {
    option routers 192.168.10.1;
    option subnet-mask 255.255.255.0;

    pool {
        failover peer "college-failover";
        range 192.168.10.100 192.168.10.200;
    }
}
```

На `secondary` **нет** директив `mclt` и `split`: они задаются на `primary`. Адреса в `address` и `peer address` меняются местами. Остальные настройки, определяющие поведение выдачи адресов, должны быть согласованы.

**Не путайте:** одинаковый `range` в двух конфигурациях здесь корректен **только потому, что оба пула включены в одну failover-пару**. Без failover такая конфигурация опасна.

## 9. Что делать с резервациями и другими пулами

### 9.1. Статические резервации

```dhcpd
host printer-01 {
    hardware ethernet 02:11:22:33:44:55;
    fixed-address 192.168.10.20;
}
```

Статические `host`-объявления и конфигурационные параметры **не реплицируются протоколом failover**. Их следует согласованно поддерживать на обоих серверах (например, через Ansible или Git). Фиксированные адреса должны находиться **вне динамического диапазона**.

### 9.2. Несколько VLAN

Для каждой подсети создается свой `subnet`, а внутри него — нужные `pool` с привязкой к тому же `failover peer`:

```dhcpd
subnet 192.168.20.0 netmask 255.255.255.0 {
    option routers 192.168.20.1;
    pool {
        failover peer "college-failover";
        range 192.168.20.100 192.168.20.200;
    }
}
```

Если у сети несколько пулов с разными правилами `allow`/`deny`, эти правила должны быть согласованы на обоих узлах. Конфигурация классов клиентов тоже должна совпадать.

## 10. Запуск и проверка

### 10.1. Проверка синтаксиса

На каждом сервере:

```bash
sudo dhcpd -t -4 -cf /etc/dhcp/dhcpd.conf
```

Команда проверяет синтаксис, но **не доказывает**, что партнеры успешно согласовали состояния.

### 10.2. Запуск службы

На Ubuntu с пакетом `isc-dhcp-server`:

```bash
sudo systemctl restart isc-dhcp-server
sudo systemctl status isc-dhcp-server --no-pager
```

Убедитесь, что в `/etc/default/isc-dhcp-server` задан нужный интерфейс (`INTERFACESv4`), через который сервер получает клиентские запросы или запросы Relay.

### 10.3. Проверка соединения партнеров

```bash
sudo ss -tnp | grep ':647'
sudo journalctl -u isc-dhcp-server -n 100 --no-pager
```

В журналах следует искать сообщения о соединении с peer и переходе в состояние `normal`. После запуска возможны промежуточные состояния восстановления; оценивать результат нужно по фактическим логам **обоих** серверов.

### 10.4. Просмотр базы аренд

```bash
sudo less /var/lib/dhcp/dhcpd.leases
```

В файле могут находиться записи `failover peer` с состояниями и временными отметками. Не редактируйте активную базу аренд вручную.

## 11. Отказ одного сервера: что происходит

**Сценарий:** DHCP-1 недоступен, DHCP-2 продолжает работать.

1. DHCP-2 замечает потерю соединения и переходит в `communications-interrupted`.
2. Он продолжает обслуживать запросы в рамках доступных ему состояний аренд и ограничений failover.
3. Возможности выдачи **новых** адресов могут быть ограничены, даже если часть диапазона кажется свободной.
4. После восстановления связи партнеры согласуют состояния и возвращаются к нормальной работе.

**Почему сервер не забирает сразу все IP?** Потому что обрыв TCP между серверами не доказывает остановку второго узла. Если оба сервера при сетевом разделении начнут бесконтрольно использовать весь пул, появится риск конфликтующих аренд.

### Ручное состояние `partner-down`

`partner-down` — административно значимый режим. Перевод в него допустим **только после достоверного подтверждения**, что партнер не продолжает обслуживать клиентов. При сетевом разделении («split-brain») перевод обоих узлов в `partner-down` опасен.

Не следует применять универсальную команду «принудительно сделать partner-down» без проверки версии, способа управления и состояния базы аренд. Восстановление после длительного отказа должно выполняться по документированной процедуре с резервной копией lease-файла.

## 12. Восстановление после отказа и типовые ошибки

### 12.1. Возврат партнера

Перед повторным запуском узла:

1. Проверить, что старый экземпляр `dhcpd` действительно остановлен.
2. Убедиться, что IP-адрес и конфигурация peer не изменились неожиданно.
3. Проверить целостность и наличие резервной копии `/var/lib/dhcp/dhcpd.leases`.
4. Запустить службу и наблюдать за согласованием состояний в журналах **обоих** серверов.
5. Проверить возврат в `normal`, а затем протестировать выдачу и продление адресов.

**Не удаляйте `dhcpd.leases` на работающей паре «для очистки»**: это не безопасный способ устранения рассинхронизации.

### 12.2. Частые проблемы

| Симптом | Вероятная причина | Что проверить |
|---|---|---|
| Серверы не соединяются | TCP 647 заблокирован, неверные `address`/`peer address` | `ss`, firewall, маршруты, логи |
| Запросы доходят только до одного узла | Relay пересылает на один адрес | `ip helper-address` / настройки DHCP Relay |
| Оба сервера запущены, но нет выдачи | Не привязан peer к `pool`, ошибка сети, отсутствие доступных аренд | `dhcpd.conf`, `dhcpd.leases`, журнал |
| Клиенты получают разные DNS/Router | Конфигурации не совпадают | Сравнить `option` на обоих узлах |
| После восстановления долго нет `normal` | Идет синхронизация/восстановление, ошибки состояния | Логи failover и состояние lease-файла |
| Возникают конфликты адресов | Независимый DHCP-сервер или ошибочный ручной failover | Найти все DHCP-ответы в сети |

### 12.3. Захват трафика

На сервере:

```bash
# Обмен между партнерами
sudo tcpdump -ni any 'tcp port 647'

# DHCP-запросы и ответы
sudo tcpdump -ni any 'udp port 67 or udp port 68'
```

При анализе DHCP Relay учитывайте адрес `giaddr` и маршрутизацию между Relay и серверами.

## 13. Рекомендации для production

- Использовать два независимых узла, разные физические хосты или разные зоны отказа.
- Указывать **оба** DHCP-сервера в конфигурации Relay.
- Согласованно распространять `dhcpd.conf`, `host`-резервации, классы и DHCP Options через систему управления конфигурациями.
- Мониторить доступность DHCP на клиентском уровне, TCP 647, состояние `normal`, число свободных аренд и ошибки журнала.
- Регулярно сохранять конфигурации и lease-файлы; отдельно проверять восстановление из резервных копий.
- Планировать поведение при сетевом разделении: **не** переводить оба сервера в `partner-down`.
- Учитывать, что `failover` ISC DHCP не заменяет отказоустойчивость маршрутизаторов, Relay, DNS и сети.
- Для новых проектов рассмотреть Kea DHCP с соответствующим механизмом High Availability; конфигурации ISC и Kea не взаимозаменяемы.

## 14. Глоссарий

| Термин | Определение |
|---|---|
| **DHCP Failover** | Согласованное обслуживание общего DHCPv4-пула двумя серверами |
| **Primary** | Первый участник failover-пары; задает ряд параметров распределения и MCLT |
| **Secondary** | Второй участник пары, который также может обслуживать клиентов |
| **Peer** | Партнер по протоколу failover |
| **Lease** | Запись об аренде IP-адреса клиентом |
| **Lease state** | Состояние отдельной аренды в базе DHCP |
| **Failover state** | Состояние взаимодействия серверов (`normal`, `communications-interrupted` и др.) |
| **MCLT** | Максимальное время опережения партнера при предоставлении аренды |
| **Load balancing** | Распределение обслуживания запросов между участниками |
| **`split`** | Параметр распределения запросов между партнерами |
| **`partner-down`** | Особое состояние, в котором партнер считается недоступным для обслуживания |
| **Split-brain** | Ситуация, когда оба узла действуют как независимые владельцы общих ресурсов |
| **DHCP Relay** | Устройство/функция пересылки DHCP-сообщений между сетями |
| **`dhcpd.leases`** | Файл, содержащий состояния аренд и служебные записи DHCP-сервера |

## Итоги — что было разобрано

- ISC DHCP Failover использует два **активных** DHCPv4-сервера с согласованными состояниями аренд.
- Партнеры связываются по TCP, а DHCP-клиенты взаимодействуют с серверами по UDP через локальную сеть или Relay.
- `split`, `mclt` и состояния протокола определяют безопасное поведение при нормальной работе и отказах.
- В каждом участвующем динамическом `pool` нужно указать `failover peer`.
- Конфигурация и резервации **не синхронизируются** самим протоколом failover.
- При отказе важны ограничения безопасной выдачи адресов; `partner-down` нельзя включать без подтверждения остановки партнера.
