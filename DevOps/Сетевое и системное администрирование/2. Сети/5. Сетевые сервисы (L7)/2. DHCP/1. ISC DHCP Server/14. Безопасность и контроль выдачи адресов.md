## 1. Модель угроз DHCP

DHCPv4 предназначен для автоматической настройки сети и **не аутентифицирует клиента или сервер криптографически**. Поэтому ограничения `dhcpd.conf` полезны для управления адресацией, но не заменяют защиту коммутаторов и контроль доступа на уровне сети.

Основные угрозы:

| Угроза | Что происходит | Основная защита |
|---|---|---|
| Rogue DHCP | Посторонний сервер предлагает неверные шлюз/DNS | DHCP Snooping на коммутаторах |
| DHCP Starvation | Злоумышленник расходует пул множеством запросов | Port Security, rate limiting, DHCP Snooping, сегментация |
| Подмена MAC / Client ID | Клиент выдает себя за зарегистрированное устройство | 802.1X/NAC; не считать MAC аутентификацией |
| Неавторизованная выдача | Любой клиент получает адрес из служебного пула | Классы, резервации, `deny unknown-clients` и L2-контроль |
| Подмена Option 82 | Клиент или недоверенный узел подставляет relay-информацию | Доверенные порты и проверка Option 82 на сетевом оборудовании |
| Утечка через логи | MAC, имена хостов и идентификаторы сохраняются в журналах | Ограничение доступа, сроки хранения, ротация |

## 2. Что реально контролирует ISC DHCP

ISC DHCP может выбирать, **какому клиенту предложить аренду**, из какого пула и с какими параметрами. Он не может запретить клиенту вручную установить IP, отправить поддельный MAC или принять ответ от другого DHCP-сервера.

Разделяйте:

- **Политику выдачи:** `host`, `class`, `subclass`, `pool`, `allow`/`deny`.
- **Сетевую защиту:** DHCP Snooping, 802.1X, ACL, изоляцию VLAN.
- **Защиту самого сервера:** firewall, минимальные права, обновления, мониторинг.

## 3. Известные и неизвестные клиенты

В ISC DHCP **known client** — клиент, сопоставленный с объявлением `host`. Это не означает «клиент из `subclass`» и не означает «клиент с ранее выданной арендой».

```dhcpd
host lab-pc01 {
    hardware ethernet 02:11:22:33:44:55;
    fixed-address 192.168.50.20;
}

subnet 192.168.50.0 netmask 255.255.255.0 {
    option routers 192.168.50.1;
    pool {
        deny unknown-clients;
        range 192.168.50.100 192.168.50.200;
    }
}
```

**Важный нюанс:** компьютер с фиксированным адресом из `host` получает его по правилам резервации; `deny unknown-clients` в динамическом `pool` регулирует выдачу из этого пула, а не является универсальным запретом всех DHCP-ответов. При проектировании проверяйте поведение отдельно для резерваций и динамических клиентов.

Указание `host` по MAC не подтверждает физическую личность компьютера: MAC подменяем.

## 4. Ограничение выдачи через классы

Для группы устройств можно использовать `class` и статические `subclass`:

```dhcpd
class "registered-lab" {
    match hardware;
}

subclass "registered-lab" 1:02:11:22:33:44:55;
subclass "registered-lab" 1:02:11:22:33:44:66;

subnet 192.168.50.0 netmask 255.255.255.0 {
    option routers 192.168.50.1;

    pool {
        allow members of "registered-lab";
        range 192.168.50.100 192.168.50.150;
    }

    pool {
        deny members of "registered-lab";
        range 192.168.50.151 192.168.50.200;
    }
}
```

`match hardware` извлекает тип оборудования и MAC. `subclass` задает разрешенные значения. Ограничения применяются к **выбору пула**, а не к возможности устройства отправлять DHCP-пакеты. Второй пул в примере доступен клиентам, не входящим в `registered-lab`, если другие правила не запрещают выдачу.

**Не путайте:** `allow members of` — проверка членства в классе; `allow known-clients` — проверка наличия подходящего `host`.

## 5. Политики allow/deny/ignore и область действия

В `dhcpd.conf` существуют правила разрешения/запрета для разных ситуаций. Их синтаксис и допустимое место зависят от конкретного правила: нельзя считать `allow`, `deny` и `ignore` универсальными переключателями для любых условий.

Часто применяются:

```dhcpd
pool {
    allow known-clients;
    range 192.168.50.100 192.168.50.150;
}
```

```dhcpd
pool {
    deny unknown-clients;
    range 192.168.50.151 192.168.50.200;
}
```

```dhcpd
pool {
    allow members of "registered-lab";
    range 192.168.50.201 192.168.50.220;
}
```

Проверяйте комбинации правил в тестовой среде: выбор пула также зависит от подсети, доступности адресов, существующих аренд и других условий. Не пытайтесь выражать сложную политику только через `deny unknown-clients`, если используются резервации.

## 6. Резервации: назначение и ограничения

`host` + `hardware ethernet` + `fixed-address` полезны для принтеров, серверов и управляемых рабочих станций:

```dhcpd
host printer-01 {
    hardware ethernet 02:aa:bb:cc:dd:01;
    fixed-address 192.168.50.30;
    option host-name "printer-01";
}
```

Резервация дает предсказуемую адресацию, но **не защищает от подмены MAC**. Для критичных устройств используйте отдельные VLAN и политики доступа на коммутаторе/межсетевом экране.

Избегайте пересечения зарезервированных адресов с динамическими диапазонами; фиксируйте их в IPAM.

## 7. DHCP Snooping: защита от поддельных серверов

DHCP Snooping — функция **управляемого коммутатора**, а не директива ISC DHCP.

Принцип:

1. Порты клиентов объявляются **untrusted**.
2. Порт к легитимному DHCP-серверу или DHCP Relay — **trusted**.
3. DHCP-ответы с недоверенных портов блокируются.
4. При поддержке оборудования формируется таблица привязок IP–MAC–VLAN–порт.

Типовой путь:

```text
[Клиент] -- untrusted -- [Коммутатор] -- trusted -- [DHCP Relay / DHCP Server]
```

Настройки различаются по производителю коммутатора. **Неверно назначенный trusted-порт** может разрешить rogue DHCP, а неверно назначенный untrusted — нарушить выдачу адресов. Проверяйте топологию, транки и relay.

Дополнительные механизмы, использующие таблицу Snooping: Dynamic ARP Inspection и IP Source Guard. Их поддержка зависит от оборудования.

## 8. Защита от исчерпания пула

DHCP Starvation — отправка множества запросов с различными идентификаторами с целью занять свободные адреса.

Практические меры:

- DHCP Snooping с ограничением скорости DHCP-пакетов на клиентских портах.
- Port Security и ограничения числа MAC-адресов, где это применимо.
- 802.1X/NAC для идентификации устройств.
- Разделение пользователей и инфраструктуры по VLAN.
- Мониторинг числа свободных аренд и аномального роста новых идентификаторов.

**Важно:** сокращение `default-lease-time` не устраняет атаку. Слишком короткая аренда может увеличить DHCP-трафик, а слишком длинная — задержать освобождение адресов.

## 9. DHCP Relay и Option 82

В распределенной сети DHCP Relay пересылает запросы между подсетями. Поле `giaddr` помогает серверу выбрать нужную сеть, а **Option 82** может передавать сведения о порте/сегменте подключения (`circuit-id`, `remote-id`).

Эти сведения пригодны для классификации и диагностики **только при доверенной цепочке передачи**. Если Option 82 может поступать непосредственно от недоверенного клиента, опираться на нее как на доказательство происхождения нельзя.

На коммутаторах настройте доверенные порты, вставку/проверку Option 82 и согласуйте ее обработку с DHCP Relay. Синтаксис классификации по Option 82 рассмотрен в заметках о классах и сложных топологиях.

## 10. Защита DHCP-сервера на Linux

### 10.1. Ограничение сетевой доступности

DHCPv4 использует UDP 67 (сервер) и UDP 68 (клиент). Если DHCP Relay находится в других VLAN, сервер должен принимать обращения от согласованных relay-узлов. Нельзя просто разрешить UDP 67 только от обычных клиентских IP: при начальном получении адреса клиент может использовать `0.0.0.0`.

Firewall проектируется **по реальной схеме интерфейсов и relay**, с учетом широковещательных запросов и ответов. Не применяйте примерные правила удаленно без проверки доступности сервиса.

### 10.2. Интерфейсы прослушивания

На Ubuntu с пакетом `isc-dhcp-server` интерфейсы IPv4 обычно задают в `/etc/default/isc-dhcp-server`:

```bash
INTERFACESv4="ens18"
```

Это уменьшает риск непреднамеренной выдачи адресов через другой интерфейс, но не заменяет сегментацию и firewall. Название интерфейса проверьте через `ip -br link`.

### 10.3. Доступ к файлам

```bash
sudo ls -l /etc/dhcp/dhcpd.conf
sudo ls -ld /var/lib/dhcp
sudo systemctl status isc-dhcp-server
```

Конфигурация может содержать ключи TSIG, адреса инфраструктуры и сведения о клиентах. Ограничьте доступ к файлам с секретами и резервным копиям. Не записывайте секреты в общедоступные журналы.

### 10.4. Поддержка продукта

ISC DHCP является **End of Life**. Для действующей системы особенно важны сетевые ограничения, инвентаризация зависимостей и план миграции на поддерживаемый DHCP-сервер, например Kea. Смена сервера сама по себе не решает проблемы rogue DHCP и MAC spoofing.

## 11. Логирование, аудит и мониторинг

Примеры команд для Ubuntu:

```bash
sudo journalctl -u isc-dhcp-server --since "1 hour ago"
sudo systemctl status isc-dhcp-server
sudo ss -lunp | grep ':67'
sudo tcpdump -ni ens18 -vv 'udp port 67 or udp port 68'
```

Проверка синтаксиса IPv4-конфигурации:

```bash
sudo dhcpd -4 -t -cf /etc/dhcp/dhcpd.conf
```

Что отслеживать:

- долю занятых адресов по каждому пулу;
- резкий рост числа новых MAC/Client ID;
- сообщения об отсутствии свободных аренд;
- повторяющиеся запросы и конфликты адресов;
- неожиданные DHCP Offer/Ack от посторонних серверов;
- доступность сервиса и ошибки чтения базы аренд.

`tcpdump` показывает трафик, доступный интерфейсу захвата: для поиска rogue DHCP в другом VLAN может потребоваться зеркалирование порта или захват на соответствующем коммутаторе.

## 12. Полный пример контролируемой выдачи адресов

Сценарий: одна подсеть `192.168.50.0/24`, управляемые компьютеры получают динамические адреса из выделенного диапазона, принтер имеет резервацию, остальные клиенты — из отдельного диапазона. Это **сегментация адресации, а не полноценная аутентификация**.

```dhcpd
# /etc/dhcp/dhcpd.conf

authoritative;
log-facility local7;

default-lease-time 3600;
max-lease-time 7200;

option domain-name "lab.example";
option domain-name-servers 192.168.50.10;

class "registered-lab" {
    match hardware;
}

subclass "registered-lab" 1:02:11:22:33:44:55;
subclass "registered-lab" 1:02:11:22:33:44:66;

host printer-01 {
    hardware ethernet 02:aa:bb:cc:dd:01;
    fixed-address 192.168.50.30;
}

subnet 192.168.50.0 netmask 255.255.255.0 {
    option subnet-mask 255.255.255.0;
    option routers 192.168.50.1;

    pool {
        allow members of "registered-lab";
        range 192.168.50.100 192.168.50.150;
    }

    pool {
        deny members of "registered-lab";
        range 192.168.50.151 192.168.50.200;
    }
}
```

**Разбор:**

1. `class` извлекает аппаратный идентификатор.
2. `subclass` перечисляет два зарегистрированных устройства.
3. Первый пул доступен членам класса.
4. Второй пул предназначен для остальных клиентов.
5. Принтер получает фиксированный адрес по `host` вне динамических диапазонов.
6. Для реального ограничения доступа к сети дополнительно необходимы 802.1X/NAC, DHCP Snooping и ACL.

Перед применением:

```bash
sudo dhcpd -4 -t -cf /etc/dhcp/dhcpd.conf
sudo systemctl restart isc-dhcp-server
sudo journalctl -u isc-dhcp-server -n 50 --no-pager
```

Не перезапускайте production DHCP без резервной копии и окна обслуживания: синтаксическая проверка не доказывает правильность всей политики выдачи.

## 13. Типичные ошибки и заблуждения

| Ошибка | Почему это проблема | Как правильно |
|---|---|---|
| «`deny unknown-clients` блокирует посторонние устройства в сети» | Ограничивает DHCP-выдачу в заданной области, но не сетевую связность | Использовать 802.1X, ACL, VLAN |
| «`subclass` подтверждает личность компьютера» | Проверяемые идентификаторы можно подделать | Считать это политикой адресации |
| «Резервация предотвращает конфликт IP» | Другой узел может вручную назначить тот же адрес | Сегментация, мониторинг, IPAM |
| «Достаточно закрыть UDP 67 на клиентах» | Может нарушить нормальную работу DHCP | Настроить доверенные порты и Relay |
| «Два DHCP-сервера с одним пулом надежнее» | Независимые серверы могут выдать одинаковые адреса | Использовать согласованный Failover |
| «Option 82 всегда достоверна» | Достоверность зависит от сети и доверенных портов | Контролировать источник Option 82 |

## 14. Глоссарий

- **Rogue DHCP Server** — несанкционированный DHCP-сервер, отправляющий клиентам параметры сети.
- **DHCP Starvation** — исчерпание пула адресов из-за большого числа запросов.
- **DHCP Snooping** — механизм коммутатора, фильтрующий DHCP-сообщения и контролирующий доверенные порты.
- **Trusted Port** — порт, через который разрешено принимать серверные DHCP-сообщения.
- **Untrusted Port** — порт, на котором серверные DHCP-сообщения ограничиваются или блокируются.
- **Known Client** — клиент, сопоставленный с `host`-объявлением ISC DHCP.
- **Unknown Client** — клиент, для которого сервер не нашел подходящее `host`-объявление.
- **Reservation** — правило назначения определенного IP-адреса конкретному идентификатору клиента.
- **Client Class** — категория клиентов, определяемая правилами ISC DHCP.
- **Subclass** — зарегистрированное значение ключа сопоставления внутри класса.
- **Option 82** — дополнительная информация DHCP Relay о подключении клиента.
- **802.1X** — стандарт контроля доступа к сети на основе аутентификации.
- **NAC** — система управления допуском устройств к сети.
- **Dynamic ARP Inspection** — проверка ARP-пакетов с использованием доверенных привязок.
- **IP Source Guard** — ограничение IP-трафика на порту по допустимым IP/MAC-привязкам.
- **MAC Spoofing** — подмена аппаратного адреса сетевого интерфейса.
- **IPAM** — учет и управление IP-адресным пространством.
- **Lease** — аренда IP-адреса, назначенная DHCP-сервером на определенный срок.

## Итоги — что было разобрано

- DHCP-политики на сервере управляют выдачей адресов, но не обеспечивают надежную идентификацию клиентов.
- `host`, `class`, `subclass`, `pool`, `allow` и `deny` позволяют сегментировать адресацию.
- DHCP Snooping, 802.1X, ACL и VLAN обеспечивают защиту на сетевом уровне.
- Сервер нужно ограничивать по интерфейсам, защищать его конфигурацию и регулярно анализировать аренды и журналы.
- ISC DHCP больше не поддерживается; существующим инсталляциям нужен план миграции.
