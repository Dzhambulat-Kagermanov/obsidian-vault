## 1. Назначение классификации клиентов

**Класс DHCP-клиентов (`class`)** — именованная группа устройств, определяемая по признакам в DHCP-запросе или по явному правилу. Классификация позволяет **выдавать разным клиентам разные параметры** и **ограничивать доступ к определенным пулам адресов**.

Типовые задачи:

- выдавать разные загрузочные файлы BIOS- и UEFI-клиентам;
- выделять отдельный диапазон адресов устройствам определенного типа;
- передавать специализированные DHCP Options определенным устройствам;
- ограничивать количество активных аренд для динамически формируемых подклассов.

Класс **не создает отдельную подсеть или VLAN**. Он управляет обработкой DHCP-запроса внутри уже описанной сетевой топологии.

## 2. Место `class` в конфигурации

Классы обычно объявляются на глобальном уровне `dhcpd.conf`; внутри них размещаются условия сопоставления и параметры, применимые к участникам класса. Внутри `pool` задаются правила допуска к адресам.

```dhcpd
class "lab-clients" {
    match if option vendor-class-identifier = "LAB-CLIENT";
    option domain-name "lab.example.internal";
}

subnet 192.168.50.0 netmask 255.255.255.0 {
    option routers 192.168.50.1;

    pool {
        allow members of "lab-clients";
        range 192.168.50.100 192.168.50.150;
    }
}
```

В этом примере только участники `lab-clients` могут получить **новую динамическую аренду из указанного пула**. Параметр `option domain-name` задан для класса. Правила разрешения параметров из нескольких областей подробнее разобраны в [[Synced/DevOps/Сетевое и системное администрирование/2. Сети/5. Сетевые сервисы (L7)/2. DHCP/1. ISC DHCP Server/3. Структура dhcpd.conf, области действия и наследование.md|Структура dhcpd.conf, области действия и наследование]].

> [!warning] Важное ограничение
> DHCP-клиент может подделать большинство передаваемых им идентификаторов. Классы и `allow members of` **не являются надежной аутентификацией устройства** и не заменяют контроль доступа на коммутаторе.

## 3. `match if` — проверка условия

`match if` включает клиента в класс, когда логическое выражение истинно.

```dhcpd
class "pxe-clients" {
    match if substring(option vendor-class-identifier, 0, 9) = "PXEClient";
}
```

- `option vendor-class-identifier` — содержимое DHCP Option 60, отправленное клиентом;
- `substring(..., 0, 9)` — первые девять байт значения;
- `= "PXEClient"` — сравнение с ожидаемым префиксом.

Сравнение полного значения через `=` подходит только тогда, когда формат идентификатора известен полностью. Для PXE Option 60 часто содержит дополнительные данные после префикса `PXEClient`, поэтому здесь применяется `substring`.

Другой пример — классификация по DHCP Client Identifier:

```dhcpd
class "special-clients" {
    match if substring(option dhcp-client-identifier, 1, 3) = "LAB";
}
```

Смещение `1` пропускает первый байт идентификатора. Такой формат допустим только если структура Client Identifier действительно известна; универсальным правилом для всех клиентов его считать нельзя.

> [!important] Порядок вычисления
> Классификация выполняется **до исполнения обычных операторов конфигурации**. Нельзя надежно использовать в `match if` значение, которое сначала создается оператором `set` при обработке того же запроса. Условия должны опираться на доступные данные пакета.

## 4. `match` и `subclass` — сопоставление с перечнем значений

Когда требуется классифицировать большое число известных идентификаторов, удобно использовать родительский класс и подклассы.

```dhcpd
class "managed-devices" {
    match pick-first-value(option dhcp-client-identifier, hardware);
}

subclass "managed-devices" 1:00:11:22:33:44:55;
subclass "managed-devices" 1:00:11:22:33:44:66;

subnet 192.168.50.0 netmask 255.255.255.0 {
    pool {
        allow members of "managed-devices";
        range 192.168.50.20 192.168.50.80;
    }
}
```

`match` вычисляет значение, по которому ISC DHCP ищет совпадение среди объявленных `subclass`. В данном примере при отсутствии Option 61 используется `hardware`. Значения `1:00:...` приведены как **пример Ethernet hardware-идентификатора**, но реальный формат зависит от данных клиента. Если клиент присылает Option 61, сопоставляться будет именно его значение; оно не обязательно совпадает с MAC-адресом.

**Отличие от `match if`:** `match if` непосредственно проверяет логическое условие, а `match` формирует ключ для поиска подкласса. Такой поиск эффективен при большом количестве фиксированных значений.

Подкласс может также содержать собственные параметры:

```dhcpd
subclass "managed-devices" 1:00:11:22:33:44:77 {
    option host-name "device-77";
}
```

## 5. `spawn with` — автоматическое создание подклассов

`spawn with` создает подклассы динамически по значению из DHCP-пакета. Типичный источник — `agent.circuit-id`, передаваемый DHCP Relay в Option 82.

```dhcpd
class "access-circuits" {
    spawn with option agent.circuit-id;
    lease limit 4;
}
```

Для каждого нового Circuit ID сервер может создать отдельный подкласс; он сохраняется в базе аренд `dhcpd.leases`. `lease limit 4` ограничивает количество одновременных аренд **на подкласс**, а не на весь родительский класс.

Это удобно, например, когда один порт или клиентская точка подключения должны получать не более четырех адресов.

`spawn with` не нужно применять там, где достаточно простого статического условия `match if`: динамические подклассы увеличивают сложность учета состояния.

## 6. Управление доступом к пулам: `allow` и `deny`

Внутри `pool` правила определяют, **каким клиентам разрешено получать адреса именно из этого пула**.

```dhcpd
class "printers" {
    match if option vendor-class-identifier = "EXAMPLE-PRINTER";
}

subnet 192.168.50.0 netmask 255.255.255.0 {
    pool {
        allow members of "printers";
        range 192.168.50.30 192.168.50.49;
    }

    pool {
        deny members of "printers";
        range 192.168.50.100 192.168.50.199;
    }
}
```

| Правило | Значение |
|---|---|
| `allow members of "name";` | Допускает участников класса к пулу |
| `deny members of "name";` | Исключает участников класса из пула |
| `allow known-clients;` | Допускает клиентов, имеющих `host`-объявление |
| `deny unknown-clients;` | Не допускает клиентов без `host`-объявления |
| `deny all clients;` | Закрывает пул для всех клиентов |

**Known client** в терминологии ISC DHCP — клиент, имеющий соответствующее объявление `host`; это не означает, что клиент прошел криптографическую проверку личности.

> [!note] Несколько пулов
> Если клиент допущен к нескольким пулам, наличие класса само по себе не гарантирует конкретный IP-адрес. На выдачу влияют существующая аренда, доступность адресов и алгоритм выбора сервера. Не следует предполагать, что адреса выдаются строго по возрастанию.

## 7. Сочетание `match if` и `spawn with`

Условие `match if` может сначала отобрать нужную категорию клиентов, а `spawn with` — создать внутри нее подклассы.

```dhcpd
class "managed-access" {
    match if option vendor-class-identifier = "LAB-CLIENT";
    spawn with option agent.circuit-id;
    lease limit 2;
}
```

Логика:

1. Проверяется Option 60.
2. Если условие истинно, извлекается Circuit ID.
3. По Circuit ID находится либо создается подкласс.
4. Для подкласса применяется ограничение на число аренд.

Это позволяет устанавливать отдельный лимит на каждую точку подключения **внутри выбранной категории клиентов**.

## 8. Условные параметры через `if` и `elsif`

Не каждое различие между клиентами требует отдельного класса. Если нужно выбрать значение одной или нескольких опций, можно использовать условные операторы.

```dhcpd
if substring(option vendor-class-identifier, 0, 9) = "PXEClient" {
    next-server 192.168.50.10;
    filename "pxelinux.0";
} else {
    option domain-name "example.internal";
}
```

Этот пример иллюстрирует синтаксис, **но не является универсальной production-настройкой PXE**: BIOS и UEFI обычно требуют разных загрузчиков, а для их различения используют дополнительные признаки, например Option 93.

Практическое различие:

- `class` удобно использовать, когда группа клиентов участвует в нескольких правилах, особенно в допуске к пулам;
- `if` удобно использовать для локального условного выбора параметров.

Детальная работа выражений вынесена в следующую заметку, а PXE — в отдельную профильную заметку.

## 9. Пересечение классов и приоритет параметров

Один клиент может одновременно соответствовать нескольким классам. Например, он может быть и PXE-клиентом, и устройством из группы `managed-devices`.

Это создает два разных вопроса:

1. **Выбор пула:** разрешено ли клиенту получить аренду из конкретного `pool`?
2. **Выбор параметров:** какое значение DHCP Option будет отправлено, если оно определено в нескольких применимых областях?

Эти задачи не тождественны. При пересечении классов нельзя считать порядок строк в `dhcpd.conf` универсальным механизмом приоритета. Для предсказуемой конфигурации избегают конфликтующих назначений одной опции в пересекающихся классах и проверяют фактический ответ сервера.

## 10. Проверка и диагностика

Проверка синтаксиса конфигурации:

```bash
sudo dhcpd -t -4 -cf /etc/dhcp/dhcpd.conf
```

Проверка журнала службы:

```bash
sudo journalctl -u isc-dhcp-server -n 100 --no-pager
```

Просмотр DHCP-пакетов на интерфейсе сервера:

```bash
sudo tcpdump -ni enp1s0 -vvv 'udp port 67 or udp port 68'
```

Здесь `enp1s0` — имя интерфейса в примере; его нужно заменить на фактический интерфейс DHCP-сервера.

Для диагностики классов сопоставляют **поля входящего DHCP-пакета** (Option 60, 61, 82, 93) с выражениями `match`/`match if`, затем проверяют, какой пул допускает клиента. `dhcpd -t` подтверждает синтаксис, но **не доказывает правильность логики классификации**.

## 11. Глоссарий

| Термин | Определение |
|---|---|
| `class` | Именованная категория DHCP-клиентов |
| `match if` | Условие включения клиента в класс |
| `match` | Выражение, формирующее ключ поиска подкласса |
| `subclass` | Подгруппа класса, сопоставляемая с определенным значением |
| `spawn with` | Динамическое создание подклассов по значению из запроса |
| `lease limit` | Максимальное число одновременных аренд для соответствующего класса/подкласса в поддерживаемом контексте |
| `allow members of` | Разрешение участникам класса получать адреса из пула |
| `deny members of` | Запрет участникам класса получать адреса из пула |
| `known-clients` | Клиенты, имеющие соответствующие объявления `host` |
| Vendor Class Identifier | DHCP Option 60 — идентификатор типа или производителя клиента |
| Client Identifier | DHCP Option 61 — идентификатор клиента |
| Circuit ID | Подопция Option 82, идентифицирующая точку подключения в сети Relay |

## Итоги — что было разобрано

- `class` группирует клиентов по данным DHCP-запроса; группа может влиять на параметры и доступ к пулам.
- `match if` проверяет логическое условие, а `match` совместно с `subclass` сопоставляет ключ со списком значений.
- `spawn with` автоматически формирует подклассы, например по Circuit ID.
- `allow` и `deny` внутри `pool` регулируют выдачу адресов; это не полноценная аутентификация устройств.
- Для надежной эксплуатации важно отдельно проверять классификацию, выбор пула и фактически отправленные параметры.
