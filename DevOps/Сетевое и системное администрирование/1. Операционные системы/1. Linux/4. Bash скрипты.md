## Введение

Bash-скриптинг — это **основной инструмент автоматизации** для DevOps-инженера в Linux-среде. ## 1. Основы Bash-скриптов: структура и выполнение

### Shebang и интерпретатор

Первая строка скрипта определяет, какой интерпретатор будет его выполнять:

```
#!/bin/bash
# Или более переносимый вариант:
#!/usr/bin/env bash
```

| Shebang               | Когда использовать                                                           |
| --------------------- | ---------------------------------------------------------------------------- |
| `#!/bin/bash`         | Когда нужен конкретный bash (например, используются bash-специфичные фичи)   |
| `#!/usr/bin/env bash` | Для переносимости: использует bash из PATH, полезно в виртуальных окружениях |
| `#!/bin/sh`           | Для POSIX-совместимых скриптов (работает на любых Unix-системах)             |

>[!WARNING] Распространенная ошибка
>Не используйте `#!/bin/sh`, если скрипт содержит bash-специфичный синтаксис (`[[`, массивы, `[[ $var == pattern ]]`). На системах, где `/bin/sh` → `dash`, такой скрипт упадет с ошибкой.

### Создание и запуск скрипта

```bash
# Создание файла
nano deploy.sh

# Добавление shebang и кода
# ...

# Сделать исполняемым
chmod +x deploy.sh

# Запуск
./deploy.sh           # относительно текущего пути
/path/to/deploy.sh    # абсолютный путь
bash deploy.sh        # явный вызов интерпретатора (без +x)

# Аргументы скрипта
./deploy.sh production --dry-run
# $1 = production, $2 = --dry-run
```

### Структура надежного скрипта

```bash
#!/usr/bin/env bash
set -euo pipefail  # Строгий режим (см. ниже)

# === Конфигурация ===
readonly SCRIPT_NAME="$(basename "$0")"
readonly SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
readonly LOG_FILE="/var/log/${SCRIPT_NAME}.log"

# === Функции ===
log() {
    echo "[$(date '+%F %T')] $*" | tee -a "$LOG_FILE"
}

usage() {
    cat <<EOF
Использование: $SCRIPT_NAME [OPTIONS] <environment>

Аргументы:
  environment    Целевое окружение: staging, production

Опции:
  -d, --dry-run  Не вносить изменения, только показать план
  -h, --help     Показать эту справку

Пример:
  $SCRIPT_NAME --dry-run production
EOF
    exit 0
}

# === Парсинг аргументов ===
DRY_RUN=false
while [[ $# -gt 0 ]]; do
    case "$1" in
        -d|--dry-run)
            DRY_RUN=true
            shift
            ;;
        -h|--help)
            usage
            ;;
        -*)
            echo "Неизвестная опция: $1" >&2
            usage
            ;;
        *)
            ENVIRONMENT="$1"
            shift
            ;;
    esac
done

# === Валидация ===
if [[ -z "${ENVIRONMENT:-}" ]]; then
    echo "ERROR: Требуется указать окружение" >&2
    usage
fi

# === Основная логика ===
main() {
    log "Запуск деплоя в $ENVIRONMENT (dry-run: $DRY_RUN)"
    
    if [[ "$DRY_RUN" == true ]]; then
        log "[DRY-RUN] Пропускаем изменения"
        return 0
    fi
    
    # ... реальные действия ...
    log "✅ Деплой завершен"
}

# === Точка входа ===
main "$@"
```

>[!TIP] Почему такая структура?
>- `set -euo pipefail` ловит ошибки на ранней стадии
>- Функции делают код переиспользуемым и тестируемым
>- Явный парсинг аргументов упрощает документирование и использование
>- Логирование через `tee` сохраняет историю и показывает вывод в реальном времени

## 2. Строгий режим: set -euo pipefail

### Компоненты строгого режима

```bash
set -e  # Exit immediately on error (выход при любой ошибке)
set -u  # Treat unset variables as error (ошибка при использовании неопределенной переменной)
set -o pipefail  # Return value of pipeline is the status of the last command to exit with a non-zero status
```

### Практическое значение

```bash
# Без set -e: скрипт продолжит выполнение после ошибки
false
echo "Эта строка выполнится"  # ❌ Нежелательно в production-скриптах

# С set -e: скрипт остановится
set -e
false
echo "Эта строка НЕ выполнится"  # ✅ Скрипт завершится с ошибкой после false

# Без pipefail: ошибка в начале пайплайна игнорируется
set -e
false | true  # Выходной код = 0 (успех), потому что последняя команда true
# ❌ Ошибка в false потеряна

# С pipefail: ошибка в любой части пайплайна будет обнаружена
set -euo pipefail
false | true  # Выходной код = 1 (ошибка от false)
# ✅ Скрипт завершится с ошибкой
```

### Когда отключать строгий режим локально

```bash
# Допустимые сценарии для временного отключения
set +e  # Позволить команде завершиться с ошибкой
if ! grep -q "pattern" file.txt; then
    log "Pattern not found, continuing..."
fi
set -e  # Вернуть строгий режим

# Или использовать условное выполнение
grep -q "pattern" file.txt || log "Pattern not found"
```

>[!WARNING] Опасности set -e
>- В конструкциях `if command; then ...` ошибка команды НЕ прервет скрипт — это ожидаемое поведение
>- В подстановках команд `$(cmd)` ошибка может не прервать скрипт в старых версиях bash
>- Всегда тестируйте скрипты с `set -euo pipefail` перед использованием в production

## 3. Переменные и подстановки

### Типы переменных

```bash
# Простое присваивание
NAME="production"
PORT=8080

# Чтение из окружения с дефолтом
DB_HOST="${DB_HOST:-localhost}"
DB_PORT="${DB_PORT:-5432}"

# Только для чтения (защита от случайного изменения)
readonly CONFIG_FILE="/etc/app/config.yaml"

# Специальные переменные
$0    # Имя скрипта
$#    # Количество аргументов
$@    # Все аргументы как отдельные слова
$*    # Все аргументы как одно слово
$?    # Код выхода последней команды
$$    # PID текущего процесса
$!    # PID последнего фонового процесса
```

### Подстановки и расширения

```bash
# Командная подстановка
CURRENT_DATE=$(date +%F)
# Или старый синтаксис (менее читаемый):
CURRENT_DATE=`date +%F`

# Арифметические операции
COUNT=5
((COUNT++))
RESULT=$((COUNT * 2 + 1))

# Подстановка параметров (parameter expansion)
FILE="/path/to/archive.tar.gz"

${FILE%.gz}      # Удалить суффикс: /path/to/archive.tar
${FILE##*/}      # Удалить префикс до последнего /: archive.tar.gz
${FILE//tar/zip} # Заменить все вхождения: /path/to/archive.zip.gz

# Проверка и дефолтные значения
echo "${VAR:-default}"   # Если VAR не задан или пуст, использовать default
echo "${VAR:=default}"   # Если VAR не задан, присвоить default и использовать
echo "${VAR:?error msg}" # Если VAR не задан, вывести ошибку и выйти

# Длина строки
NAME="hello"
echo "${#NAME}"  # 5
```

### Массивы в Bash

```bash
# Объявление и инициализация
SERVERS=("web1" "web2" "web3")
declare -a PORTS=(80 443 8080)

# Доступ к элементам

echo "${SERVERS[@]}"     # все элементы как отдельные слова
echo "${#SERVERS[@]}"    # количество элементов

# Итерация
for server in "${SERVERS[@]}"; do
    echo "Processing $server"
done

# Ассоциативные массивы (требует Bash 4+)
declare -A CONFIG
CONFIG[host]="localhost"
CONFIG[port]=5432

echo "${CONFIG[host]}"  # localhost

# Итерация по ключам
for key in "${!CONFIG[@]}"; do
    echo "$key = ${CONFIG[$key]}"
done
```

## 4. Условия и циклы

### Условные конструкции

```bash
# Простое if-else
if [[ -f "/etc/nginx/nginx.conf" ]]; then
    log "Config exists"
else
    log "Config missing" >&2
    exit 1
fi

# Проверка нескольких условий
if [[ "$ENV" == "production" && "$DRY_RUN" == false ]]; then
    confirm_deployment
elif [[ "$ENV" == "staging" ]]; then
    log "Deploying to staging..."
else
    log "Unknown environment: $ENV" >&2
    exit 1
fi

# Case для множественного выбора
case "$COMMAND" in
    start|stop|restart)
        systemctl "$COMMAND" nginx
        ;;
    status)
        systemctl is-active nginx
        ;;
    *)
        echo "Unknown command: $COMMAND" >&2
        exit 1
        ;;
esac
```

### Тестирование файлов и строк

```bash
# Файловые тесты
[[ -e /path ]]      # Существует (файл или директория)
[[ -f /path ]]      # Обычный файл
[[ -d /path ]]      # Директория
[[ -L /path ]]      # Символическая ссылка
[[ -r /path ]]      # Читаемый
[[ -w /path ]]      # Записываемый
[[ -x /path ]]      # Исполняемый
[[ -s /path ]]      # Не пустой
[[ file1 -nt file2 ]] # file1 новее file1
[[ file1 -ot file2 ]] # file1 старше file2

# Строковые тесты
[[ -z "$VAR" ]]     # Пустая строка
[[ -n "$VAR" ]]     # Не пустая строка
[[ "$A" == "$B" ]]  # Равенство (используйте == в [[ ]])
[[ "$VAR" =~ ^[0-9]+$ ]] # Регулярное выражение

# Числовые сравнения (в (( )) или [[ ]])
(( COUNT > 10 ))
[[ $PORT -ge 1024 ]]
```

### Циклы

```bash
# For по списку
for env in staging production; do
    deploy_to "$env"
done

# For по выводу команды
for pod in $(kubectl get pods -l app=myapp -o name); do
    kubectl logs "$pod"
done

# While с условием
RETRY=0
MAX_RETRIES=5
while [[ $RETRY -lt $MAX_RETRIES ]]; do
    if curl -sf http://api/health; then
        break
    fi
    ((RETRY++))
    sleep 2
done

# While read для обработки построчно
while IFS= read -r line; do
    process_line "$line"
done < input.txt

# Until (выполнять, пока условие ложно)
until ping -c1 database > /dev/null 2>&1; do
    log "Waiting for database..."
    sleep 5
done
```

>[!TIP] Безопасная итерация по файлам
>Избегайте `for file in $(find ...)` — сломается на пробелах в именах. Используйте:
>```bash
>while IFS= read -r -d '' file; do
  >  process "$file"
>done < <(find /path -name "*.log" -print0)
>```

## 5. Функции и область видимости

### Объявление и вызов функций

```bash
# Базовый синтаксис
my_function() {
    local arg1="$1"  # local ограничивает переменную областью функции
    echo "Processing: $arg1"
}

# Вызов
my_function "value"

# Возврат значения
check_service() {
    if systemctl is-active --quiet "$1"; then
        return 0  # успех
    else
        return 1  # ошибка
    fi
}

if check_service nginx; then
    log "Nginx is running"
else
    log "Nginx is down" >&2
fi
```

### Область видимости переменных

```bash
GLOBAL_VAR="visible everywhere"

scoped_function() {
    local LOCAL_VAR="only in function"
    GLOBAL_VAR="changed globally"  # Изменяет глобальную переменную
    echo "Inside: $LOCAL_VAR, $GLOBAL_VAR"
}

scoped_function
echo "Outside: $GLOBAL_VAR"  # "changed globally"
echo "Outside: $LOCAL_VAR"   # Пусто (не определена)
```

## 6. Обработка ошибок и сигналов

### Trap для обработки сигналов

```bash
# Очистка временных файлов при выходе
TEMP_FILE=$(mktemp)
trap 'rm -f "$TEMP_FILE"' EXIT

# Обработка прерывания пользователем (Ctrl+C)
cleanup() {
    log "Received interrupt, cleaning up..."
    # Очистка ресурсов
    exit 130  # Стандартный код для SIGINT
}
trap cleanup SIGINT SIGTERM

# Игнорирование сигнала (осторожно!)
trap '' SIGPIPE  # Игнорировать SIGPIPE (когда pipe закрывается)
```

### Логирование и отладка

```bash
# Базовое логирование с уровнями
log() {
    local level="$1"
    shift
    echo "[$(date '+%F %T')] [$level] $*" >&2
}

log INFO "Starting deployment"
log ERROR "Failed to connect to database"

# Отладочный режим
DEBUG="${DEBUG:-false}"
debug() {
    [[ "$DEBUG" == true ]] && echo "[DEBUG] $*" >&2
}

# Включение отладки bash
set -x  # Выводить каждую команду перед выполнением
# ... код ...
set +x  # Отключить

# Или условно:
if [[ "$DEBUG" == true ]]; then
    set -x
fi
```

### Retry-логика для нестабильных операций

```bash
retry() {
    local retries="$1"
    local delay="$2"
    shift 2
    local attempt=1
    
    while [[ $attempt -le $retries ]]; do
        if "$@"; then
            return 0
        else
            log "Attempt $attempt/$retries failed, retrying in ${delay}s..."
            sleep "$delay"
            ((attempt++))
        fi
    done
    
    log "ERROR: Command failed after $retries attempts" >&2
    return 1
}

# Использование
retry 5 10 curl -sf --connect-timeout 5 https://api.example.com/health
```

## 7. Работа с внешними командами и пайплайнами

### Проверка доступности утилит

```bash
# Проверка наличия команды
if ! command -v jq &> /dev/null; then
    echo "ERROR: jq is required but not installed" >&2
    exit 127
fi

# Или через hash (быстрее, но менее переносимо)
if ! hash kubectl 2>/dev/null; then
    echo "kubectl not found" >&2
    exit 1
fi
```

### Безопасное выполнение внешних команд

```bash
# Экранирование аргументов (избегать инъекций)
USER_INPUT="$1"
# ❌ Опасно: eval "ls $USER_INPUT"
# ✅ Безопасно:
ls -- "$USER_INPUT"  # -- завершает опции, дальше только аргументы

# Использование массивов для аргументов
CMD=(curl -sf --connect-timeout 10)
URL="https://api.example.com/data"
"${CMD[@]}" "$URL"  # Правильное разделение аргументов

# Обработка вывода с сохранением кода выхода
output=$(my_command 2>&1) || {
    exit_code=$?
    log "Command failed with code $exit_code: $output" >&2
    exit $exit_code
}
```

### Парсинг структурированного вывода

```bash
# Парсинг JSON через jq
get_pod_status() {
    local pod_name="$1"
    kubectl get pod "$pod_name" -o json | jq -r '.status.phase'
}

# Парсинг ключ=значение вывода
parse_env_file() {
    while IFS='=' read -r key value; do
        [[ "$key" =~ ^#.*$ ]] && continue  # Пропустить комментарии
        [[ -z "$key" ]] && continue         # Пропустить пустые строки
        export "$key=$value"
    done < "$1"
}

# Парсинг таблиц (awk)
get_active_connections() {
    ss -tunap | awk 'NR>1 && $1=="tcp" {print $5}' | cut -d: -f1 | sort -u
}
```

>[!TIP] Предпочитайте структурированные форматы
>Когда возможно, используйте `-o json` или `-o yaml` в утилитах (kubectl, docker, aws-cli) вместо парсинга человекочитаемого вывода — это надежнее при изменениях версий CLI.

```bash
# ❌ Опасно: инъекция через неэкранированные переменные
rm -rf /tmp/$USER_INPUT  # Если USER_INPUT="../../etc", будет катастрофа

# ✅ Безопасно: всегда кавычки и --
rm -rf -- "$USER_INPUT"

# ❌ Опасно: eval с пользовательским вводом
eval "command $USER_INPUT"  # Позволяет выполнить произвольный код

# ✅ Безопасно: использовать массивы или прямое выполнение
CMD=(command)
"${CMD[@]}" "$USER_INPUT"

# ❌ Опасно: предсказуемые временные файлы
TMP="/tmp/myapp_$$.tmp"  # $$ можно угадать, race condition

# ✅ Безопасно: mktemp
TMP=$(mktemp /tmp/myapp.XXXXXX) || exit 1
```

## 10. Практические шаблоны скриптов для DevOps

### Шаблон: Health-check сервиса

```bash
#!/usr/bin/env bash
set -euo pipefail

readonly SERVICE_NAME="${1:-nginx}"
readonly TIMEOUT="${TIMEOUT:-10}"
readonly RETRIES="${RETRIES:-3}"

check_http_health() {
    local url="$1"
    curl -sf --connect-timeout "$TIMEOUT" --max-time "$((TIMEOUT * 2))" "$url" > /dev/null
}

check_tcp_port() {
    local host="$1"
    local port="$2"
    timeout "$TIMEOUT" bash -c "echo > /dev/tcp/$host/$port" 2>/dev/null
}

main() {
    case "$SERVICE_NAME" in
        nginx)
            check_tcp_port "localhost" 80
            ;;
        postgres)
            check_tcp_port "localhost" 5432
            ;;
        api)
            check_http_health "http://localhost:8080/health"
            ;;
        *)
            echo "Unknown service: $SERVICE_NAME" >&2
            exit 1
            ;;
    esac
}

# Retry-логика
attempt=1
while [[ $attempt -le $RETRIES ]]; do
    if main; then
        exit 0
    fi
    echo "Attempt $attempt/$RETRIES failed, retrying..." >&2
    sleep 2
    ((attempt++))
done

echo "Service $SERVICE_NAME is unhealthy after $RETRIES attempts" >&2
exit 1
```

### Шаблон: Атомарное обновление конфигурации

```bash
#!/usr/bin/env bash
set -euo pipefail

readonly CONFIG_SRC="$1"
readonly CONFIG_DST="/etc/myapp/config.yaml"
readonly BACKUP_DIR="/var/backups/myapp"

validate_config() {
    # Пример: проверка YAML-синтаксиса
    python3 -c "import yaml; yaml.safe_load(open('$1'))" 2>/dev/null
}

reload_service() {
    systemctl reload myapp
}

main() {
    # 1. Валидация исходного конфига
    if ! validate_config "$CONFIG_SRC"; then
        echo "ERROR: Invalid configuration" >&2
        exit 1
    fi
    
    # 2. Создание бэкапа
    mkdir -p "$BACKUP_DIR"
    cp -p "$CONFIG_DST" "$BACKUP_DIR/config.$(date +%F-%H%M).yaml"
    
    # 3. Атомарная замена через временный файл + mv
    local tmp_config
    tmp_config=$(mktemp)
    cp "$CONFIG_SRC" "$tmp_config"
    mv -f "$tmp_config" "$CONFIG_DST"
    
    # 4. Перезагрузка сервиса
    if ! reload_service; then
        echo "ERROR: Failed to reload service, rolling back..." >&2
        # Простой rollback: восстановить из бэкапа
        cp -p "$(ls -t "$BACKUP_DIR"/config.*.yaml | head -1)" "$CONFIG_DST"
        exit 1
    fi
    
    echo "✅ Configuration updated successfully"
}

main "$@"
```

### Шаблон: Параллельное выполнение задач

```bash
#!/usr/bin/env bash
set -euo pipefail

readonly MAX_PARALLEL="${MAX_PARALLEL:-4}"
readonly SERVERS=("web1" "web2" "web3" "web4" "web5")

deploy_to_server() {
    local server="$1"
    echo "[$(date '+%T')] Deploying to $server..."
    # ... реальная логика деплоя ...
    ssh "$server" 'bash -s' < deploy-remote.sh
    echo "[$(date '+%T')] Completed $server"
}

# Ограничение параллелизма через fifo
run_parallel() {
    local max="$1"
    shift
    local fifo
    fifo=$(mktemp -u)
    mkfifo "$fifo"
    exec 3<>"$fifo"
    rm "$fifo"
    
    # Инициализация "токенов"
    for ((i=0; i<max; i++)); do
        echo "token" >&3
    done
    
    # Запуск задач
    for task in "$@"; do
        read -u3  # Ждать доступный токен
        {
            $task
            echo "token" >&3  # Вернуть токен после завершения
        } &
    done
    
    # Ожидание всех фоновых задач
    wait
    exec 3<&- 3>&-
}

# Использование
tasks=()
for server in "${SERVERS[@]}"; do
    tasks+=("deploy_to_server $server")
done

run_parallel "$MAX_PARALLEL" "${tasks[@]}"
```

>[!TIP] Когда использовать параллелизм
>Параллельное выполнение ускоряет операции на множестве хостов, но требует идемпотентности задач и обработки ошибок. Для сложных сценариев рассмотрите [[Synced/DevOps/IaC/5. Ansible (Основы)/1. Архитектура.md | Ansible]] с `strategy: free` или специализированные инструменты.
